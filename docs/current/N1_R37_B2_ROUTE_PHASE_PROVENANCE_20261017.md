# BSC 新版 Native 第37轮（当前对话第3轮）：B2 路线两阶段生成、引用保持与成员 packet 同源

日期：2026-10-17。研究对象：用户提供的《Total War: WARHAMMER III》Windows x64 `Warhammer3.exe`，**SHA256** `9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`，文件大小 `232531920` 字节，PE ImageBase `0x140000000`。所有本文地址均为 **RVA**；ASLR 下不等于运行时地址。

**研究类型：仅静态、只读。** 未 Hook 游戏，未修改 EXE，未获得任何新版 Shift 折返的实例级动态证据，未制作 gameplay patch。不再重复证明已由玩家确认的同兵牌成员挤压问题。

## 1. R36 留下的关键问题，已经闭合到同一个 B2 类型

R36 已证明存在 B1/B2/B3 三种 Group 内嵌任务，但仅检查各自 `virtual+0x10`，尚未知道 B2 `+0x78` 的生产者；因此旧报告中的“B2 需要等待其它任务填入未知路线”不完整。

新版 B2 构造器 `0x03268D34` **真实安装** vtable `0x03AE5800`，其两个方法槽均已重新读取 `.rdata` 中的实际指针：

| 方法 | 真实 RVA | 已确认职责 |
|---|---|---|
| `B2 vtable+0x08` | `0x03276970` | 先检查 `B2+0x60`：已有路线可条件性直接发 packet；否则生成/更新 `B2+0x78` 路线节点 |
| `B2 vtable+0x10` | `0x032863A0` | 先检查已发送标志 `B2+0x80`；未发送且 `+0x78` 节点准备好才走延后发包 |

因此，**同一个 B2 实例存在“直接路线”与“等待路线节点”两条受条件保护的原生执行路径**。不能再把 B2 说成始终晚于创建而发送，也不能将两条路径算作必然两次成员发包。

## 2. 新增：B2+0x60 直接路线数据来自创建时的 shortTask 转换器

准确的创建链如下，所有箭头经新版原始 EXE 字节、真实指令起点、分支及具体成员字段核对：

```text
shortTask 转换函数 0x02F54510
  0x02F545DA CALL 0x03126A58  -> 返回路线 node
  0x02F545E2 MOV RDX,RAX       -> RDX=node
  0x02F545E5 RCX=shortTask
  0x02F545EB CALL 0x02F3BB44 -> 发布路线记录到 UnitRoot+0x270
  0x02F545FF MOV RDX,[node+0x70] -> 当前 node 的路线数据指针
  0x02F54613 CALL 0x03268DD4 -> [临时record+0x28]=RDX
  0x02F54621 读取 UnitRoot+0x32F8 当前 Group
  0x02F54628 CALL 0x0327ED4C
    0x0327EDD5 CALL 0x03268D34 B2 ctor
      0x03268D7C 从 [record+0x28] 读取指针
      0x03268D80 复制到 B2+0x60
      0x03268DBF 初始化 B2+0x78=NULL
      0x03268DC4 初始化 B2+0x80=0
```

关键不是同一个字段偏移，而是 **同一调用栈的 node → 记录实参 → B2 构造器 → +0x60** 数据流，外加构造器安装的唯一具体 B2 虚表。原生基础构造器 `0x030C861C` 是无下游 CALL 的叶函数、完整指令没有修改 R11，因此已核验 B2 构造器在直接 E8 之后读取此前 `R11=R8` 记录指针的身份。**这不能推广为 Win64 volatile R11 在任意函数间都安全。**

## 3. 新增：`UnitRoot+0x270` 对 node 有实际引用保持，而非仅存一个裸指针

创建时 `0x02F3BB44`：

- 先 `0x02F3BB58 CALL 0x0301E890` 清理原路线记录；该叶函数在旧记录 `+0x80` 标志非零时，`0x0301E8A2` 对旧记录关联 `node+0x04` 做 **decrement**。
- `0x02F3BB97` 将新 node 记入新 `record+0x18`；`0x02F3BBB8` 对相同 node 的 `+0x04` 做 **increment**。
- `0x02F3BBBF` 写 `UnitRoot+0x270 = record`。

因此，“B2+0x60 来源不明、创建时即无保持”的说法不正确。至少当前路线记录对**节点**的引用增加/释放是真实存在的。然而不能据此推定 `B2+0x60` 所指的**路线缓冲区**独立 AddRef，亦不能在未观察节点回收与消费的时序时断言发生悬空指针或跨代错误。

## 4. B2 路线直接/后备分支的成员发送条件

**B2 `virtual+0x08=0x03276970`**：

- 读取 `B2+0x60` (`0x03276982`)。非 NULL 时以其构造成员发送记录，`0x032769F2 → 0x0326A994`，并在 `0x03276A03` 设置 `B2+0x80=1`；直接分支跳过后备节点生成。
- 若 `B2+0x60==NULL`，先根据是否存在旧 `B2+0x78` 有条件减少旧节点引用，在 `0x03276A68` 调用 `0x03126A58` 生成节点，在 `0x03276A6D` 保存到 `B2+0x78`。**这里没有直接成员发送调用。**

**B2 `virtual+0x10=0x032863A0`**：

- 若 `B2+0x80!=0`，`0x032863B7` 跳过本次发包路径。
- 若未发送，则检查 `B2+0x78!=NULL`（`0x032863BD/C1/C4`）以及 `node+0x08!=0`（`0x032863CA/CE`）。满足条件后，读取 `node+0x70` 并在 `0x03286445` 调用**同一个** `0x0326A994`，随后条件性设置 `B2+0x80=1`。

两个位置的 sender **完全相同**，均为 `0x0326A994`，由它遍历已传入的 Group 成员数组 `Group+0x28`、数量 `Group+0x24`，逐成员通过 `vtable+0x368` 调用接收器。

**不能宣称**所有 B2 一定直接发包、fallback 一定成功、某次 Shift 一定选择哪条分支。后备节点的 `node+8` 状态位非零，也尚未被证明保证 `node+0x70` 永远非 NULL；不要把这一个潜在静态条件缺口提升为已发生的 Shift 挤压根因。所有“可发包”判定仍以其它调用成功、任务时序和成员接收门槛为前提。

## 5. 同一发包函数，不代表所有士兵在同一个动作相位

通过类型化 B2 sender 进一步连回成员入口 `0x03070A48`：

- 首先按 Group 模式与 `packet+0x50 bit0x20` 决定是否创建内嵌动作任务。
- 进入成员虚表动作方法时，再由 **每名成员自己的** `member+0x104` 分流 `+0x100` 或 `+0xE8`（先前 R33 已发现，此处将 B2 实例明确连接过去）。
- 后续 `member+0x1E0` 目标提交、world goal 解析、`member Tick` steering 与接触输出，并**不因为一次群组发送器循环完成就自动构成原子状态快照**。

**本轮消除的低价值猜想：** B2 在 ctor 时 `+0x78=NULL` 是正常初始化，并不证明缺路线或早期坏 packet；B2 直接与后备路径在已确认分支中被 `+0x60` 及 `+0x80` 门槛分隔，不能默认同一实例重复发两个 packet。

**仍然开放的高价值问题：** B2 某一路成员 packet 已被接受后，各成员的 `inline action`、`member+0x104`、`member+0x108 bit4`、`member+0x324`、世界目标及 steering 更新是否在相同真实 queued MOVE 下发生不兼容的跨相位运动。需要最终物理位移／速度真实写者或具实例生命周期的安全观察窗口才有资格判断因果。
