# BSC R61 / 本对话第27轮 — 全资源交叉审计、R60 延迟清理闭环补充与转弯研究止损

日期：2026-10-22。最终目标始终是**改善原生 CA Shift 连续 MOVE 折返时的平滑度，并减少同兵牌内部成员相互穿插挤压**，不重新用 Lua 驱动队列，不牺牲寻路、渐进转弯、避障、普通 RMB MOVE 或 Shift ATTACK。

**本轮安全边界：仅在用户提供的本地新版游戏 EXE 上进行只读机器码分析；完整原始 EXE、Derpy `.pack`、memreader Plus DLL 或运行时指针均不随本报告/ZIP/GitHub 分发。没有 Native Patch，没有运行游戏/第三方 DLL，也没有获得新的 Shift 同实例动态记录。**

## 2. R61 真正新发现：R60 忽略了一条类型化的间接清退链

新版 EXE 固定 SHA、PE unwind 边界和 GNU objdump 真实指令起点确认以下直接调用：

```
普通成员 vtable 0x03912950 +0x368 → 0x03070A48
   ↓ 立即接收成员状态不是 1/2
普通成员 vtable +0xE8 → 0x03078268
   0307827C  检查第六参数是否非零；本 receiver 固定传 1
   03078290..2AE  读取 [member+0x58]+0x440→+0x150→+0x28
                       条件 m∈[6,9]
   030782B0  E8 → 0x0307AE84
                         0307AE8A  member+0x324=0
                         0307AE94  RCX = &member+0x490
                         0307AE9B  E8 → 0x02DB5AC4   条件清退旧延迟任务
                         0307AEA7  E8 → 0x02DB5A20   清退旧 action
                         0307AED1  E8 → 0x0324D994   构造新 action
   030782CF  E8 → 0x03163DC4 （随后位置和状态处理）
```

关键 Win64 栈别名：接收器 `0x03070B74 MOV [RSP+0x28],1` 设置**第六调用参数**；`0x03078268` 经过一次 push 和 `sub rsp,0x30` 后，在 `0x0307827C CMP BYTE PTR [RSP+0x68],0` 读取这个相同的参数。它不是随意的、可能未初始化的内存。在此特定接收器 +0xE8 路径，原生第六参数为1。

进一步扫描整个新版可执行 `.udata` 的所有 E8 rel32 候选并要求 PE unwind/真实指令 `call`：

- 延迟任务清理器 `0x02DB5AC4`：**81 个**经过验证的直接调用者，远多于 R60 在成员接收器自身找到的一处。
- 类型化清理包装器 `0x0307AE84`：**2 个**直接调用点，`0x030782B0` 与 `0x03078985`。
- 其中 `0x03078985` 属于**普通成员 vtable+0x478 → 0x03078944** 的另一条原生状态恢复方法，不依赖 packet 接收器本体；特殊成员 vtable+0x478 又在 `0x0307860D` 调用该方法。普通成员、特殊成员对应虚表地址均在新 EXE 中实际核对。

**纠正 R60 的解释：** “接收器 immediate 分支没有对延迟槽的直接 E8”依旧正确；但“因此旧延迟任务不会在这次状态更改中被取消”不能成立。已证明存在真实的 transitive cleanup。不过，是否在某次用户 Shift 折返中进入具体清理分支，目前未知；并非所有立即路径都会清理。

## 3. 另一个重要约束：B2 恒清 flag0x20，并且使用同一个原生模式 helper

直接确认无 unwind 叶函数 `0x02DC7E30..0x02DC7E48`：读取 `context+0x28`，并用比特掩码 `0x29` 判断，返回 `true` **恰好对应模式 0、3、5**；函数体没有改写 RDX，也没有进一步 call。故接收器在 `0x03070A87` 使用 `RDX+0x50` 时，不能仅因 Win64 的 RDX volatile 约定就判定该 packet 地址丢失——这个具体 helper 已被全指令核对保留 RDX。

同一个 `0x02DC7E30` 被 Group A/B 分派器 `0x0327ECA4 → 0x0327ECC6` 使用，也被成员 packet 接收器 `0x03070A48 → 0x03070A7B` 使用。**两者都沿各自的所属对象链读到 `context+0x150`，但尚未实机证明所有实例的两个上下文指针地址相等。**

B2 发送器 `0x0326A994` 使用的构造器 `0x02F648E4` 确认先过滤输入两个低位，再置 `0x06`，可额外置 `0x08`，本发送器还有对 `0x40` 位的操作；**没有置 `0x20` 的已审计路径**。R61 重新逐指令检查了 `0x02F64926/31/3A/48/66` 的来源与写入。

因此，在上下文**模式保持不变**且 packet 确实来自上述 B2 构造路径的严格条件下，连续两条此类 packet 在普通成员接收器中只能保持**同一种延迟/立即门槛**，不能仅靠 packet 内容变成 D1 延迟→I2 立即：

| 模式 m | B2 packet bit0x20=0 | 该模式下 `+0xE8` 的已证清退门槛 |
|---|---|---|
| 0、3、5 | helper=1 → 立即分支 | 不因 m=6..9 条件而清退 |
| 1、2、4 | helper=0 → 延迟分支 | 非 applicable |
| 6–9 | helper=0 → 延迟分支 | **如果来自其它 packet 的 bit0x20=1 使其立即，并且走 +0xE8**，则先清退旧延迟任务 |
| >=10 | helper=0 → 延迟分支 | 未通过现有 m=6..9 分支证明清退 |

**严谨限定：** 这个不变量不排除不同 packet 种类介入、上下文模式实际改变、`member+0x104 ∈{1,2}` 的另一方法、其它成员派生类型或间接清退。R60 的 H60 应降为**有额外先决条件的低优先级假说**，不能按旧表述直接发布“清旧延迟任务”补丁。

## 4. 接下来要如何真正改善原生 Shift 的转弯流畅度

以减小试错为原则，调整候选优先级：

1. **首选：同一次后继 MOVE 的实际世界坐标目标是否连续。** 将 R53–R57 已证的源位置 C（可能带参考框架）、阵型范围 D 与 16 位朝向 θ，和后继成员 `+0x1E0/+0x1F0` 世界目标及真实积分输入联系起来。只有真实的 
   `P_before=C_before-0.5*D_before*V(theta_before)`、`P_after=C_after-0.5*D_after*V(theta_after)` 无法由下游平滑处理，才考虑在 CA 原生路线构造上做局部修复。R57 ±90° 侧向角度虽然可能出现二值跳变，**但还没有被证明它导致世界目标跳变**；不可全局改角度常量。
2. **次选：成员级动作状态和原生目标预瞄的匹配。** R38 证明成员会有自身朝向补偿；R41–R45 证明积分器与 action 阶段可不同步；Derpy 源码显示单兵 prelook 距离对自身速度有影响。必须看同一单位不同成员的 `active action / current goal / actual position`，不能把 Derpy 的 WASD 目标距离直接套成 CA 原生 Shift 常数。
3. **H60 停止单独滚雪球。** 现在知道 B2 packet 固定标志、mode helper 条件和两条原生清退路径，继续纯粹搜索相同 `+0x490` 字段的收益较低。只有静态或旧日志证明了“模式改变／其它 packet 到来、已延迟任务仍有效、最后确实提交旧运动目标”三件事，才重启此候选。**没有这些证据，不能以防止旧包覆盖为由清空成员任务。**

未来少量取证应优先利用 `memreader Plus 0.13.0` 的类型化只读接口与 Derpy 已验证的成员指针数组入口，配合 R49/R51 的采样预算和失败封闭；**工作线程与 Lua 无原子屏障，未经验证不得直接交给玩家运行**。更精确的低频原生状态检查与一个带完整实例身份的有界采样，明显好于十几轮盲扫 RVA。
