# BSC N1 / 2026-10-13：成员延迟任务与动作模式来源 — 46 处原生校验

## 本轮最重要的纠正

**不能把成员接口 `+0x580` 定义为“普通 RMB”，也不能把 `+0x5B8` 定义为“Shift”。** 在精确原版 `Warhammer3.exe` SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a` 上，已经发现同一成员对象的 **`+0x348` 定时任务工厂**、两种定时回调，以及由 *任务内部模式字节* 触发的 `+0x580`／`+0x4B0` 分叉。另一个几何分发器还可以安装 `+0x5B8` 子类，因此静态已知至少 **三类不同成员动作对象**。

### 1. 明确的同一对象类型

同一套成员虚表 `0x038FD658` 和 `0x03910500` 各有：

| 槽位 | 相同原生实现 | 目前严格可证的用途 |
|---|---|---|
| `+0x348` | `0x0306B510` | 清理并在 `member+0x4A8` 构造定时任务 |
| `+0x368` | `0x0306B9F0` | 前次日志已确认的成员目标接收器 |
| `+0x4B0` | `0x03069844` | 根据成员现有动作与延迟任务门槛，有条件替换 `member+0x330` 动作 |
| `+0x580` | `0x0306A990` | 安装动作子类 `0x03913808` |
| `+0x5B8` | `0x0306A8C0` | 几何分发接口，安装动作子类 `0x03ADAA08` |
| `+0x5F0` | `0x0306B0F8` | 另一类成员命令消费接口，本轮尚不赋予 Shift/RMB 键位标签 |

`0x0306B510` 对 `[member+0x490]` 旧控制区调用 `0x02DB0AB4`，然后把新任务放入 `member+0x4A8`：
`0x0306B53B CALL 0x02F5F1E8`。此构造器通过
`0x02F5F1FD lea ... -> 0x03906C88` 安装定时类，其
`+0x08 = 0x02F7301C`、`+0x10 = 0x02F83868` 都按群组时钟和初始化时刻检查后调用同一 `0x02F79BB8`。初始化时刻还使用同群组时钟和伪随机状态；不能当作固定间隔命令。

### 2. 定时任务里动作模式字节的**真实传递路径**

**`0x032638C4`** 初始化一份任务描述符，在
`0x032638D7 mov byte ptr [rcx+0x02],0` 将 mode 置零；
例如 `0x032774B0`、`0x03277B6E`、`0x0327BD0B`
会调用此生成器，随后分别调用成员虚函数 `+0x348`。

在 `0x02F5F1E8` 任务构造器里，`0x02F5F207 lea rcx,[rdi+0x40]`，
`0x02F5F20E CALL 0x02D99E58` 复制描述符：
`0x02D99E64 movzx eax,byte ptr [rdx+0x02]`，
`0x02D99E68 mov [rcx+0x02],al`。

所以 **`descriptor+0x02` 被复制到定时任务 `task+0x42`**，然后
`0x02F79BCD cmp [rcx+0x42],dl`、`0x02F79BD0 je`
分出：
- **非零：** `0x02F79C3D virtual+0x580`
- **零：** `0x02F79CB6 virtual+0x4B0`

初始描述符为零的这几条分发路径，与后来调用 `+0x580` 的路径绝不应自动合并；
不过其他写字段及后续状态变化尚未穷举，不能断言这一字节在存续期间永不改变。
`0x02F79CC4` 的另一条模式处理还可调用 `+0x580` 或 `+0x5F0`。

### 3. 第三种真实成员动作子类不是同义函数

`+0x4B0` 入口 `0x03069844` 首先检查：
`member+0x324`、`member+0x5C0`、
`member+0x4A8` 定时任务 `virtual+0x80` 和
`member+0x330` 当前动作的虚函数状态。
满足相应替换条件时，`0x03069910` 先清理
`member+0x328` 控制区，再在 `0x03069924` 调用
`0x0304E5D4` 安装 **第三类 `vtable 0x03ACD208`**，
其 `+0x08=0x0307C388`，与先前
`+0x580 -> 0x03913808 / tick 0x032599C8`、
`+0x5B8 -> 0x03ADAA08 / tick 0x03259950` 都不同。

若描述的目标指针有效，`0x0304E5D4`
还从目标对象的 `+0x88/+0x90` 减去成员的
`+0x88/+0x90`，把**当前成员到目标的相对 X/Z 位移**
写到新动作对象的 `+0xE0/+0xE4`；
这既不同于旧子任务方向的对称投影公式，也不是纯粹复制新子任务四个 float。
在此动作的 tick `0x0307C388`，还能观察到
`member+0x270` 写 1、某条件下清理成员 `+0xB11` 标志 0x20，
以及虚表 `+0xC8` 回调；**不允许直接改这些成员标志**。

### 4. 重新理解普通 RMB 与 Shift MOVE

**静态已确认的相同点：** 两者最终可能使用同一 CA MOVE 任务生成器与士兵运动系统，合法的多路成员动作选择由原生命令/任务状态决定。

**静态已确认的不同点：** 统一 MOVE 入口 R9B/DL 决定 clear/append 队列；后继队列槽位可以条件性复用前一个大任务，重建新段几何并有条件继承旧子任务投影。**除此之外还存在同一成员的定时任务模式、旧动作状态和至少三种子类安装。**

**尚未证实的关键：** 哪一条 Shift 后继 MOVE order 实例产生了 `descriptor+0x02` 的实际值、最终选择了哪一类成员动作、何时消费 old/new 几何，以及不同成员为何出现目标穿插。不能仅凭 vtable 区分玩家键位。

本轮独立在原始 EXE 上：**46/46 原字节及指令起点、10/10 直接 E8、18/18 同类型/任务虚表槽 PASS**。只读工具
`maintenance_tools/native_shift_re/audit_member_timer_mode_lineage.py`，
回归 `tests/test_native_shift_re_member_timer_mode_lineage.py`。公有 CI 不包含原始 EXE，因此只测试静态合同；原始真 EXE 的离线检查在本地执行。
