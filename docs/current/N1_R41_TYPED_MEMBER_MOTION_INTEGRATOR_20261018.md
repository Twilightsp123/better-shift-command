# Better Shift Command — R41：新版 EXE 普通士兵运动积分写入闭合（2026-10-18）

## 目的、成果和界限

本轮只读分析使用用户提供的新版 Windows x64 `Warhammer3.exe`：完整 SHA256 `9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`，大小 232,531,920 B，PE ImageBase `0x140000000`，下文均为 RVA。**发现了真实普通成员类型的可达运动积分函数，并证实它在同一个成员对象上把空间运动增量写入实际 XYZ 坐标和运动向量**。这是相比 R39 的“对子对象按外部新位置同步”的不同新证据。未进行 Windows 游戏内 Shift 折返动态观测，也不宣称已经找到用户已证实的挤压 Bug 的具体原因。

本轮独立静态审计：**14 个 PE unwind 函数范围，134/134 指令字节及 GNU objdump 真正指令起点，14/14 E8 调用，7/7 JMP/JCC 目标，7/7 成员虚表槽**；另在整段可执行 PE 节扫描 `0x03146FF0` 的直接 E8 调用者，恰有 **3** 处且均为实际解码的 `call`。本地 **16/16 unittest PASS（含真实新版 EXE）**；无 EXE 环境 **15 PASS / 1 SKIP**。这些是**本地**结果，不能表述为 GitHub CI PASS。

## 一、定型普通成员及特殊成员的物理更新虚方法

普通成员构造器 `0x03052BA8`：在 `0x03052D20` 装入真实虚表 `0x03912950`，`0x03052D34` 存至普通成员对象。

| 具体对象的 vtable | 槽位 | 真实目标 | 本轮意义 |
|---|---|---|---|
| 普通成员 `0x03912950` | `+0x18` | `0x03086F04` | 主 Tick，原已确认呼叫 steering `0x03059BC8` |
| 普通成员 `0x03912950` | **`+0x20`** | **`0x030592BC`** | **本轮定型的运动/位置更新方法** |
| 普通成员 `0x03912950` | `+0xF0` | `0x03164710` | 另一个成员更新方法，非本轮积分器 |
| 普通成员 `0x03912950` | `+0x100` | `0x030785AC` | 原 B/A packet 的一种成员方法，E8→`0x0316460C` |
| 特殊派生成员 `0x03AD3360` | `+0x18` | `0x03086224` | 派生主 Tick |
| 特殊派生成员 `0x03AD3360` | **`+0x20`** | **`0x03058D2C`** | `0x03058D5E` 先 E8→普通成员 `0x030592BC`，再进行子对象处理 |
| 特殊派生成员 `0x03AD3360` | `+0xF0` | `0x03164710` | 与普通成员共用另一个更新方法 |

此处借由**同一具体构造器装表 + 固定类型虚表槽 + 真实 E8 调用**保证对象身份，避免此前“其它 component+0xE0 误认 member”的问题。派生类型的位置同步是额外操作，而不是证明普通成员没有独立持续积分。

## 二、普通成员 `+0x20` 的条件分派

`0x030592BC` 将输入 `RCX=member` 存入 RBX（`0x030592C8`），随后：

```text
member+0x108 & 0x10 非零 ─────────────────┐
                                       ├─ 0x030592FF E8→0x0310006C
否则 member+0xB20 非 NULL 且 +0xB28 == 4 ┘

否则 → 0x030592F8 E8→0x03146FF0
```

`0x0310006C` 是**另一种成员运动包装/条件路径**，它本身两处调用同一积分器：`0x031000F6` 和 `0x0310014C`；还在 `0x03100233` 获取 `&member+0x1E0`，于 `0x03100247` E8→`0x03121F54` 解析世界目标。注意同一方法存在不同分支，其中一次明确在积分器调用后才解析当前世界目标；不可把该目标读取简单描述成总是本次积分前的输入。

可执行节**所有**满足 E8 相对目标 `0x03146FF0` 的编码仅有：`0x030592F8`、`0x031000F6`、`0x0310014C`。均通过 PE unwind 所有者/objdump 指令起点交叉验证。这约束直接调用者，但**不能排除间接引用、函数指针或特殊时序**。

## 三、积分器同一成员上的实际位移/运动字段写入

`0x03146FF0` 在 `0x03147019 MOV RBX,RCX`，此后下列字段均访问同一类型的当前成员对象，分两种条件路径。

| 功能 | 第一组真实 RVA | 第二组真实 RVA | 实际字段 |
|---|---|---|---|
| 叠加 XYZ 空间增量 | `0314720B/223/23B` | `03147E85/E9D/EB5` | `member+0x88/+0x8C/+0x90` |
| 根据增量写运动向量 | `03147281/293` | `031483BD/3CF` | `member+0xE0/+0xE8` |
| 更新成员自己的待应用增量 | `03147199/A1` | `0314745D/465/46D` 等 | `member+0x13C/+0x140/+0x144` |

实际证据如 `0x031471ED MOVSS xmm0,[rbx+0x88]`、`0x031471F5 ADDSS xmm0,[rbx+0x13C]`、`0x0314720B MOVSS [rbx+0x88],xmm0`，其他坐标有等效计算；**是将运动增量积分进已有 XYZ**，并非仅复制外部世界坐标。第一组运动向量运算使用实际 PE 映像中的 `0x03922388` 初始浮点 **1000.0** 及 `0x03D0E294` 初始整数 **100** 作为比例相关输入。后者在可写节 `.srdata`，不能仅从镜像的初始值断言运行时恒为 100、更不能直接称之为“引擎帧计数”。同样不得将 +0xE0/+0xE8 的物理单位未经验证说成米/秒。

本轮补充发现：积分器**自己也写** +0x13C/+0x144，见 `0x03147199/A1`；在第一种路线上完成积分后，又在 `0x031472C3/D1` 用零值初始化的二进制全零记录清理此运动增量。这说明 +0x13C/+0x140/+0x144 不仅仅是“来自未知外部写者的输入”，它是本函数参与更新的中间运动状态；其其它写者和全部生命周期尚未闭合。

## 四、成员 packet 与积分选路之间最值得追的状态桥

积分器在 `0x031471A9` 读取 `member+0x108`，`0x031471B5 TEST DL,0x02`，`0x031471B8 JNE 0x0314738F`，此后经不同积分/修正路径更新成员。此前 R38/R33 中已定型的两类 packet 成员位置方法，在新版中分别由 `0x03164676/7F/81` 和 `0x03164477/80/82` 执行 `flags=(flags & 0xF7)|0x02`：**清 `bit0x08`，设置 `bit0x02`**，且不清 `bit0x04`。本轮将这个写入与同类型真实积分器的 `bit0x02` 读取位置组成静态数据控制闭环。

这只说明 packet 接收器可能改变后续积分分支；**并不证明该组士兵一定由同一 queued Shift 实例触发**，更不能把允许的逐成员状态差异本身叫 Bug。下一个真正有价值的假说，是这种原生分支切换是否在路点折返附近产生不兼容的已应用增量或不一致的 world goal；需要以相同成员、同一更新代际的数据核验，而非单靠机器码字符串相邻。

## 五、调度边界仍不允许过度肯定

确认 `0x0304874C` 的 `0x03048888 E8→0x0304C72C`，后者遍历 `UnitRoot` 三组对象集合，分别在 `0x0304C75D/788/7B3` 调用元素 `virtual+0x20`。但三个容器内元素的具体对象类型尚未全部闭合，**不能由“槽位也是 +0x20”直接认定当前普通士兵每次都会受其调度**。本轮验证的是**类型化成员方法及其内部持久运动写入**，不等同于确证每个 Shift 战场实例的物理更新时刻。

R40 已证明的 `0x03085114→0x02DD06F0→订阅者/事件队列` 属事件路由，而非本轮这一确定成员运动写入链。R39 的 `0x031612E8/0x031614C0` 涉及特定同步场景，不能简单替代这里的增量积分。静态状态表不证明 runtime 队列某次触发了这些入口。

## 六、结论及下一步只追一个问题

- **新增正证据**：普通成员 vtable+0x20 确切映射到 `0x030592BC`；其后静态直接边闭合至 `0x03146FF0`，对同一成员的 XYZ 和运动向量确有增量积分写入；还连接了 packet 设置 bit0x02 与积分器读取 bit0x02。
- **新增反证/纠错**：事件广播器不是这条直接积分路径；`+0x13C` 在积分器内部也有写者；位于可写数据节、镜像初值为 100 的标量不能冒充固定帧计数；Root 三组 virtual+0x20 容器未完全类型化。
- **尚未证明**：Shift/RMB 在同条件的逐成员 bit2/Delta/world goal 是否有异常顺序；Group 与路线跨代混用；真正的挤压根因；安全 Native Patch 位置。
- **Gameplay 补丁**：**没有**；`native_patch_authorized=false`；未经证明不全局 NOP `0x03146FF0` 或清 `member+0x108 bit0x02`。

**下一轮唯一优先问题：** 继续从 `0x03146FF0` 读写 `member+0x13C/140/144` 的定义、积累、修正和清退顺序出发，追踪相同成员的目标 `+0x1E0` 在什么分支影响这些增量；如果不能确立真正的目标—运动差异，则停止此候选，转向其它积分输入，不要求用户重新证明缺陷。静态和离线验证优先，实机观测须先通过安全门槛。
