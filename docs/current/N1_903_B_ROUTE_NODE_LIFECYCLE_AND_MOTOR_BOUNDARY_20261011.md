# N1 / WH3 9.0.3 — B 路线节点的生产、更新、回收与成员运动消费者边界

> **分析日期：2026-10-11；全部地址为 ImageBase 0x140000000 对应 RVA。**
>
> 原始 EXE SHA256：`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`。只读验证器 **58 个固定机器码守卫、20 条 E8 调用边、20 项原始 EXE / 离线测试通过**。本次没有启动游戏、没有启用 DLL，也没有证明旧 V3 真正执行 B 分支。

## 先说明调查问题与结果

本次问的是：「B 分支生成的群组路线对象**在哪里存储、谁在群组更新时消费、旧路线什么时候失效**，以及是否能接通**主兵模实际路线／移动控制**」。

**已证实：** B 分支生成的路线节点以链表方式保留在 **群组路线控制器 `group+0x160`**，节点内部 `+0x70` 持有一份几何路线。下一次及后续群组更新中，`0x02DD579C→0x03128E80` 会处理这张链表；节点变为 `+0x4==0` 后才会摘链、回收并释放几何路线。对于尚未生成几何路线的有效节点，一次群组管理器调用**最多填充一个缓存**。A 分支也调用 `0x030FDA9C` 构建几何路线，不过立刻把结果传给 `0x030D5490` 成员目标分发，随后释放临时几何路线。这是 A/B 行为上的真实区别：**直接生成并向成员分发 vs. 将路线几何保留在群组节点、稍后更新**。

**仍未证明：** B 节点的 `+0x70` 最终怎样变成普通士兵的实际运动方向。当前已核实的 B 任务消费者只是判断路线参考有效性、群组链表管理与延迟缓存生成，没有发现已证实的 `B.node+0x70 → member 的独立路线/速度字段` 的完整数据流；仍可能经其他上下文、虚函数或成员类型专用代码间接到达。这也是为什么保留节点**不等于**某名士兵仍在沿旧指令移动。

## 特别重要的三个差异和两条反证

1. **同一群组控制器**：B 任务 `0x032814DB–0x032814EF` 通过 `task+0x8→owner+0x440→group+0x160` 取得子路线控制器；群组更新 `0x02DD58D7→0x02DD58DE` 读取 `group+0x160` 并调用 `0x03128E80`。这样 B 创建的链表确实有原生定期维护者，不是孤立记录。
2. **引用计数式失效**：在 `0x0328147D–0x0328148C`，旧节点的 `+0x4` 被递减，B 任务中的旧节点指针被清空。**这一步不直接调用几何释放函数**；后续 `0x03129059–0x03129065` 只有看到节点引用计数归零才摘链。多个节点/多份引用可以暂时共存，但没有证据证明旧节点仍被士兵消费。
3. **延迟缓存填充的预算**：`0x03129038` 初始化本次完成数量为 0；`0x03128EC6` 设置目标为 1；`0x03129073` 比较并阻止超出；成功生成时 `0x0312909B` 增量。对于 `node+0x8==0` 的候选缓存，一轮管理器调用最多处理一个。**新建的有 prior 路线节点 `0x030ECB10` 初始 `+0x8=1`，因此并不是所有 B 节点都会受这个延迟预算。**
4. **误判反证 A**：`0x0310E770` 仅负责双向链表前后链接，不是运动积分器；`0x030F65AC` 是资源回收，不是开始沿旧路线运行。
5. **误判反证 B**：`0x02F83F44` 一类已识别成员的局部曲线在**成员自身** `+0xB60` 内存和进度 `+0xBCC` 运算，不能把这个字段当作 B 组路线节点 `+0x70` 的直接别名。不同士兵类型也不能套用同一字段。B 到真正主运动控制器仍需生产者—消费者证明。

## RMB 与 Shift 的确切区别以及本轮新增信息

普通 RMB 的新 MOVE 原生状态从空对象初始化；Shift 后继 MOVE 可以条件性续接共享原生路线状态。A 与 B 群组路径都由具体的 group mode 决定，**不是按玩家按没按 Shift 划分的两个独立引擎**。这轮多了一层**A 的瞬时目标分发与 B 的持久节点管理**区别；同为 Shift，也可能走不同群组模式。本轮不能把 B 节点共存当作 Shift 挤压的直接根因。
