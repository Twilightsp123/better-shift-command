# BSC N1 — 原生 RMB / Shift MOVE 整链节点审计（2026-10-11）

**对象**：用户提供的原始 Total War: WARHAMMER III Win64 EXE。SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，ImageBase `0x140000000`；下文地址均为 RVA。**本次只有静态反汇编和离线测试，不修改游戏、DLL 或队列。**

### 1. 命令交接（RMB 和 Shift 的第一处已知差异）

- 普通 RMB 非排队 MOVE：`0x030323C8 → 0x030090BC`，初始化 `MOVE+0xA0 = null`（`0x030090E7`）；这不是复制一套完全不同的士兵物理引擎。
- 合格的 Shift MOVE→MOVE 后继可以通过 `0x0304459D / 0x030445AB` 继承原生共享任务状态，再经 `0x03040864` 接收后继路线参数；`0x03025D70` 可进行兼容性检查，失败会丢弃该继承。普通 RMB 和 Shift 最终进入共用任务／路线求解体系。
- `0x02F561E8` MOVE 任务回调具有多周期子任务状态判定，不等同于“所有士兵已完成当前路点”。

### 2. 群组模式分支：A 和 B 都是真实原生代码，V3 选择未知

`0x02F561E8 → 0x03279E40` 检查群组模式；`0x02DC2E04` 对模式 **0、3、5** 返回许可，形成下述条件分支。

**A（符合模式）**：`0x030D554C → 0x030FDA9C → 0x030D5490`：准备成员目标记录，调用 `0x02F5F868` 构造 `0x26` 目标包，在一次函数调用的循环中依次调用成员 `virtual+0x368`；该包可能先执行个体朝向／坐标变换 `0x02F72520 / 0x0307F5C8`。公共接收实现 `0x0306B9F0` 可以进入 `virtual+0xE8 → 0x03073224 → 0x0315EC98`，并立即调用 `0x03078B1C` 处理成员当前模式。之后根据状态条件处置旧 `member+0x328` 子动作，并安装虚表为 `0x03914618` 的新动作；后续该动作通过 `0x0325C818` 更新。该分支在历史 V3 旧采集器上零命中，**不可声称当时 V3 实际采用 A**。

**B（不符合模式）**：`0x03263AB0` 创建另一张虚表 `0x03AE0128` 的群组任务，对成员调用 `0x03068C38` 做位置／方向分类，再逐个写 `member+0xB10` 的第 7 位。它的任务虚函数 `+0x10 → 0x03281408` 能进入 `0x03281444 → 0x03121ABC → 0x030ECB10 → 0x030FE1E4` 的几何建路体系（必要时通过 `0x030C1FDC / 0x030C7858` 生成／合并路段）。`0x030DEA20` 对该子路线的**路线段参考对象**做一致性检查；存在不一致就可以重建，**不是逐名士兵到达判定**。历史 V3 对 B 也没有群组模式／任务虚表运行采样，不能因 A 零命中就断言 B 一定命中。

### 3. 真正的对象和所有权：原生存在至少三张不同列表

**从 `0x02DD579C` 群组 Tick 的原始直接调用边逐项展开**：

| 群组对象成员 | 原生消费者 | 作用与重要限制 |
|---|---|---|
| `unit+0x1F0` | `0x02F853A0` | 上层／泛用任务管理，不是 B 子路线链表 |
| `unit+0x1F8` | `0x02F56B0C` | 另一独立群组服务 |
| `unit+0x150` | `0x02DD81B0` | 群组任务／阶段状态机，间接可以走到原生 MOVE 发令 |
| `unit+0x160` | `0x03128E80` | B 路线控制器，此对象**内部**另有路线计算列表与路线缓存链表 |
| `unit+0x178` 等 | `0x030B4EBC` 等 | 其他原生群组服务，未推断为士兵运动积分器 |

特别地，**`unit+0x1F0` 与 `route_context+0x1F0` 是不同持有者的同偏移，不能合并**。后者经 `0x03128E80 → 0x0311DE74` 处理路线计算列表。`route_context+0x2D0/+0x2D8` 才是 B 路线节点链表。

B 子节点的 `node+0x70` 存几何路线缓存；原生群组更新 `0x03128E80` 可对最多一个待填充路线缓存调用 `0x030FDA9C`；失效／引用计数归零者经 `0x03109D78 → 0x030F65AC` 摘链并释放。旧、新节点能够在内存中短暂共存，**但“内存未释放”不是“士兵仍在消费旧路段”**。

A 与 B 的部分几何生成共用 `0x030FDA9C`。因而 RMB/Shift 表现差异不应先归咎于存在两套本质不同的转弯物理。

### 4. 新接通的字段生产者—消费者：B 的成员方向标记

这次跨过此前反复检查的路线缓存，找到**一条真正由成员状态写入流向后续成员任务分支的数据通道**：

1. B 的 `0x03263AB0` 调用 `0x03068C38`，根据每个成员的当前位置／朝向计算，分别写入 **`member+0xB10` bit7**。同一兵牌中结果可以不完全相同。
2. `0x02F87684` 会读取这名成员和其关联成员的 bit7（位置在 `0x02F879C7 / 0x02F879D7`），结合方向／空间分类分支决定后续动作。
3. **消费者不是 B 群组任务本身，而是另一类成员任务的虚方法**：`vtable 0x03905D98 +0x78 → 0x02F87684`。活动任务的 `+0x28 → 0x02F85960 → 0x02F83E5C` 可以在正确实例上再通过虚 `+0x78` 进入它。
4. 负对照：`vtable 0x03905D18 +0x78 → 0x011287FC`，说明只看到“调用 v+0x78”也不能推定调用了 `0x02F87684`。此前包递交后可安装的子动作 `vtable 0x03914618` 和延后包任务 `vtable 0x03905E18` 也**不是**这张表。

**证据等级：**字段**写入／读取和条件任务虚表身份**有机器码支持；“V3 中 B 任务如何安装并激活该成员任务、其更新是否在折返发生”**还缺运行实例／对象身份边**。特别注意 bit7 的其他写入者也存在，它不是 B 独占的路点阶段位。

### 5. 每名士兵的接包、动作重算和最终运动不是一个屏障

- A 的已识别公共成员处理可以在收到目标时**即时**调用 `0x03078B1C` 修改 `member+0x318` 模式；`member+0x328` 子动作会按生命周期条件替换。
- 共用成员 Tick `0x03081EB4` 对 `member+0x318` 的**周期性重新判断**具有 10 个成员分组的门槛（默认原生参数），但是门槛**不包住所有位置或朝向更新**；已识别 38 张成员虚表能静态到达该共用 Tick。
- 某些类型还使用 `0x02F83F44`，按各自 `+0xB60/+0xBCC` 局部路线推进。不同成员类型复用内存偏移，不能将所有 `+0xBCC` 强行解释为同一个“路点进度”。
- `0x03071E04→0x03071F20→0x0311954C` 是另一组确实写入成员目标／运动状态的链，但已知接触／动作路径的调用来源不足以证明它就是当前 B 路线节点 `+0x70` 的最终消费者。

### 6. 额外被证实但不能误用的直接链

单从原生群组 Tick 出发，可以经真实机器码直接调用：

`0x02DD579C → 0x02DD81B0 → 0x02DC8820 → 0x030323C8 → 0x0302DB44 → 0x030D5490`

这些是**静态分支可达**的真实 call 链；不代表 V3 中某次调用每一级都执行过，也不代表与 `0x02F561E8→0x03279E40` 的条件 A/B 分支具有同一上游任务对象。

### 7. 现阶段可证与不可证

| 问题 | 等级 |
|---|---|
| 普通 RMB 新建、Shift 有条件共享路线状态续接 | **已证静态行为** |
| MOVE 的群组模式 A/B 两种原生任务 | **已证条件分发**；V3 当次未知 |
| B 路线几何、链表与更新／清理所有权 | **已证静态行为** |

| 已解析 A 接包时可即时重算，成员后续分组复查非全兵牌同步 | **已证静态机制**；并非物理转向延迟的直接测量 |

## 2026-10-11 原始 EXE 新增静态闭环：B 缓存 → 成员 packet、成员延迟 task

**真实性等级：原始 `Warhammer3.exe` SHA256**
`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`
**在本轮实际核验一致**；其机器码反汇编和字节验证已在本地执行。GitHub 公共 CI 仍不含游戏 EXE。
脚本与测试：`audit_b_route_to_member_packets.py`、`test_native_shift_re_b_route_member_packets.py`。
**没有修改原始 EXE、没有 Native DLL、没有实机运行。**

### 1. 之前遗漏的带对象类型数据边

**不能把三张 B 类任务虚表混为一张：**

| 原生虚表 | 已确认的虚方法 | 实际任务含义（静态） |
|---|---|---|
| `0x03AE00E8` | `+0x08 → 0x03271B0C`，`+0x10 → 0x03281520` | 缓存路线读取／向成员 fanout 的 B 子任务 |
| `0x03AE0108` | `+0x10 → 0x03281600` | 另一种子任务，不可直接以相同字段偏移套用 |
| `0x03AE0128` | `+0x10 → 0x03281408` | 旧审计已知的 B 主群组任务 |

- `0x03279EE8 → 0x03263EC4` 构造 `0x03AE00E8` 类型（调用 site `0x03279F71`）；构造时 `task+0x78=null`。
- 该子任务 `+0x08→0x03271B0C` 的 `0x03271C09` 可将 `0x031219B0` 返回的真实 B 路线节点写入 **这个 task+0x78**。
- **关键新增生产者—消费者：** `0x03281520` 在 `0x0328153D` 读 `task+0x78`，要求节点非空和 `node+0x8 !=0`（`0x0328154A`）；在 **`0x03281554`** 原始 `48 8B 40 70` 读 **`node+0x70` 几何指针**，并在 `0x03281566` 将其装入本地传递结构。之后 **`0x032815C5 → 0x03265B24`**。
- `0x03265B24` 取该结构的几何指针（`0x03265B8B`），经群组策略 `virtual+0x48` 生成成员目标；循环成员数组（`0x03265BD4`），逐名调用 `0x0326A3A0` 造包，最后经 **`0x03265D3F`：`call [vtable+0x368]`** 下发。
- 因此，**B 路线几何到“原生成员目标包下发”已存在真实静态对象/数据流闭环**。旧文档“B route 缓存只发现维护/清理读者”在这一点已过时；请以本节为准。

**限制仍然关键：** 到 `member virtual+0x368` 的目标包下发不是 `member+0x1E0` 的主 motor 写入证明。尤其常见接收器 `0x0306B9F0` 后续有模式/任务/子动作分支，不可省略。

### 2. 又找到了 B packet 的条件延迟任务边

- B 子任务成员建包函数 `0x0326A3A0` 可经 `0x0326A423` 或 `0x0326A466` 调用 `0x02F5F8DC`。该构造器将 `packet+0x4C=0`（`0x02F5F91A`），同时在 `0x02F5F940/0x02F5F95E` 构造 `packet+0x50` 标志。此处 **bit 0x20 恒未设置**，但其余 bit 会因构造参数而变化。
- `member virtual+0x368` 常见实现 `0x0306B9F0` 在 `0x0306BA23` 用 `0x02DC2E04` 检查**成员所属群组的模式许可**；许可失败且 `packet+0x50&0x20=0` 时，于 `0x0306BA5B` 调用 `0x02F5F7C8` 安装**另一张独立的延迟成员任务** `vtable 0x03905E18`。
- 延迟任务 `+0x10→0x02F83B24`。在 `0x02F5F843/0x02F5F84A` 初始化 `task+0xA0 = group_tick + packet+0x4C`；`0x02F6B170` 后续读取 `task+0xA0`，在 `0x02F6B18A` 对比原生群组 tick。**这不是每名士兵主 motor 同时切换的屏障证据**。
- `0x03905E18` 是**延迟包任务**，不同于 bit7 消费任务 `0x03905D98`、正常 packet 动作子对象 `0x03914618`。
- 在发令源和成员接收器**确实属于同一群组模式**的前提下，B 模式分支和该延迟任务分支具有静态条件对应关系。不能据此断言旧 V3 的具体兵牌已执行该条件。

### 3. bit7 工厂已经补到真正的虚函数入口

完整 EXE 数据段精确指针搜索确认
`vtable 0x03AC6F78 +0x90 = 0x02F6EF4C`；
`0x02F6EE60` 构造此类对象；
`0x02F6EF4C` 条件性从 owner+0x178/+0x160 管理的任务池取槽，
通过 `0x02F5E284` 初始化并在 `0x02F6EFDE` 安装
`0x03905D98` 虚表、置 task+0xA0=3。
其 `+0x28→0x02F85960→0x02F83E5C→virtual+0x78` 可进入
`0x02F87684`：`0x02F879C7` 读 member+0xB10，
`0x02F879D7` 读关联 member+0xB10，条件分支下
`0x02F879F3` 还会写回清位。
**仍未证明 B 子任务创建该工厂实例并在历史 V3 执行。**

### 4. 对安全补丁范围的即时影响

1. 不再宣称 `node+0x70` 没有成员读取者；已经证明**通过 B 子任务 +0x78 引用和目标包分发**。
2. 不能直接把 `0x03281520` 的缓存就绪改为忽略旧节点：它是已验证的原生群组到成员目标的必要条件之一，会影响 CA 保留路线与渐进转弯。
3. 不能把 `0x02F83B24` 一概解释为 bug：延迟任务是原生条件路径，tick 和动作状态条件仍需确认。
4. **剩余精确缺口：** 对同一 B packet 实例，`member virtual+0x368` 经 `0x03905E18` 延迟任务何时写入普通成员 **`+0x7F8/+0x818 → +0x1E0`**，旧控制目标何时失效，以及 RMB 新建和 Shift 续接在该交接点的生命周期差异。V3 当次群组模式／虚表实例未知。
5. `patch_authorized=false` 不变；需要安全根因与 ABI 才可做最小 Patch，不修改公共成员 Tick 或 CA 队列弯道。

本地原始 EXE 额外审计已跑 **41 处指令守卫、9 个虚表槽、10 条调用边**并通过；合成／EXE 混合测试 **9/9 PASS**。GitHub 提交的轻量验证脚本覆盖其中大部分相同边；CI 不持有 EXE，不能将 CI 结果升级为真实 EXE 或游戏行为测试。

### 1. 完整的、仍有条件门控的原生成员数据流

```text

       0x02F5F7C8, task vtable 0x03905E18
```

### 2. 真正的两类原生目标交接存在分叉

- `0x03265B24` 在 `0x03265BEB` 读生成记录 `+0x2C`，
  在 `0x03265BF5` 读**当前成员** `member+0x318`；按记录代码
  5/6/7 等有条件生成动作 `0x67/0x68/0x69`，也可能因包标志
  令代码清零；`0x03265C3F` 将最终 `EBX` 放入 `R9D`。
- `0x0326A3A0` 把成员动作参数传给 `0x02F5F8DC`，后者在
  `0x02F5F945` 写 `packet+0x34`。目标包经成员接收器
  `0x02F5F7C8→0x02D99F74` 从 packet 复制到 `task+0x40`，

  `task+0x74` 是否属于 `0x67..0x69`；还看
  `task+0x90 bit0x10`、成员距离和 `task+0x78`，
  满足特定条件才在 `0x02F7A116` 调用成员 `virtual+0x580`。
  其余可在 `0x02F7A17D` 使用 **`virtual+0x568`**。

  **38/38** 的 `+0x580→0x0306A990`；

  `0x03ADD278` 动作，`+0x10→0x0325D9E0`，与第一类
  `0x03913808+0x10→0x0325E294` 不等价。
- `0x0325E294` 到 `0x03071E04` 还需要
  `0x0325EA21` 的 `action+0x6E==1`、

**离线原生分支模型**能生成同一群组中一个成员走 `+0x580`、
另一个走 `+0x568` 的可执行反例。然而这只是机器码许可的
状态组合，不是历史 V3 士兵的实际目标更新帧、速度或挤压因果证明。

`0x03905E18` 延迟状态进入

## 2026-10-11 增量 III：原生 MOVE 回调接通 B 缓存子类，并定位精确 5 单位成员分叉门槛

**这次不是扩大调用图：已在用户提供的精确 SHA 原始 EXE 中完成限定对象、数据标志与分支条件的追溯。**
研究分支新增：
`maintenance_tools/native_shift_re/audit_member_goal_distance_split.py`、
`tests/test_native_shift_re_member_goal_distance_split.py`。

### 1. B 缓存子任务不再只是独立系统：已有原生 MOVE 回调入口

```text
MOVE task callback 0x02F561E8
   [conditional, 0x02F5646F..0x02F56479, current substate==3]
   -> 0x02F4F514 (E8 0x02F56479)
   -> 0x03279EE8 (E8 0x02F4F62C)
     [0x02DC2E04 group-mode check false]
   -> 0x03263EC4 (E8 0x03279F71; subtype vtable 0x03AE00E8)
   -> 0x03271B0C or 0x03281520 [native task phase-dependent]
   -> 0x03265B24
   -> per-member packet
```

该静态条件链既不等于历史 V3 命中，也不说明每次 Shift 都走 B。
但**“B 缓存分发子类与 MOVE 回调无法连接”作为静态缺口现已关闭**。
另一条现有 `0x02F56404→0x03279E40→0x03263AB0` 属于不同的 B 主群组任务入口，不能把其虚表与 `0x03AE00E8` 混为一谈。

### 2. 精确找到 B packet 的局部动作分支状态来源

这条证据采用同一子任务实例，而不是把所有 `+0x70` 字段当作别名：

```text
B cached subtype task+0x70
 (0x03263F26 constructor copies original subtype descriptor's +0x38)
   → 0x0328156B [B subtype +0x70]
   → 0x0328156E [stack route descriptor +0x0C]
   → 0x032815B5 [descriptor address passed to 0x03265B24]
   → 0x03265C61 [r15+0x0C]
   → 0x03265C65 [fifth stack argument to 0x0326A3A0]
   → 0x0326A3EC [fifth argument byte]
   → 0x0326A407 [r9d]
   → 0x02F5F8DC at 0x02F5F94B [packet+0x38 = r9d]
   → 0x02F5F7C8→0x02D99F74 [packet copied to task+0x40]
   → task+0x78 = packet+0x38
```

前一轮只知道 `task+0x78` 会控制动作选择；现在补上了原生参数链，
**它不是无由来的士兵路点编号、不是 B node 的 `+0x78`，也不应改成全兵牌同步索引。**

### 3. 新的精确动作分叉谓词：水平距离 5 单位

`0x02F79FF0` 中，原生代码使用成员坐标 `member+0x88/+0x90` 与目标变换坐标计算水平距离平方。
`0x02F7A07F` 的 `comiss` 对应真实静态浮点常量
**`[RVA 0x03942D74]=25.0f`**；`0x02F7A086` 在距离平方 >=25 时跳过下一步。

满足 `task+0x74∈{0x67,0x68,0x69}` 且 `task+0x90 bit0x10 ==0` 时：

- 如果 **`task+0x78 ==1` 且平方距离 <25**，原生
  `0x02F7A08E` 清为 0，转入 `virtual+0x580→0x0306A990`。
- 如果 **`task+0x78 !=0` 且平方距离 >=25**，转入
  `virtual+0x568→0x0306A8FC`（常见成员；另有一个特殊类）。
- 如果 `task+0x78 ==0`，无论远近仍可走 `+0x580`（在上述其它条件成立时）。
- 特殊动作代码不符合、或 bit0x10 设置，直接走 `+0x568`。

**同一 B 子任务的两个成员合法地出现不同原生动作类**的离线反例：
标志均为 1、动作码均为 `0x68`，成员 A 距目标 4 单位 → `+0x580`；
成员 B 距目标 6 单位 → `+0x568`。精确边界 5 单位为 **>=** 侧。
这是**真实机器码许可的分叉**，仍不是 V3 已记录的运动逆行，也不是一定有错：
CA 可能故意把“目标很近”与“目标很远”交给不同渐进式动作控制器。

### 4. 普通 RMB 对照更具体

普通 RMB 的已确认**条件静态路径**：
`0x030323C8` 在 `0x03032965` 可调用 `0x0302DB44`，
后者重建群组状态并通过 `0x0302DBDB→0x030D5490`
在成员循环中调用 `virtual+0x368` 直接发包。
这说明 RMB 参照不只是 `MOVE+0xA0=null`：
还有**显式群组重建／立即目标包分发**的合法原生路径。

**没有证明** RMB 所有实际移动都采用上述路径；
也不能凭“直接发包”证明所有 RMB 成员已经同一帧提交了 motor。
下一段比较应当精确区分：
RMB 是否经历同一种 `0x67..0x69` packet / `+0x78` 标志门槛，
还是只在 queued MOVE 的特定子状态里出现，
并确定 `+0x568` 是否确实保留与新路段不兼容的旧 motor goal。

### 5. 当前补丁判据

**新增怀疑点：`0x02F7A086..0x02F7A116` 的 5 单位／packet flag 分叉。**
它是具体原生条件，且具有同兵牌成员分流反例；但没有实机成员
旧目标/新目标代际记录，也未证明 `+0x568` 的动作是错误延迟。
**当前不允许把距离门槛改大、强制走 `+0x580`、
全局清 `task+0x78` 或跳过共享路线续接**，否则可能破坏
CA 原生渐进转向、远距离行进、路径完整性和攻击。

验证：本地精确 EXE **29 项指令原字节 + 12 条直接 E8 + 浮点常量 25.0**
均已校对；另有分支的近/远/特殊码/错误版本拒绝离线测试。GitHub CI 是无游戏 EXE 的合成测试。
交付工具只读且报告 `safe_patch_authorized=false`。


### 当日补充：远距离分支 +0x568 不是“只走旧目标”（反证通过）

原始 EXE 补充 7 处精确机器码守卫与 3 条 E8 调用链，
新距离门槛审计增至 **36 个字节守卫、15 条直接调用守卫、常量 25.0f**。
过去“+0x568 不提交新 motor，所以强制统一为 +0x580”的推论**不成立**：

- **近距离动作** `0x03913808+0x10→0x0325E294`：
  `0x0325EA85→0x03071E04` 有条件地提交原生目标。
- **另一动作** `0x03ADD278+0x10→0x0325D9E0`：
  `0x0325DA69→0x03255FF0`，后者 `0x03256161→0x03071E04`
  同样能提交原生目标。
- `0x032490D0` 构造这种动作时，在 `0x032490F9`
  **清空动作 `+0x90` 的一次性提交状态**。`0x03255FF0`
  的 `0x03256007` 先读该标志；若已发出且
  `member+0x710 !=0`，在 `0x0325601A` 提前结束；
  否则在 `0x03256161` 走主目标重建，
  `0x03256166` 再设置已发出标志。
  这是一种合法原生**一次性动作安装/目标交接门槛**。
- 因此下一个精准问题是，queued Shift 是否存在**没重建动作实例**
  却给该实例下发新路段的实际路径，使旧的 `action+0x90`
  和 `member+0x710` 联合拒绝新目标；而 RMB 重建动作/队列
  能清理此标志。仅有机器码可达还不能证明这种实例重用发生。
  如果远距离动作每次都被正确新建并提交目标，就应排除此假说，
  转查几何路径冲突。

**补丁继续 NO-GO**：不得强制两类动作合并、改 5 单位比较、直接清 `member+0x710` 或盲清 `action+0x90`。


## 2026-10-11 增量 IV：RMB 直接更换成员动作 vs B 延迟保持旧动作 — **旧目标失效的精确边界**

本轮在精确原始 EXE 上又补齐了之前距离分流后面的 **两种动作都有主 motor 提交路径** 的负对照，
及更加重要的 **成员接收器本身何时销毁旧动作** 对照。
新 `audit_member_goal_distance_split.py` 累计 **56 原始 x64 opcode 守卫、
22 条原始 E8 调用校验、25.0f 距离平方常量**。本地对所有新增
27 个原始字节现场和 13 条关联 E8 逐项再次检查通过；
公开 CI 依然只是源结构/模拟验证，不持有 EXE。

**同一个原生接收器 `0x0306B9F0` 具有机器码级不同的动作生命周期：**

1. RMB 已核实的 `0x0302DB44→0x030D5490→0x02F5F868`
   形成 `packet+0x50=0x26`（`0x02F5F8BD`），**bit 0x20 已设置**。
   无论群组模式是否许可，常见接收器
   `0x0306BA2F test packet+0x50,0x20`
   跳过延迟任务建立；对于 RMB packet 的 `+0x34=0`，
   `0x0306BBA7→0x0306BBAE` 调用 `0x02DB0A10`
   清理旧 `member+0x328` 动作，
   `0x0306BBD5→0x03248B0C` 安装新 `0x81` 子动作。
2. B 缓存成员包来自 `0x0326A3A0→0x02F5F8DC`：
   `0x02F5F940/0x02F5F95E` 构造的标志没有 bit0x20。

   **`&member+0x490` 的延迟任务持有结构**；

但它可能是 CA 维护渐进转向的正常设计，也未证明旧动作在折返时执行

之后、**其 `member+0x4A8` 延迟任务尚未安装新的 `member+0x330` 动作**
之前，旧 `member+0x1E0` motor goal 是否仍指向
上一段**与当前 CA 渐进路径不兼容**的目标。若这段窗口内
旧 motor 已被正确调整，应排除此假说转查阵型几何。


### 成员 Tick 条件交叉核对：旧动作继续活动不等于同帧并发执行

本轮又核对 `0x03081EB4` 的原始完整函数范围。成员 `+0x108` 状态位 `0x04` 的路径，进一步要求 `member+0x324` 为 `0x10` 或 `0x04`（`0x03082281..0x0308228F`），才能经 `0x030822CB→0x03080F4C` 对**仍安装的 `&member+0x328` 动作**执行 `virtual+0x08/+0x10`。另一条状态路径在 `0x03082343` 读取 `&member+0x4A8` 并调用其 `virtual+0x80`，以决定后续更新。**这两个具体入口分属不同条件臂**，不能仅凭接收器延迟保留旧动作就推断当帧旧动作实际 Tick、也不能把 `virtual+0x80` 误作成员 motor 提交。

新增精确实机判据因此是：延迟任务安装后，在 `member+0x328` 被替换之前，(a) `member+0x108/+0x324` 实际处于何种成员 Tick 分支，(b) 旧动作真正读取的目标与 `member+0x1E0` 是否仍是旧路段，(c) 替换后新目标是否与渐进 Shift 曲线兼容；与 RMB 同状态控制变量配平。如果旧动作根本未 Tick、或当前 motor 已正确对齐渐进路线，则这一“过时目标碰撞”假说必须否决而非盲改。

### 原生主任务对象具体布局与运行时推进

`0x030EE850` 是**大任务对象**初始化器（与 `0x02F2C734`
构造的短期对象不能混为一类），初始：
`task+0x20=0`，`task+0x158=NULL`，
`task+0x120/+0x130/+0x140` 初始几何已建立。
随后 `0x0311FC98` 于 `0x0312058B` 创建子对象并写到
`task+0x158`；`0x0311DE74` 的其他状态分支也可在
`0x0311DF17` 和 `0x0311E4D1` 写入该引用。

`0x0310ED2C` **任务等待/初始化循环**：
`0x0310EDD8/0x0310EDE5` 要求 `task+0x20=4`，
`0x0310EDF8` 要求 `task+0x24=1`，
`0x0310EE12` 在 `task+0x158==NULL` 时
经 `0x0310EE06 -> 0x0311DE74` **继续推进任务直到引用出现**。
`0x03128E80` 中又有同样状态4／+0x24／+0x158
检查与 `0x0311DE74` 调用。**所以 +0x158 不是可以无条件清空的垃圾旧缓存**，
它明显参与 CA 正常状态推进与任务间移交。

在队列槽位的同任务交接中，
`0x03040864` 写 `task+0x20=1` 并将新段 48 字节参数放到
`task+0x120..+0x14F`，**保留 `task+0x158` 旧子任务引用**。
下一次任务状态机 `0x0311DE74` 的 state=1 分支
`0x0311DEC0 -> 0x0311E578`：
- `0x0311E580` 从 `task+0x160` 获得后继子任务 `next`；
- `0x0311E5C2/0x0311E5D3/0x0311E5FA` 把新段
  `+0x120/+0x130/+0x140` 几何搬至任务当前参数；
- 在 `task+0x24==1` 下，
  `0x0311E645` 读取 `old = task+0x158`，
  **`0x0311E64C` 还把 old 写入 `[next+0x20]`**；
- `0x0311E65E..0x0311E6E7` 从
  `old+0x20/+0x24` 读取 X/Z，
  从 `old+0xA8/+0xAC` 读取两个水平向量，
  从 `old+0xB8` 读取长度，
  用 `0x0391CBC8` 中**常量 0.5f**计算并写入
  `next+0x48/+0x4C/+0x50/+0x54`：

```text
half_extent = 0.5 * old[+0xB8]
next[+0x48,+0x4C] = oldPosXZ - half_extent * oldDirXZ
next[+0x50,+0x54] = oldPosXZ + half_extent * oldDirXZ
```

最后 `0x0311E6EC` 清理 `task+0x158=NULL`，
**但 old 子任务指针已经存到了 `next+0x20`**。
所以这不是完全的“旧任务状态删除”；这是明确的连续性移交，
主字段随后释放自身引用并不代表旧对象已不再可从后继子任务访问。

### 对补丁方向的含义／重要负证据

这一块很可能就是 CA 保留进场方向、连续移动平滑转弯的底层机制，
不能粗暴将旧子任务清空或把 `+0x158` 置 NULL：既可能破坏
`0x0310ED2C` 的任务推进循环，也可能让后继 subtask
失去原生长度/朝向插值，退化成停步后突转。

目前真实日志只观测到模型目标同步反转和局部距离靠近，
没有记录这个 `task+0x158` 子对象的原生位置/方向/长度，
更无法给样本标出确切 RMB/Shift order ID。
因此尚不能证明公式本身有错；可能的缺陷是**排队折返时 oldDir
与 next geometry 配合造成某些成员前瞻段相向/交叉**，
但本题必须基于每模型目标与实际轨迹作 RMB-vs-Shift 实例对照才可定案。

下一步优先静态对比`DL=0` replace 新建动作时 vs `DL!=0`
append 转移时，这段投影是否经过相同几何检查；
定位成员 `NATIVE_MEMBER_SEND` 和 `next subtask`
之间的具体子任务/群组指针引用，不能以虚表偏移猜类型。
当前**仅定位到精确可能补丁层，不授权写补丁**；无需重复以前的
挤压症状实机证明。
