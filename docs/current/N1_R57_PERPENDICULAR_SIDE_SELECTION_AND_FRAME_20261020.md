# BSC R57 / 本对话第23轮 — 原生 ±90° 侧向朝向选择与坐标框架连续性

**日期：2026-10-20。只读静态研究。** 目标是改善 CA 原生 Shift 连续 MOVE 折返的队形流畅度，保留原生 MOVE 队列、渐进转向、寻路避障、RMB MOVE、Shift ATTACK。不允许把发现的一般几何函数当成已证实的 Shift 缺陷或直接全局打补丁。

## 一、确切版本和复核范围

用户上传新版 Windows x64 `Warhammer3.exe`，SHA256 `9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`。所有地址是 RVA。依赖 R53 已有的 PE ImageBase、exception unwind、GNU objdump 真正指令起点检查。完整 EXE 只读核验 **64/64 个机器码指令、7/7 E8、6/6 直接 JCC/JMP**；经可执行节 E8 全扫描与真实指令起点过滤，`0x0310E450` 只有 **2** 个直接调用者 `0x03102CD8`、`0x031232BF`。23/23 Python 单元测试（含真实 EXE）；不带 EXE 22 PASS / 1 SKIP。没有游戏进程附加、没有 Hook、没有 DLL 调用、没有采集到真实 Shift 折返。

## 二、最重要的新增原生函数：0x0310E450

`0x03102B28` 路线转换器在 `0x03102CD8` 调用 `0x0310E450`，另一条路径 `0x031232BF` 也调用它。该 helper 的输入使用 Win64 栈参数：

- 从 caller `[rsp+0x28]` 传来的引用保存于 callee `[rsp+0x98]`，供 `0x0310E47B MOV RCX,[RBX+0x10]` 读取。
- 从 caller `[rsp+0x48]` 传来的原始 16-bit heading 对应 callee `[rsp+0xB8]`；在 `0x0310E4D6` 的 `SUB CX,[rsp+0xB8]` 中进入有符号方向判别。
- 若引用为空或经 `virtual+0x40` 的返回对象缺少状态位 `(flags+0x124)&0x02`，或 `virtual+0x80` 不返回 AL=1，则直接使用传入 heading（`0x0310E4FC`）。
- 通过上述门槛后，`virtual+0x80` 在栈中写入一个参考朝向，
  `0x0310E4D6` 计算 `signed16(ref-heading)`。`0x0310E4E8/ED` 给 ref **加 0x4000（90°）**；`0x0310E4F2/F7` 给 ref **减 0x4000（90°）**。
- 分支方向：`signed16(ref-heading)>0` 或 `ref-heading==0x8000` 用 **ref−0x4000**；其它情况包括差值为0用 **ref+0x4000**。

原生计算选择的是**相对关联对象参考方向的垂直侧向方向**，不是已证明的“将士兵逐帧旋转 90°”。代码中 `0x0310E54C` 将结果传入 `0x030FA978`；后者的 `0x030FA9DE` 写入**新建临时路线记录的 `+0x44`**。旧描述符原始朝向保存在自己的 `+0x38`（由 `0x030F1B86` 写入）；两者不能混淆。

### 值得检查的二值侧向选择边界

在上述门槛**保持有效**且输入 heading 固定的合成模型中，当参考角由 `heading−1` 变成 `heading+1` 这个只有2个16位编码单位的变化时，输出选择的垂直侧发生切换：两次输出相隔 `0x7FFE`，约 **179.989°**。这只是分支函数的**角度输出差**，不等于实际成员路线或士兵朝向瞬变。对应反例和门槛为假时保持输入的反例已放入 `test_r57.py`。

该候选的物理解释**可能**是参考对象的方向跨越选侧分界造成路线侧向选择翻转，但游戏可能通过对象策略、模式门槛或后续路段过渡保证它不会发生；尚未证明 Shift 会命中这个边界。严禁把 `0x4000` 直接替换成其它角度或全局禁用该分支。

## 三、纠正 R56：投影中心 C 不是永远固定的世界坐标

路线描述符构造器 `0x030F1B3C` 将传入空间记录的 `source+0x18` 引用复制到 `descriptor+0x30` (`0x030F1B71/75`)；位置保存在 `descriptor+0x18`。转换器 `0x03102B94 CALL 0x0312214C` 使用 `&descriptor+0x18`，后者从记录 `+0x18` 获取坐标参考对象，不为空时调用 `0x02F3D668` 将 xyz 转成**当前世界坐标**，为空时直接复制本地 xyz。

因此 R56 给出的静态几何投影在两路段交接时必须写成：

`P_before = C_before - 0.5 D_before V(heading_before)`

`P_after  = C_after  - 0.5 D_after  V(heading_after)`

`P_after - P_before = (C_after-C_before) - 0.5 (D_after V_after-D_before V_before)`

其中 `D=A-B` 是阵型几何跨度差，`C` 可能来自**不同的参考框架及不同的采样时刻**。如果只算方向和跨度变化而没有 C，就只能报告 `UNKNOWN_CENTER_FRAME`，不能报告“真实路线已跳变”。

纯合成数值：`D=16`、方向从0到90°、空间参考 `C` 不动，单独模型的投影变化长度约11.314；若 `C` 与投影补偿反向同步变动，最终投影位置**可以保持不变**。这是数学反例，不代表游戏实际执行了补偿。

## 四、为什么这比继续查宏观键位更有研究价值

我们现在有两个**可被独立证伪**的流畅性候选：

1. **Route frame / extent continuity**：换段时 `C`、`D`、方向联合导致投影不连续。必须给出同一实际后继 MOVE 的有效对照数值；只看方向变化无效。
2. **Binary perpendicular side-selection**：相同类型关联对象、相同语义参考，在输入与参考角差值穿过零或对径边界时选侧翻转。必须确认真实 Shift 使用 `0x0310E450` 该门槛及其临时记录 `+0x44` 确实影响成员目标，且下游没有平滑。

目前两个候选都**不是已证明的 gameplay 根因**。`0x0310E450` 的第二个直接调用者 `0x031232BF` 也说明它并非专用于键盘 Shift。它更像通用的相对几何构造辅助函数，需优先定型 `[descriptor+0x28]` 的关联对象和其 `virtual+0x40/+0x80` 具体实现。

## 五、下轮的单一止损目标

**确定侧向 ±90° 生成的临时路线记录 `+0x44` 究竟如何进入成员目标生成，还是仅用于合法横向阵型几何。** 优先从 `0x030FA978` 输出对象开始顺着路线缓存/求解器识别真实消费者，并定型触发分支的关联对象。限定静态调用深度及相关类型；如果只能证明通用阵型垂直朝向而没有 Shift 同实例和成员目标数据边，就降低本线索优先级，转向弧线曲率/逐成员运动协调。
