# BSC 本对话第 26 轮／R60：延迟 packet 与立即 action 的原生交接审计

研究日期：2026-10-20。目标：改善 CA 原生 Shift 连续 MOVE 折返时的成员转向流畅度及队形协调。不重做“Shift 缺陷存在”的证明，不使用 Lua 替代原生队列，不向游戏部署任何 Patch。

## 1. 输入、审计边界和本轮新发现

用户提供的新 `Warhammer3.exe`，Windows x64，文件 232,531,920 B，固定 SHA256：

`9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`

所有地址均为 **RVA**，实际地址 = 模块当前加载基址 + RVA。代码读取只来自本地原始 EXE，不读写游戏进程。脚本逐条确认原字节、PE unwind 所属函数及 GNU objdump 指令起点，并核对直接 E8/JCC 和真实类型化虚表。

**R60 实际证明的区别：** 普通成员接收函数 `0x03070A48` 存在一个明确的延迟任务槽 `member+0x4A8`，与立即 packet 安装的 `member+0x328/+0x330` action 槽位不同。延迟路径先清退旧延迟任务后保存一份 packet；立即路径在自身直接代码内没有调用同一延迟清理器，但它会清退旧 action。延迟任务后续存在用保存的 packet 重新驱动成员动作方法的条件代码。**不能据此认定 Shift 实际发生“旧 packet 在新 packet 后重新执行”，因为下游间接调用或更早任务清退尚未排除。**

## 2. 接收器分流与对象归属

新版成员虚表 `0x03912950 +0x368 → 0x03070A48`（普通成员）。R38 已限定 B2 构造的 `packet+0x50 bit0x20` 清零；这不等于所有 native sender 均满足相同门槛。

`0x03070A83/85` 检查原生模式 helper，`0x03070A87/8B` 检查 packet+0x50 bit0x20。仅在 `helper=0 && bit0x20=0` 的路径进入延迟任务创建：

```text
03070A8D  LEA RCX,[member+0x490]
03070A94  CALL 02DB5AC4          ; 旧延迟任务的条件清退
03070A99  LEA RCX,[member+0x4A8]
03070AAC  LEA RDX,[member+0x490]
03070AB3  CALL 02F647D0          ; 创建具体延迟任务
03070AB8  JMP 03070C32           ; 本次不走立即 action 安装分支
```

另一分支在本接收器自身完成 member+0x104 决定的位置/动作方法调用：

- `0x03070B66`: virtual+0x100；`0x03070B9C`: virtual+0xE8；
- `0x03070BD2`、`0x03070C06`: **清的是 `member+0x328` 的 action (`0x02DB5A20`)**，之后分别在 `0x03070BF8`、`0x03070C2D` 构造两种 `member+0x330` action；
- **直接 E8 全函数清查：此接收器只在 `0x03070A94` 直接 CALL 延迟任务清理器 `0x02DB5AC4`。** 这不证明即时路径的下游函数不通过其它方式取消延迟任务。

`0x02DB5AC4` 收到的是 **`member+0x490` 父任务管理区**，在 `+0x130` 标志为1时析构内嵌子对象 `+0x18`，随后清理标志。这与针对 `member+0x328` 的 action 清理函数 `0x02DB5A20` 不是同一个对象槽位。

## 3. 延迟对象确实缓存 packet，而不是每次重新取最新 packet

`0x02F647D0` 的来源与本次接收器三参数相对应：`RCX=&member+0x4A8`、`RDX=&member+0x490`、`R8=packet`。它通过 `0x03250F9C` 初始化父子任务关系（在 `0x03250FEB` 置父对象 `+0x130=1`，即 `member+0x5C0`），再将 **实际虚表 `0x0390BEA8`** 安装到子任务。

`0x02F647EF/F6 → 0x02D9E078` 将 packet 多数字段复制到 `task+0x40`，并对 flags+0x50 使用逐位操作；不是保留一个“以后都读取最新 packet”的指针。`0x02F64812` 清 task+0x9C/+0x9D 的初始状态。`0x02F6484B/52` 根据当前 Group 计数和 packet+0x4C 的 DWORD 设置 task+0xA0，作为后续时相门槛。

任务具体虚表（由新 EXE `.rdata` 直接读取）：

| 延迟 task 虚表槽 | 真实代码 | 已验证作用 |
|---|---|---|
| `+0x08` | `0x02F7885C` | 清 `task+0x9C` 初始状态并进入受时间条件限制的处理器 |
| `+0x10` | `0x02F88BB0` | 按 task 状态、成员当前 action 和组状态执行条件性推进 |
| `+0x80` | `0x008F5810` | 返回 `((task+0x90 >> 4) & 1)`，即来自缓存 packet 的状态位 |

新版普通成员 Tick `0x03086F04` 在 `0x0308738A/93/9D` 与 `0x03087622/2B/35` 两处先检查 `member+0x5C0`，随后向 `member+0x4A8` 的**这个具体子任务**调用 virtual+0x80。这只能证明 Tick 实际**查询**延迟任务状态，不能将查询视为已经执行其 virtual+0x10。

## 4. 延迟对象的后续实际 packet/动作处理通道

`0x02F70178` 有严格的时间门槛 `0x02F7018C/92/98`: 在 Group 当前计数低于 `task+0xA0` 时返回；满足其它门槛后，可以通过 `0x02F7F07C` 或 `0x02F7F604` 等路径继续处理**任务保存的 `task+0x40` packet 数据**。

- `0x02F7F0BC/C0` 解析延迟对象持有的当前目标记录；`0x02F7F209` 经成员 virtual+0x568 条件安装动作；
- `0x02F7F604` 使用任务保存的输入准备一份新的动作 packet，然后在 `0x02F7F765` 经成员 virtual+0x5B0 交给当前成员处理；
- `0x02F88CA4` 有另一条经 virtual+0x578 的条件动作通道。成员普通与特殊两类真实虚表共享这些方法槽位：`+0x568→0x0306F954`、`+0x578→0x0306F990`、`+0x580→0x0306F9E8`、`+0x5B0→0x0306FD58`，它们与最初的 packet 接收器 `+0x368` **不是同一个方法**。

这些方法可以清理／重建 `member+0x328` action，但是否具有“旧任务已无效”的其它验证，还需进一步定型具体状态及调用先后。**没有断言上述三个条件通道都会执行。**

## 5. 可以否证的候选与目前的负证据

**待否证假说 H60：** 同一成员已有延迟包 D1，新的即时包 I2 被接收；若 D1 的父任务有效标志依然存在，且 D1 随后的全部时间/状态门槛成立，则可能把创建时缓存的输入重新提交给成员，造成新旧运动意图相位相反或折返不够流畅。

**支持研究该假说的静态事实：** 接收器两分支不同的直接清退对象；延迟对象保存输入及时间门槛；成员 Tick 有延迟任务状态查询；延迟任务后续存在成员动作分发方法。

**尚未排除的解除条件：** 即时分支调用的 `virtual+0x100/+0xE8` 及其下游的清退/状态方法；Group 任务完成状态；另一个线程的清退；旧任务在 I2 之前已经消费或销毁；B2 sender 的原生 mode 与 Shift 后继 MOVE 实际关联尚不成立。

已核对的两个 immediate 成员方法 `0x030785AC`、`0x03078268` 本体没有直接 E8 到 `0x02DB5AC4`。**这是局部直接调用负证据，不是完整转调闭包、不是实际运行的残留证明。**

离线 `local_receiver_only()` 的 `['deferred','immediate']` 例子**仅模拟此接收器自身直接写入**，保留尚有任务并不代表 CA 整体状态如此；允许显式 `external_cancel` 模型说明不能把未观测的下游排除。

## 6. 对平滑转弯的真正作用与止损标准

这个候选如果真实发生，会导致同一成员对新旧路段的动作意图交错，比单纯的“瞬时角度跳变”更接近局部运动冲突。但是没有本游戏实际同实例证据，**不允许清零 `member+0x5C0`、NOP 延迟任务或禁用原生 B2**，这些字段由多类成员动作共享。

**下一轮唯一高价值目标**：从 immediate 成员方法和当前 action 的具体 virtual 更新中追 `member+0x490` 父任务是否经间接清退，或找到更上游的“新命令导致延迟任务无效”的标志；若存在强制清退不变量，就**明确排除 H60** 并回到原生路线预瞄／转角几何。若没有这种约束，再考虑极少数据量的同实例只读观测，记录旧任务创建序号、新包接收序号和任务最终消费情况，而不是再次让用户证明挤压。
