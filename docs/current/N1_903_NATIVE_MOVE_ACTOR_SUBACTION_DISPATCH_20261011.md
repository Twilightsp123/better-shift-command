# Better Shift Command — WH3 9.0.3 原生 MOVE → 成员动作类型闭环逆向

2026-10-11 · 用户原始 `Warhammer3.exe` · SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a` · PE ImageBase 0x140000000。全部地址为 RVA。**这是原生条件路径的静态证明，不是 V3 动态命中证明，也不是游戏修复。**

## 逆向解决了什么

这次聚焦一条此前已有条件调用关系但未打通的链：真实 V3 命中的 `0x03025D70` MOVE 工作函数，其任务 `0x02F561E8` 在特定共享状态条件下可调用 `0x03279E40 → 0x030D554C → 0x030D5490`。旧 V3 对 `0x030D5490` Hook 报告零命中，所以**不能断言 V3 当时实际通过此分支**。

在此 *条件成立时* 的具体目标包处理，可以从原始机器码和虚表证明：

1. `0x030D5490` 为每个成员生成 `0x02F5F868` 原生目标包。`packet+0x50=0x26`，`packet+0x34=0`。`packet+0x51` 的最低两位在辅助函数运行后保证为 `0x03`（其余位不能据此确定）。下发前在 `0x030D54EB` 传第 5 个栈参数 `1`。
2. `0x02F5F868` 因而在 `0x02F5F8CD` 调用 `0x02F72520`。后者设置 `packet+0x51` 的 `0x02` 位，并在 `packet+0x50 & 2` 成立时用当前成员对象及 `0x0307F478` 更新包内朝向。**先前假定这个位未设置是错误的。**
3. `0x0306B9F0` 对 `0x26` 先跳过构建“延迟成员任务”的分支。因 `packet+0x51 & 2 !=0`，它在 `0x0306BA75` 调用 `0x0307F5C8`。这一路内部使用 `0x0307F690`、`0x0307F4E4`、`0x0311D0CC` 与 `0x03107FD8` 等变换函数，输出**结合成员现有状态转换后的目标位置/朝向**。因此不能把组生成的 48 字节记录直接当作最终成员局部运动目标。
4. 在已采集过的 `member+0x104=0` 情况下，常见接收器选择成员 `virtual+0xE8`。36 张公共成员类型中 28 张直接去 `0x03073224`，另 3、4、1 张通过不同包装实现进入相同函数，处理新目标、动作状态与 `+0x910/+0x930` 空间缓存。
5. **接收之后，原生还会替换成员动作子对象**：因为目标包 `+0x34=0`，`0x0306B9F0` 在 `0x0306BBAE` 调用 `0x02DB0A10`。它检查旧动作 `member+0x328+0x154` 的持有标志，必要时虚析构旧动作并清标志。随后 `0x0306BBD5` 调用 `0x03248B0C`，构造 `member+0x330` 中虚表为 `0x03914618` 的新动作对象，传入原生状态 `0x81`。它**不是**之前研究的动作 A 虚表 `0x03ACD208`，也不是动作 B 虚表 `0x03ACD468`。

## 跟正常 RMB 的关系：可证明与不可证明

- 普通 RMB 的 REPLACE 与 Shift 后继 MOVE 都进入 CA 的原生 MOVE 系统，差异首先发生于高层路线状态来源/共享任务续接。
- 在这一**共用的** `0x26` 目标包分发实现里，接收器按包标志和成员 mode/动作类型分流，没有证实一个“Shift 独有、等待每位士兵旧动作任务完成才接受新目标”的条件。
- **这条路径直接反驳**“所有成员都必须等自己的旧动作完成才接收新目标”的简单假设。收到新目标后，至少 `+0x328` 子动作可以被清理/替换；但 `member+0x7F8/+0x818` 的主运动轨迹、独立进度或其物理生命周期不等于 `+0x328` 子动作，不能据此宣称所有士兵立即改向。
- 仍有**各成员独立变换目标和刷新空间缓存**的机制，依当前成员状态产生不同局部结果是正常代码能力。没有证明它是本次 V3 的压缩根因。
- V3 旧的零命中数据没覆盖此分支，只有当时记录的采样成员模式 0；也没有它们具体属于哪张虚表的现场记录。不能用静态调用关系虚构 V3 内部事件。

## 工程决策

1. **不用**原来“动作 A `0x03088618` 兼容时跳过更新”作为 SHIFT-MOVE 通用补丁依据。该动作有接触/交互来源，且与目标包创建的新子动作类型不同。
2. **不用**强制全体完成成员任务、清 `+0x930`、全局 Hook `+0xE8` 或禁用原生状态续接。
3. 真正剩下的窄因果层是：**高层路线续接前后，`0x26` 成员包的48字节输入、actor-specific目标变换、以及 `+0x7F8/+0x818` 主运动目标更新的实际生效时机**。已有原生代码证明新包可覆盖动作子对象，不再优先把“等待旧子动作结束”当作原因。
4. 只有在上述局部主运动数据流上发现正确的原生协调条件，才设计可回滚实验补丁。历史 V3 原始数据未记录内部目标包与动作类型，因而不能仅靠这份 EXE 回推当年的实际分支是否执行。
