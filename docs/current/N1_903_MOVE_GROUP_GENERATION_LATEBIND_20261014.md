# BSC N1 — 原生 MOVE 短期任务的当前 Group 读取与对象池重用风险（2026-10-14）

## 本轮结果 / 证据等级

在用户上传的原始 `Warhammer3.exe` 上实际校验 SHA256
`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，
ImageBase `0x140000000`。严格 PE 节、unwind（及已限定的无 unwind 叶函数）、
GNU objdump 指令起点、RIP/虚表和原始 E8 校验：**91/91 处指令、19/19 E8、3/3

结果等级为 `EXACT_ORIGINAL_EXE_STATIC + SYNTHETIC_ORDERING_COUNTEREXAMPLE`，
不是 WH3 真实 Shift 折返回调顺序取证，也不是 Native 挤压修复。

## 1. group 确实来自可回收对象池，而非不可复用的单调对象 ID

已有路线入口 `0x0302DB44 → 0x0301B8E4`：

- `0x0301B8F3` 取得 `root+0x3280` 容器；`0x0301B902` 调用 `0x030197A8` 清退容器中的旧 group。
- `0x030197C7..0x030197E0` 对每个旧 group 指针取得
  `[container+0x8] → +0x440 → +0x150 → +0x58` **同一对象池槽**，调用 `0x0302C2D4`。
- `0x0302C2D4` 先通过旧 group 的实际虚表 `+0x10` 调析构，再把**同一地址**写入对象池链表头。
  真实 group 虚表 `0x0390F5F0+0x10 = 0x030C61D4`；`0x0302C2E7` 设置 `EDX=0`，
  而析构函数仅在参数 bit 0 为 1 时才调用 `0x04EA934` 释放 group 存储。因此这条回收路径
  **不释放 group 对象本身的堆内存**，而是允许该地址被对象池复用（析构仍处理内部资源）。
- `0x0301B834` 随后读取同一来源的 `+0x150 → +0x58` 空闲链表，取出 `rbx`，
  `0x0301B8B0` 修改 free-list head，`0x0301B8B7` 将该对象交给
  `0x030C2C3C` 重新构造（安装真实 group 虚表 `0x0390F5F0`）。
- `0x0301B96D` 最后写 `root+0x32F8 = rebuiltGroup`。

**关键含义：** `group_ptr` 即使在相邻两个 MOVE 后数值完全相同，也可能已经历
析构/复用/新建；`ptr` 不是任务代际 ID。反过来，相同地址是否在某次特定游戏行动中
真的重用，需要实例取证，不能由静态对象池能力断定。

## 2. 短期 MOVE 任务以 UnitRoot 为锚，分发时动态读取当前 group

- 独立任务构造器 `0x02F2C734` 的 `0x02F2C74D` 将传入 UnitRoot 保存为
  `shortTask+0x08`；这个短期任务的虚表 `0x03ABBE18 +0x10` 指向
  更新函数 `0x02F561E8`。**这不是 queued slot+0xA0 的大任务实例**。
- 更新函数首先检查关联任务的 `+0x20==4 / +0x24!=0`，再检查
  `shortTask+0x74`。通过后，`0x02F56358` 用 shortTask 的局部输入构造待分发描述，
  `0x02F56371/77/89/94` 将子对象坐标和参数搬入临时栈记录。
- **关键现场**：`0x02F563F4` 才读取 `shortTask+0x08` 的 UnitRoot，
  `0x02F563FD` 再读取**当时** `root+0x32F8`，在 `0x02F56404`
  把这个 group 和任务准备的栈参数一起传入 `0x03279E40`。
- 后继的 `0x03279E40 → 0x030D554C → 0x030D5490` 仍受原生 group/context
  模式与成员分发条件影响；`0x030D5490` 按 `member[i] ↔ record[i]` 分发。

`0x02F561E8` **在这条分发边上采用 live root group**，而不是从它自己的固定字段
直接读出创建时的 group。没有证明短任务其它字段不可能持有群组相关引用；这里仅
描述真正调用 `0x03279E40` 时取 RCX 的来源。

## 3. 已经检查的清退与代际约束

`0x02F56404` 在本条路径中先调用群组处理，之后转向 `0x02F564B7`，
接下来的 `shortTask+0xA0/+0xA1` 状态门槛下才可能进入包含
`0x02F5652D/0x02F5657B` 的 **当前 group 指针比较及清理**。
因此不能拿这些**后续、受条件保护**的清理比较，冒充已经在 `0x02F56404`
之前校验过 group 代际。同样不能说其它调度器状态绝无防护：还没有
证实旧 shortTask 能在下一次 group 重建之后继续进入这条分支。

## 4. 精确的假设与对照条件

离线模型只是独立模拟**可能的调度顺序**，没有假装模拟 CA 的 Tick：

| 假设顺序 | 指针是否改变 | 代际是否不同 | 能否出现跨代输入（离线） |
|---|---|---|---|
| T0 创建、T0 回调、没有新 MOVE | 否 | 否 | 否 |
| T0 创建、G1 更新、T0 回调 | 是 | 是 | 是 |
| T0 创建、G0 回池、同一地址重建 G1、T0 回调 | **否** | **是** | 是（ABA 反例） |
| T0 创建、G1 更新、T0 已被清退 | 不重要 | 是 | 否 |

这里的 `epoch` 是离线测试模型的**合成标签**，不是发现了真实 WH3 的 epoch 字段。
要把它升级为 Shift 因果证据，首先必须证明实际连续 MOVE 在时间上满足
`group rebuild before old shortTask dispatch`，而不是仅根据地址相等推断。

## 5. 最小 Native 修复的边界与下一步

如果静态/单次确定性证据最终确认跨代分发，应在 `0x02F563F4..0x02F56404`
附近研究任务归属与 group 代际一致性；但不能简单清空 `root+0x32F8`，
禁止直接跳过 group fanout，也不能把 shortTask 或 group 指针随意固定：
对象池析构与引用计数、任务完成状态、普通 RMB、Shift ATTACK、原生
渐进转向/避障都要保护。尤其只比 group 指针地址的补丁无法识别 ABA。

尚未确认任何游戏中有旧任务在新 group 重建后继续执行，也没有确认这就是相邻
成员 motor goal 穿插的原因。**native_patch_authorized=false**。

本轮新增 `audit_move_group_generation_latebind.py`、同名回归测试和静态证据 JSON，
不上传 EXE 和用户原始指针 JSONL；不修改 `main`；无需用户重复已确认的折返。
