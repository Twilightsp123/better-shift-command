# BSC N1 第24轮：原生邻近对象响应的调用对象身份与速度写入边界（2026-10-16）

## 这轮实际验证了什么

输入：用户原始 Win64 `Warhammer3.exe`，SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，ImageBase `0x140000000`。全部地址为 RVA。真实原始 EXE 的只读本地审计：**31/31 原码字节及 objdump 真正指令起点、5/5 函数所属真实 E8 直接调用点，9/9 本地单元回归 PASS**（包含实际原始 EXE、错误版本 SHA fail-closed、Python -O、不可覆盖原始 EXE）。公开 CI 没原始 EXE 时应跳过其专属用例。

之前第23轮追至 `0x03054B84 → 0x030557BC → 0x030800C4 → virtual+0x10`。本轮没有对虚方法身份做无证据猜测，而是把五个调用者的数据所有者核实清楚。

## 1. 五个真实直接调用者，不是 Shift 独用

对整个原始可执行节查找 E8 rel32，逐个以 PE unwind 所属函数和 objdump 真正指令起点过滤，`0x030800C4` 恰有五处直接调用：

- `0x030557BC`，成员邻近运动条件链内；
- `0x0307B219`、`0x0307B3DD`，同一另一大型处理函数的两处分支；
- `0x0324F503`；
- `0x03260D11`。

全部调用者在执行前都经过等价的两步字段表达式：首先读取 `[source+0x440]`，然后读取 `[上述结果+0xF0]`，把结果作为 `RDX` 传给 `0x030800C4`。本轮已独立核对五处两条实际 MOV 的字节、函数内部寄存器保留及 E8 目标，**但不能证明五次调用在不同运行实例中取到相同指针**。

其中成员运动调用者的 source 更可细化：`0x03054C86 LEA R13,[member+0x58]`，`0x03055771 MOV RAX,[R13]`，之后 `0x03055788 MOV RDX,[RAX+0x440]`、`0x030557B0 MOV RDX,[RDX+0xF0]`。**不能把该 member+0x58 根指针来源强加给另外四处调用者**；它们各自有自己的 source。

## 2. 函数内确实是组装响应记录、然后虚方法分发

`0x030800C4` 保留 `RDX` 为 `R13`。函数读取双方 `+0x74` 优先级、当前对象状态以及记录标志，组合 0x01、0x02、0x04、0x08、0x10 等控制位，把成员身份、位置/速度相关输入及标量装配到本函数的栈内记录。

最后在 `0x0308024D` 执行 `LEA RCX,[R13+0x1D8]`，`0x03080254` 取 `[RCX]` 虚表指针，`0x03080257 CALL QWORD PTR [RAX+0x10]`。

独立检查这一整个原生函数体：**在它自己的直接写入中，没有发现针对当前对象/选中邻近对象的 `+0xE0/+0xE8` 速度或 `+0x1E0/+0x1F0` 目标写入。** 它可能通过其他普通调用或末尾虚调用**间接**造成状态变化，因此绝不将此结果夸大为“整个邻近响应系统不改变运动速度”。

## 3. 真正的阻碍与下一步决定点

虽然五处调用者的双重上下文引用已闭合，**`receiver+0x1D8` 处实际安装的虚表及其 `+0x10` 具体函数没有找到严格的构造器身份闭环**。该偏移还出现在其它不同类型的对象上，不得只根据偏移把无关虚表拼接。

本轮研究结论是：`0x030800C4` 本体**不是已证实的直接 steering/速度写入器**，更像是构造并转交邻近对象响应记录的公共分发路径。对该虚调用是否发生间接 steering 修正，仍列为 UNKNOWN。

下一阶段要设定止损标准：限定追查该上下文 `+0xF0` 返回对象的构造器与 `+0x1D8` 子对象虚表安装；如果无法类型化目标，就不要继续追周边数百 RVA，立即去找**真实写入 member+0xE0/+0xE8 或运动输出**的具体函数，再判断已确认 Shift 连续 MOVE 折返中的两名相邻士兵第一次分叉究竟在 world goal 还是本地 steering。未经两成员同实例证据，不授权游戏补丁，也不要求用户重新证明症状。
