# Better Shift Command N1 — RMB / Shift 原生 MOVE 的完整已证状态机与成员运动阶段图

> 2026-10-11。只读分析对象是用户提供的原始 WH3 Windows x64 EXE（用户标记 9.0.3）。SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，ImageBase `0x140000000`，全文地址均为 **RVA**。本文记录代码能证明的条件路径，不把静态可达性冒充 V3 发生过的事件，也没有安装任何 Native Hook。

## 一句话模型

**SHIFT 与 RMB 最大的已证区别在最上层的 MOVE 队列／共享路线状态，而不是两套独立士兵避障算法。** Shift 满足队列续接条件后可以交接共享路线状态，而这一条件没有遍历全部士兵的局部任务；下层群组路线随后根据所有者的 *群组模式*，进入两种不同的任务／路线处理；成员目标包的接收、子动作替换与成员之后自己的每帧模式变更也并非同一时刻的同一状态机。因此原生命令结构存在**兵牌级已推进／成员仍按自身条件运动**的时序空间，但不能据此断言 V3 中哪一项条件实际制造了拥挤。

## A. 输入：普通 RMB 与 Shift 的第一个真正分歧

- 普通 RMB 替换命令：新 MOVE 构造器 `0x030090BC` 在 `0x030090E7` 写入 `MOVE+0xA0 = null`；新任务需要从新路线状态初始化。
- Shift 排队：在特殊原生 MOVE→MOVE 情况下，`0x0304433C` 的续接检查和 `0x0304459D` 附近的引用计数／vfunc +0x48 状态移交可能把旧的共享状态交给后继 MOVE；`0x030445B1` 后按原生队列推进。这个特殊区段不逐个检查士兵局部任务完成标记。
- 继承是**条件性**的：`0x03025D70` 内会验证旧状态是否与新 MOVE 兼容，不满足会清掉继承指针。继承不等于把旧目标位置永久沿用，也不等于 Shift 必然挤压。
- 原生 MOVE 工作函数 `0x03025D70` 配置路线参数（`0x03025E91→0x0301287C`），创建 MOVE 任务（`0x030260AF→0x02F2C734`，任务 `vtable 0x03ABBE18`，虚表+0x10 `0x02F561E8`）。V3 实际记录到 `0x03025D70` 的短时密集入口，这是少数确定的运行事实。

**不能宣称：** RMB 一次点击后 60 名士兵物理模拟会在同一帧同时转向；目前只有新高层命令／路线状态的机器码事实。

## B. 原生 MOVE 任务回调本身是跨更新的状态机

`0x02F561E8` 不是单次「发完包立即结束」。它的状态来自 task+0xA0/A1/A2/A4、`0x02F4EFE0` 获取的附属任务描述与 `task+0x90` 指向的下级轨迹任务。

- `0x02F562E3` 检查下级任务类型 `+0x20 = 4`，`0x02F562F2` 检查就绪位 `+0x24`，满足时在 `0x02F56358/0x02F56431` 创建相应的任务对象，在 `0x02F56460` 调整其参数，然后 `0x02F56404` 调用 `0x03279E40`。
- 后续回调处理还检查 `task+0x90` 关联对象、关联任务 `+0x60` 和 `+0x58` 是否满足后续条件（`0x02F564C4–0x02F56505`）；通过时会调用 `0x02F36B1C` 并设置 `task+0xA1`，最终 `0x02F565C2→0x02F32ED0` 更新 `task+0x18` 结束态。
- `task+0x90` 是这层 MOVE 回调的一个下级关联对象；不要混同下述 **B 分支**另行生成的 `0x03AE0128` 虚表的群组动作对象。

代码上这就是“命令阶段/下级任务结果”而非“逐名士兵走完后才弹路点”的实现。是否有其他外部栅栏不属于这些机器码的排除范围。

## C. `0x03279E40` 是真正的两种群组路线分支

先调用 `0x02DC2E04` 检查群组上下文中的所有者模式 `owner+0x28`。该函数用 `0x29` 位图，只接受模式 **0、3、5**。这里的 owner 模式**不等于** V3 采集到的 `member+0x104` 模式；两者不能混用。

```text
原生 MOVE task callback 0x02F561E8
            |
            v
        0x03279E40
            |
        group owner mode
            |
   +--------+--------+
   |                 |
  0/3/5              其余
   |                 |
  0x030D554C        0x03263AB0
   |                 | group vtable 0x03AE0128
  0x030D5490          v+0x10 0x03281408
   |                 |       |
   |                 |     0x03281444
   |                 |       |
   |                 |     0x03121ABC 或 0x031219B0
   |                 |       |
   |                 |     0x030ECB10 → 0x030FE1E4
   |                 |                  |
   |                 |        0x030C1FDC / 0x030C7858
   |                 |        保存生成路线 → submotor+0x70
   |                 |
   +-- (A 为群组目标包；B 为原生群组路线子控制器)
```

### C1. A：群组目标包分发

`0x030D5490` 读取编队策略 vfunc+0x48 的 48 字节成员记录，逐个成员运行 `0x02F5F868`，目标包 `+0x50=0x26, +0x34=0`，第五个构造参数开启成员差异处理，原生 `0x02F72520` 会设置目标包 `+0x51` bit2。循环中每名成员通过 vfunc+0x368 接包（常见成员 `0x0306B9F0`）。

历史 V3 对 `0x030D5490` 的旧 Hook **零命中**：可能是该分支当时未满足、旧 Hook 配置或入口覆盖不足等；必须保留这个负证据，不得称此路径为 V3 实际路线。

### C2. B：非 A 模式时的群组任务及下级运动路径

`0x03263AB0` 构造 vtable `0x03AE0128` 的任务，对每位成员调用 `0x03068C38`。此函数依据成员位置、朝向和几何阈值分类，将返回值写到 `member+0xB10` 的 bit7（先清位，再写本次值）。**这不是被证明的路点完成标记，且不是实际路线段下发。**

随后这个群组任务的 vfunc+0x10 为 `0x03281408`，它检查 task+0x58/+0x98，必要时调用 `0x03281444`。后者在自己的条件成立时选择 `0x03121ABC` 或 `0x031219B0`；其中 `0x03121ABC` 进入 `0x030ECB10`，复制路线描述，调用 `0x030FE1E4`；后者调用 `0x030C1FDC` 生成路线段、`0x030C7858` 追加/合并路段。结果写入下级控制对象 `+0x70`，并通过 `0x030DB824` 获取朝向，再由 `0x0310E770` 仅把相关对象接入双向关联链表（读写 `+0x10/+0x18`）。**这还不等于主兵模已经消费这条路线或更新了速度。**B **因此确实连通原生几何路线生产**，不能再简单说 A 零命中等于没生成目标。

`0x03281408` 也调用 `0x0181F450`，根据任务内部关联列表的谓词设置它自己的 `task+0x20` 完成标记。此处没有证据支持“检查当前整个兵牌的 60 人都到位”。其内部关联列表对象和单位兵模清单并未建立 1:1 映射。

## D. 在 A 的条件路径下，目标包接收会同步做三件不同的事

```text
0x0306B9F0  common member receiver
    ├── 可选 0x0307F5C8：按成员数据转换目标位置/朝向
    ├── mode=0 → member vfunc+0xE8 → 0x03073224
    │      ├── 0x0315EC98：可写成员姿态位置+0x88/+0x90、朝向+0xB0
    │      ├── 0x03078B1C：条件性选择并写入 member+0x318 模式
    │      └── tail 0x03056ED4：刷新 member+0x910、处理+0x930空间关联
    └── 按包类型清理 member+0x328 旧子动作并安装新的动作
                 vtable 0x03914618 (packet+0x34=0 的普通情况)
```

几点不能混淆：

1. `0x03073224` **确实**在接包阶段立即调用 `0x03078B1C`，过去说它「只修改成员姿态」已被机器码推翻。
2. `member+0x318` 是这个动作代码中的成员动作/运动模式，**不是**玩家 Shift 路点序号、士兵当前位置或可直接编辑的速度。
3. A 的群组循环是**一轮 CPU 调用中的逐个发送**，不是一个各成员的完成屏障，也不证明渲染帧中每个人已开始下一段。
4. `member+0x930` 是空间关联：其他原生动作可用它影响目标重建，但一条可能属于跨单位接触的 `0x03088618` 分支不能直接当作 A 接包必经的运动目标替换。没有证明 A 直接写 `member+0x7F8/+0x818` 的持久主路径目标。

## E. 更关键：同一个新目标之后，各成员还有自己的动作 Tick

在使用相应成员 Tick 的条件下：

- `0x03081EB4` 的一条分支先要求更新标志包含 `0x04`，然后要求 `member+0x324` 等于 `4` 或 `16`，才在 `0x030822D2` 调用 `0x03080F4C(&member+0x328)`。
- `0x03080F4C` **又检查该成员自己的**状态 byte+0x154，以及 `+0x10/+0x18` 子状态，再分别调用新动作 vfunc+0x08 和 +0x10。
- 新动作 vtable `0x03914618` 的 +0x10 是 `0x0325C818`。这里按**该成员自己**的动作模式、链接引用及其他虚函数谓词分流，在 `0x0325C89B`、`0x0325CA15`、`0x0325CA6F`、`0x0325CD2F` 四个独立站点调用 `0x0307885C`。
- `0x0307885C` 再根据 vfunc+0x260、+0xA0 等条件决定是否调用 `0x03078B1C`；真正写入 `member+0x318` 的指令在 `0x0307902F`。**即使同一时刻获得了相同目标包，不同成员也可能在该后续 Tick 中经历不同动作状态转移。**
- 特殊情况：`0x03078B1C` 可以通过关联对象的 `+0xDD4` 数量、`+0xDD8` 指针列表递归传播模式给某些关联成员。这个传播不是无条件对整个 60 人遍历，也无法仅据这段代码判断其组成员清单与兵牌全体相等。

这从**代码机制**上给出了两名士兵切换阶段不同步的一条条件性可能路径，不需要猜测 “Shift 没避障”。但是这里“Tick 不同”只是各成员更新条件不同，不等价于一定跨多帧，更不能由静态代码反推历史 V3 的命中顺序。

## F. RMB/Shift 原生行为时序重建（按层级，不冒充实机帧时间）

| 层级 | 普通 RMB | Shift 队列后继 MOVE | 是否必须等每个士兵 |
|---|---|---|---|
| 原生输入队列 | REPLACE，创建全新 MOVE | 排队等待高层续接 | 此特殊交接区段没有逐名完成门槛 |
| 共享路线 | 新 MOVE 的 +0xA0 初始空 | 可能继承旧共享路线状态并暂存新参数，再初始化求解 | 由共享状态兼容条件驱动 |
| MOVE 任务本体 | 创建原生任务+子任务 | 同一类任务更新函数，前置状态来源不同 | 由 task 状态机判断，不是简单等 60 人 |
| 群组路线处理 | 根据群组模式可能 A 或 B | 同样根据群组模式可能 A 或 B | A 为逐名包分发；B 为群组任务/路线子控制器 |
| 成员接收（仅 A） | 条件性立即修改姿态与动作模式 | 同样的接收器 | 单次群组循环内可逐个下发 |
| 成员后续 Tick（对应动作类型） | 由个体本地标志驱动 | 同一类 Tick 与局部谓词 | **无本段代码可证的全兵牌完成屏障** |
| 模型具体运动方向 | 来自姿态、路线与不同子类型主运动计算 | 同源运动框架但输入阶段可能不同 | 真实物理同步帧未知 |

**较强的机制解释**：Shift 高层 MOVE 续接有能力在士兵继续物理移动期间处理下一段；共享路线状态和成员后续局部动作 Tick 分开调度。于是条件允许“前部已对新阶段改变运动模式、后部仍在旧阶段”，折返时可能相向冲突。普通 RMB 重建高层状态，通常不会保留相同的连续路线交接上下文。但这一机制是否就是 V3 实测的唯一根因，尚无同次运行时的成员模式/主运动目标数据闭合。

## G. 哪些已证明、哪些绝不能冒充证明

**已由原始代码证明**：

- 普通 RMB 初始化共享 MOVE 状态为空，Shift 后继在原生允许时可带状态交接；最上层差异是状态来源。
- MOVE task callback 多次更新、关联子任务和完成标志条件；不是无状态的一次执行。
- `0x03279E40` 根据群组所有者 mode（0/3/5）分为 **A 逐名目标包**和 **B 群组路线任务**。
- B 分支的 Task 能按每名成员自身位置/方向计算 bit7，后续下级对象可以构建、合并真实路线几何并保存指针；`0x0310E770` 是链表挂接，不是主兵模移动推进。
- A 分支的公共成员接收处理可以同步调用成员姿态写入和 mode 变更；后续成员 Tick 还有单独的 mode 写入可能性。
- 当前找到的独立 Tick 和部分相关成员递归更新不是自动遍历整张兵牌的「等待所有士兵」条件。

**未证明**：

- V3 当次命中了群组 A 还是 B；旧 A Hook 零命中是反证约束，不证明 B。
- V3 60 人使用哪几种成员 vtable（此前只稳定采样了 36 名）；不能把一类 Tick 推广给全部。
- `member+0x318` 何时驱动实际主 motor 的目标速度或位移方向；不能把「模式不同」直接换算成「下一路点索引不同」。
- B 路线对象 `submotor+0x70` 的实际**主兵模运动消费者**还未沿虚函数/链接对象完全解析；仅证明创建了路线几何及双向链表挂接，不能宣布成员已经开始沿其运动。
- 两个模型是否在同一渲染/模拟帧实际开始转向；无帧号/调用次序的运行数据。
- 全引擎其它层绝不存在群组同步屏障；上述只是已解代码子图不包含统一等人逻辑。
- 旧 +0x930 保留与 V3 挤压间的实际因果关系；跨单位接触来源限制仍有效。

## H. 对修复设计的实质影响

禁止继续改掉 CA 渐进转弯、全局强制清除成员+0x930、全体硬设置 member+0x318、全局跳过继承状态、改造队列或拿接触位图做速度避让。它们要么没有因果证据，要么不保留原生路径。

补丁真正需要符合的边界是：**仅对原生 queued MOVE→MOVE 源状态，观察／限定群组路段交接与成员实际可消费的下一段运动参数之间的有效性，不破坏原生转弯几何。** 当前只建立了静态子图，未识别可安全修改的单一生产/消费指令；没有宣称修复，更不要求用户立即实机试参。
