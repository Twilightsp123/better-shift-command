# BSC N1 — 2026-10-13 双上游工厂与 +0x100 成员定时任务分叉（精确 EXE）

## 本轮突破

**此前尚未证明所属虚表起点的 `0x03915930`，现已明确属于原生代码亲自安装到对象上的 `0x03915830` 表的 `+0x100` 槽。** 不再需要把 `0x0327BD38` 当作孤立函数。并且找到平行的另外一个处理对象：

| | 工厂版本 A | 工厂版本 B |
|---|---|---|
| 工厂入口 | `0x0326F0DC` | `0x0326F07C` |
| 该回调地址所在静态指针槽 | `0x03940EE0` | `0x03941408` |
| 创建对象字节数 | `0x68` | `0x60` |
| 真实安装的 vtable | `0x039156F8` | `0x03915830` |
| `vtable+0x100` | `0x0327BCF8` | `0x0327BD38` |
| 上游来源引用 | parent`+0x68` → new`+0x58`; parent`+0x50` → new`+0x60` | parent`+0x60` → new`+0x58` |
| 下游成员接口 | 先调用 `0x032638C4` 建描述符，再调用成员 virtual`+0x348` | 经来源 virtual`+0x60/+0x70` 分叉，安装成员 `+0x4C0/+0x4B8` 所用任务 |

**此处列的是原生处理对象类型及任务安装行为，不是 RMB / Shift 的按键分类。** 两个静态工厂回调指针槽并未被证明来自同一玩家 MOVE 订单。

## 可重复复核的真正字节关系

版本 B：
```asm
0x0326F09B mov ecx, 0x60              ; 创建 0x60 对象
0x0326F0A0 mov r9, [rbx+0x60]        ; 上游引用
0x0326F0A4 call 0x030C4BBC           ; 分配
0x0326F0B9 call 0x03264D88           ; 基础构造
0x0326F0BE lea rdx,[rip+...]         ; 0x03915830
0x0326F0C5 mov [rcx+0x58],r9
0x0326F0C9 mov [rcx],rdx             ; 安装虚表
...
0x03915930 [指针] = 0x0327BD38       ; vtable+0x100
0x0327BD58 mov rcx,[rcx+0x58]
0x0327BD5F call [rax+0x60]
0x0327BE59 call [rax+0x70]           ; 前一来源为 NULL 才走
```

版本 A：
```asm
0x0326F0FB mov ecx,0x68
0x0326F100 mov r9,[rbx+0x68]
0x0326F104 mov r10,[rbx+0x50]
0x0326F108 call 0x030C4BBC
0x0326F11D call 0x03264D88
0x0326F122 lea rdx,[rip+...]         ; 0x039156F8
0x0326F129 mov [rcx],rdx
0x0326F12C mov [rcx+0x58],r9
0x0326F130 mov [rcx+0x60],r10
...
0x039157F8 [指针] = 0x0327BCF8       ; vtable+0x100
0x0327BCFF mov r8,[rcx+0x58]
0x0327BD0B call 0x032638C4
0x0327BD29 call [rax+0x348]          ; 成员定时任务安装
```

**特别注意 R9 / R10**：Windows x64 ABI 原则上把 R9/R10 视为 volatile。若只看到 `r9` 读入、经过函数调用、最后写入对象，就直接断定没有改动，会犯静态推断错误。本轮**实际反汇编检查** `0x030C4BBC..0x030C4C32` 和 `0x03264D88..0x03264E1D` 两个被调函数，它们都没有 `call` 或 R9/R10 读写指令。在**这个精确 EXE 的这条确定调用链内**，所以能验证其寄存器值被保留；若后续版本变化，这条关系必须重新校验。

## 与现有五种成员动作类的关系

版本 A 的 `+0x100` 通过成员 `+0x348` 安装 `0x03906C88` 计时任务，后续使用 `task+0x42` 模式和旧动作状态选择 `+0x4B0/+0x580` 等成员接口。

版本 B 的 `+0x100` 就是前轮发现的 `0x0327BD38`，经群组来源虚方法 `+0x60/+0x70`、成员已有任务和状态，安装 `0x03AC8200` 或 `0x03AC7FF0`，后续可触发 `+0x4C0/+0x4B8` 的新动作子类。

**所以五类动作不是 5 个互不相干的键位选择，至少两大原生任务家族来自这对不同的上游处理对象工厂。**

但我们还没把这两个工厂的**真实创建条件**与普通 RMB（替换队列）或 Shift 后继 MOVE（追加队列）实例关联；不应声称一类就是普通 RMB、另一类就是 Shift。

## 运行时类型谓词进一步验证（2026-10-13）

已检查 `0x0327711C`，其读取 `[object+0x38]`，并与静态回调注册指针 `0x03D19C08`、`0x03D19C10` 比较；另有 `0x0327714C` 和 `0x03277214` 将同一字段与包括 `0x03D19A88` 的回调指针集合比较。这是**运行时对象类型鉴别**的原生代码，意味着两种工厂家族不仅出现在数据段，也在实际可执行的类型判断中被明确区分。当前还没接到具体 Shift 后继 MOVE 的同一任务实例。`audit_two_handler_factory_origins.py` 已添加这些字节守卫；本地精确 SHA EXE 独立测试为 39/39 真实指令、9/9 E8、12/12 类型及静态注册指针、2/2 RIP 表安装，两个 R9/R10 保留叶函数也验证通过。此项不构成修复或现场 Shift 命中证据。
