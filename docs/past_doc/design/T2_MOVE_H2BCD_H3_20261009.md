## Scope: experimental behavior, not released

This branch **intentionally changes** old SC1 90°/135°/180° proactive
handoff and exact Native MOVE adoption permission when strict route fidelity
cannot be shown. It is an isolated behavioral candidate. Its source passes
synthetic Controller tests, but no actual WH3 execution has been observed.

No change to Native DLL/Hook/address map, gameplay CFG scalars, T2-B Attack
dual-envelope policy, or T1.6's unique transaction/cursor commit authority.

## H2-B: separate execution commit from waypoint credit

The old bug was reproduced and preserved as immutable H2-A:
`ACTION_COMPLETE reason=STEERING_CORNER_HANDOFF remaining=40.000000`
after Native acknowledged an early proactively issued 90°/180° MOVE. The
controller **correctly knew** the new command executed but **incorrectly
claimed** the previous MOVE's waypoint was reached.

For MOVE→MOVE, H2-B now binds a route-credit disposition in the
transaction's frozen geometry:

- `SATISFIED`: route arrival/completion evidence is available. If the
  action is not already complete, commit may issue a single
  `H2_ROUTE_SATISFIED_OBSERVED` completion credit.
- `DEBT_PRESERVED`: T1.6 still commits a verified execution edge and
  advances to the next canonical action, but registers the current waypoint
  in the existing SC3 debt table. The old MOVE is not marked complete.
- `BLOCKED`: a new proactive ISSUE is not submitted. On already Native-
  executing exact `i+1` MOVE, the adopt-only envelope is denied and
  existing bounded rollback/recovery remains authoritative.

ACK rejection, missing ACK, stale revision and invalid Native identity
remain non-credit. The current generation, exact action, canonical index
and T1.6 single-commit safety checks remain intact.

## H2-C: issue-time route-fidelity gate

`R1.H1RouteObligation.evaluate` supplies the **existing reach tolerance**,
fresh crossing evidence, successor chord and prior SC3 debt geometry.
`advance()` denies Move→Move `ISSUE` if the verdict is `BLOCKED`,
even when the legacy SC1 predictive timing window is open. `dispatch()`
rechecks the obligation after draining the Journal and before making the
actual Native ISSUE.

This is **not** another speed/angle/distance tune. It removes a false
permission: a command that directs the unit back from x=60 to x=0 cannot
be treated as preserving player waypoint x=100. An outbound 90° shortcut
at x=60 is likewise not certified. A 90° turn after observing the unit
within the already-existing waypoint envelope is still allowed.

**Trade-off not yet resolved in WH3:** conservative route fidelity can
force visible waypoint braking or stepwise motion. H2 cannot prove smooth
physical turning without actually observing WH3. Do not reinterpret
synthetic compliance as proof of no pauses.

## H2-D: unified ISSUE / ADOPT obligation protocol

A proactively issued successor freezes the same route disposition in the
T1.6 transaction as an exact native `i+1 MOVE` adoption. The Native path
uses only `cached.h1_shadow` captured while the original MOVE was
**exactly active**, after F's V3-only/live revision checks, D generation,
action identity and prior-debt checks, and G's original turnback guard.

The route-credit proof is shared, but the T1.7 issue and adopt time
windows remain separate. No `i+2` canonical skip is legal.

## Historical contract and mutation maintenance

The old `test_v104_blocks.lua` assertions saying a unit MUST proactively
U-turn while still 40m away from the waypoint and MUST credit a 90° turn
at x=60 are explicitly superseded **on this isolated branch only**.
Their H1/G original files and CI results remain unchanged as archival
evidence. Replacement cases assert: (1) route-unsafe early issue is
denied, (2) ordinary collinear and SC3 payable debt continue, (3) a
near-waypoint turn still issues, (4) route completion never precedes ACK
without independent arrival proof.

The obsolete early-SC1/SC2/SC4 mutations were replaced in the active
maintenance path by five H2 authority mutants: bypassing route issue
guards, losing pre-ISSUE proof, bypassing Native debt veto, incorrectly
crediting a payable debt, and deleting debt transfer. The historical
mutation suite is preserved by the frozen H1/G source branches.

T2-B Move→Attack, C/T1.6 transaction protocol, A/B/D pure models,
original independent Native/ADDR contracts still execute in the active
maintenance suite.

## WH3 live acceptance — currently NOT RUN

The testing operator must have the correct Windows x64 WH3 executable,
the fixed WinX64 Native Bridge build, ability to load one local PACK,
and access to battle `script_log_*.txt` and a video capture.

Use ONLY ONE debug or plain candidate at a time, and avoid simultaneously
loading a subscribed/public BSC PACK of the same mod. Keep the original
stable build available for comparison.

| Gate | Controlled WH3 maneuver | Must verify |
|---|---|---|
| RT-TP-04a | Single unit, 3–10 collinear Shift MOVE nodes | Continues automatically; no silent waypoint loss; no repeated rollback/reissue |
| RT-TP-04b | 45° and 90° Move→Move with visible waypoint | Route fidelity AND actual stop/brake behavior separately recorded |
| RT-TP-05a | 135° then 180° foldback at distinct waypoints | No turnback self-compression; waypoint physically visited before reversing; record any pause |
| RT-TP-05b | Dense 5–15m zigzags and repeated corners | No skipped nodes, runaway SC3 debt, jitter or pinball reissue |
| RT-TP-05c | Two or more units using distinct Shift paths | Per-unit ownership, sequence and ACK correctness, no cross-unit identity pollution |
| RT-TP-02 | Straight MOVE→ATTACK after MOVE route | Does not completely park then attack; exact target retained |
| RT-TP-03 | Angled MOVE chain→ATTACK with route obstacle | No illegitimate shortcut, stop/reassert loop, or lost Attack |

Record **both** (A) waypoint preservation and (B) movement smoothness as
independent PASS/FAIL columns. A test fails if either invariant fails;
do not hide a stop by only recording correct route geometry.

After each WH3 test, preserve: exact candidate pack hash, executable
version/build, loaded mods list, battle setup/units, raw script log and
an appropriately named video. Look for
`H2_ROUTE_ISSUE_BLOCKED`, `H2_PREISSUE_DENIED`,
`H2_EXECUTION_COMMITTED_ROUTE_OWED`, `H2_WAYPOINT_CREDIT`,
`TRANSITION_EDGE_COMMITTED`, `ROUTE_OBLIGATION_SATISFIED`,
`NATIVE_SUCCESSOR_ROLLBACK`, `CONTROLLER_FAIL`.

**Runtime access limitation:** CI hosts do not contain a WH3 game process.
The project agent cannot start the user's local Windows game from this
cloud environment. Runtime status must remain **NOT TESTED** until
operator-supplied WH3 gameplay/log evidence is reviewed.
