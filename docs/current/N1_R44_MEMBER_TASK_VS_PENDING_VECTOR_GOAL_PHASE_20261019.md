# Better Shift Command — R44 / 本对话第 10 轮

**日期：2026-10-19。** Win64 游戏原生 Shift MOVE 折返穿插问题的只读静态逆向。**本轮没有制作 Native gameplay patch，也没有新版游戏进程内采样。** 本报告聚焦 R43 待处理通道的生产者疑点及另一个更接近成员运动状态的真实输入边界。

## 1. 严格版本与证据范围

- 原始 EXE：用户提供的 `Warhammer3.zip` 中 `Warhammer3.exe`，232,531,920 字节，SHA256：`9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`。
- PE32+ x64、ImageBase `0x140000000`。本文所列全部数值为 **RVA**；运行时地址必须加上实际装载基址。
- 本轮新审计 `audit_r44_member_task_vs_pending_20261019.py` 使用固定完整 SHA、GNU objdump 真正指令边界、PE unwind 函数范围及 `.xcode` 原生虚表内容：**111/111 原始指令、11 个函数/叶函数范围、13/13 个 E8、9/9 个控制转移、7/7 个具体虚表槽**。
- 对整个可执行节所有 `E8` 字节先以相对目标过滤、再以完整函数反汇编起点筛选。核验 `0x03065DB8` 的全部**直接 E8** 调用者；不包括虚表、函数指针、JMP 或动态间接调用。
- 本地新版 EXE `unittest` **18/18 PASS**；无 EXE `17 PASS / 1 SKIP`。**这不是游戏实测**，不代表碰撞修复 PASS。

## 2. R43 的待处理记录没有证明是唯一通道；新增反证

R43 已确定成员 Tick：

```text
member+0x8D8 非零
    ↓
03086FD2 检查
    ↓
03086FE5 R8 = &member+0x8DC（向量）
03086FF1 RDX = &member+0x8E8（目标）
0308700C 先清 +0x8D8
03087013 CALL 03065DB8（目标/增量安装器）
```

本轮在新版 EXE 整个可执行节找到 `0x03065DB8` **四个经过真正指令起点确认的直接 E8 调用点**：

| RVA | 类型证据 | 目标 RDX 与向量 R8 |
|---|---|---|
| `03087013` | 已证普通成员 Tick | 当前成员 `+0x8E8` 与 `+0x8DC` 缓冲区 |
| `030728C1` | 普通成员同类型虚表 `+0x470=03071DC8` | `&member+0x1E0`；该函数计算的栈上三维向量 |
| `0308DA71` | 普通成员 Tick `03087351` 直接到 `0308D830` | `&member+0x1E0`；经多道状态和随机门槛产生的栈上向量 |
| `0325E544` | 类型化成员内嵌任务虚表 `+0x08=0325E4B4` | **执行时** `&member+0x1E0`；**构造时**保存的 `&task+0x38` 三维向量 |

**直接纠错：** `member+0x8D8` 不是所有 `0x03065DB8` 目标／增量更新的必要前置条件。R43 关于此缓冲区内部消费时序的原码结论继续成立，但不得把它扩大为整个成员更新系统只有一个入口。

本轮额外做了可执行函数的 `+0x8D8/+0x8DC/+0x8E8` 直接编码引用搜索，再对相关函数反汇编。**在已定型的这些普通成员函数中**，直接 `member+0x8D8` 引用只有成员构造器 `0305306F` 取地址、Tick `03086FD2` 检查，以及 `0308700C/18` 清标志。未找到一个已定型的直接非零生产者。但这个负证据**不是整个游戏不存在生产者**：`&member` 子对象别名、偏移基址转换、批量复制和其它虚方法仍可能绕过直接扫描。按本项目的止损规则，**将“待处理生产者是 Shift 的主要来源”降级**，不再无期限全局搜索 `0x8D8`。

## 3. 类型化闭合：成员 state16 内嵌任务到目标/增量安装

这一条链以前只掌握了若干外围虚表/字段，本轮首次连接成同一成员对象的连续机器码数据流：

```text
普通成员构造器 03052BA8
  03052D20  安装 vtable 03912950
  03052E7B  RSI = &member+0x328
  03052EEE  [member+0x328] = member
      ↓
成员虚表 +0x550 = 0306F594（须满足若干状态门槛）
  0306F70B  RBP = &member+0x328
  0306F712  member+0x324 = 16
  0306F71F  清理旧内嵌任务（受条件）
  0306F724  RCX = &member+0x330
  0306F730  RDX = &member+0x328
  0306F733  CALL 0324DBAC
      ↓
0324DBAC → 03053630
  0305363D/40  task+0x08 = [member+0x328] = member
  03053650     启用 action+0x154 的状态标记
  0324DBBB/C2  安装 task vtable 03AE22D0
  0324DBC5..D8  把输入的三个 float 复制到 task+0x38/+0x3C/+0x40
      ↓
普通成员 Tick 03086F04
  当 member+0x108 bit0x04 置位，且 state+0x324 为 4 或 16
  0308731B  RCX = &member+0x328
  03087322  CALL 03085F9C
      ↓
03085F9C（active 与任务标志通过时）
  03085FC1  virtual+0x08（首次更新）
  03085FC8  将 task+0x18 置为 1
  03085FD4  条件性 virtual+0x10
      ↓
03AE22D0 +0x08 = 0325E4B4
  0325E50F  R8  = &task+0x38（创建时保存的向量）
  0325E513  RCX = [task+0x08] = member
  0325E530  RDX = &member+0x1E0（执行时的成员当前目标）
  0325E544  CALL 03065DB8
      ↓
03065DB8 复制当前目标并调用 03154974
  03154974 把传入向量换算成 member+0x13C/+0x140/+0x144 增量，置相关状态位
```

对象身份证明强于“相同偏移推断相同对象”：本轮验证了成员自己的构造器虚表、`[member+0x328]=member`、任务构造器保存的成员指针、同一任务的实际虚表槽及 Win64 RCX/RDX/R8 调用现场。其余成员、特殊派生类型不能未经验证直接类推。

### 最值得进一步检查的时间边界

**任务创建时缓存输入向量，但任务实际首次运行时才读取成员当前目标。** 这产生一条可以否证的候选不变量：

> 对同一成员的一次 state16 内嵌任务，`task+0x38` 的运动向量与第一次 `virtual+0x08` 时的 `member+0x1E0` 目标是否属于相容的同一路线更新阶段？

如果创建与执行之间其他命令改变了当前目标，而旧向量未对应重建，理论上可能出现目标/运动不一致。**但还没有证据证明玩家 Shift 折返触发这条错配，更没有证据它导致士兵互挤。** 正常 CA 异步成员转向本来就允许短时不同朝向，不应直接据此强制同步。

## 4. 同一普通成员的两条其他入口不能混为 Shift 根因

1. `member vtable+0x470=0x03071DC8` 使用其 `RCX=member`、传入的关联对象以及当前目标来计算向量，条件性直达 `03065DB8`。没有建立它和 Shift 后继 B2 packet 的同实例关系。
2. 成员 Tick 有 `03087349 CALL 03059BC8`（steering）后接 `03087351 CALL 0308D830`。后者另受 `member+0x30 != 0`、`member+0x2E8 != 0`、`member+0x26C` 为 `0x78/0x79`、进一步虚方法/概率等多重门槛控制，才可能在 `0308DA71` 调用目标/增量安装器。旧 R39 认为它的一个 `+0x90` 写入是随机上下文而非坐标，这仍然正确；**但该函数后段另有真实的成员运动目标更新**，不可因前段写入对象类型不同而漏审全函数。

## 5. 止损与修复约束

- 新事实：`0x03065DB8` 有四个直接 E8 调用者；state16 内嵌任务存在**缓存向量／执行时读取当前目标**的可核验数据边。
- 降低优先级：仅查 `member+0x8D8` 显式写者，或将所有目标更新都归结为 Tick 待处理通道。
- 没有证明：哪种成员状态在玩家 Shift 折返命中、创建与执行之间确实改变目标、两名真实空间邻兵实际收到互相冲突的增量、RMB 对照差异以及 bug 的首个错误条件。
- **禁止施工**：不得全局改 `bit0x02/bit0x04`、NOP 状态任务、合并不同成员的 Tick、删除 CA 原生渐进转向、寻路、避障，或破坏普通 RMB MOVE / Shift ATTACK。
- 这里发现的是风险窗口和具体下一条调查边，不是 gameplay 修复成功。

## 6. 下一轮仅保留两个优先目标

1. **沿 B2 packet → 成员接收器的虚方法选择 → member+0x550 state16 写者**，验证该已类型化内嵌任务是否能够由 queued MOVE 后继实例创建，以及是否存在原生的目标/向量一致性门槛。避免再花多轮证明所有任务类都能用同一槽位。
2. 若同一 MOVE 无法触发 state16 或确有防混代机制，立刻降低此候选优先级，转向 `03071DC8` 所生成的逐成员增量及普通积分器 `03146FF0` 的消费，不再追隐含 `+0x8D8` 生产者。
