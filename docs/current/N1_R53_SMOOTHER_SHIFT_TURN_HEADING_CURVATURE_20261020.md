# BSC — 第19轮 / R53：从原生路段朝向和队形曲率调查 Shift 折返平滑度

日期：2026-10-20。目标不是再次证明缺陷，而是寻找保留 CA 原生 Shift MOVE 队列、渐进转弯、避障的**更流畅转弯**条件。**无 Native gameplay patch；无游戏内动态命中；不对全局 steering 打补丁。**

## 1. 输入与可复现程度

本轮直接读取用户新版 `Warhammer3.exe`：SHA256 `9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`；Win64；ImageBase `0x140000000`；本轮地址全是 RVA。使用 GNU objdump 及 PE Exception DataDirectory 的真实 x64 RUNTIME_FUNCTION 函数范围。**33/33 完整机器码和真实指令起点、9/9 E8 目的地址、1/1 JCC 目的地址、4个独立 unwind 函数，实际 EXE 静态验证 PASS**；21/21 unittest PASS（含真实 EXE 1 项）。无 EXE 环境应为20 PASS/1 SKIP。

注意：从 R13 到 R52 已知道部分字段，但这是首次在**新版 EXE** 内把两种后继朝向源、frame-aware 世界目标输入与 ushort 角度换算率在同一小型 audit 里一起确认。本轮新增价值在**转弯平滑度的可判定数值量**，不是把旧工作宣称为首次发现。

## 2. 新版 Native MOVE 后继激活：两种不是一回事的朝向输入

核心函数：`0x0302AE74`，其路段配置共用同一个原生函数 `0x030179B0`。

```
queued MOVE slot+0x9A bit 0x02
       │
       ├─ 非零： 0x0302AF7A 读取 WORD [MOVE slot+0x98]
       │          ↓ R8W=已保存的16位路段朝向
       │          0x0302AF95 CALL 0x030179B0
       │
       └─ 清零： 0x0302B0BC 读取 [UnitRoot+0x32F8] 的当前 Group
                  0x0302B0C3 读取 Group 的空间记录
                  0x0302B0CA CALL 0x02D5008C 取得当前 Group 空间点
                  0x0302B0D9 CALL 0x0312214C 解析目标坐标
                  0x0302B0E7/EC 按 X/Z 做相对坐标差
                  0x0302B0F2 CALL 0x01183A8C 计算角度类结果
                  0x0302B0F7 乘以 10430.3779296875
                  0x0302B0FF CALL 0x004EDA50 量化/转换
                  0x0302B119 R8D=AX 取最终16位朝向码
                  0x0302B126 CALL 0x030179B0（同一个配置器）
```

这里 `0x0312214C` 进一步验证：如果目标带参考对象，会通过 `0x02F3D668` 对 `ref+0x18` 参考坐标做变换；否则直接复制 XYZ。**所以 live 分支根据 Group 空间点至解析后的目标点形成方向，不是直接读取 Group 的面向角字段。** 把它误叫“live Group facing”将引导错误补丁。

角度比例：EXE 中 `RVA 0x03922260` 的 Float32 值为 `10430.3779296875`，等于 `65536/(2π)`（浮点舍入内）。因此这里用 **65536 个单位对应一整圈**。单步 ≈ `0.005493164°`，角度量化分辨率足够细，**单纯 16-bit 量化并不能解释宏观约90/180度的大幅转向**。更值得比较的是**预存 heading 与按执行时空间重新计算的 heading 是否突然改变**。

### 参数和提交身份

`0x030179C7` 把传入的 R8W 保存到 EBX；在 `0x03017A69` 把 BX 转为 `R9D`，`0x03017A79` 交给路线构造器 `0x030F1B3C`。此处证明了两个条件分支的角度都进入**同一**下游路线构造逻辑，不是两套毫不相关的算法。

构造器检查上下文 `+0x94`、UnitRoot `+0x184` 和第5/6栈实参等条件，条件通过可在 `0x03017ABB` 写入 `UnitRoot+0x270`。**配置函数可因门槛提前退出，不代表每次 CALL 都完成新的路线提交**。对应的 shortTask 构造函数仍于 `0x0302B1B3` 调用，是否满足进一步推进条件仍未知。

早期统一 MOVE 入口 `0x0303777D` 在部分条件下 OR 描述符 `+0x5A` 的 `0x06`，且 `0x03037791` 修改保存角度描述符 `+0x58`。因此不同命令路径可能选用不同后继 heading 源；它们的含义**不是“RMB 一律一种、Shift 一律另一种”**，需依据真实 MOVE slot 的字段和状态判断。

## 3. 转弯更流畅：不要只追输入键位，应分析可实现的曲率

假设队形中心轨迹是平面曲线 `c(s)`、单位切向量 `t(s)`、法向量 `n(s)`、曲率 `κ(s)`，横向距中心的成员偏移 `u`。如果要求队形相对中心在转弯中保持横向位置，那么成员轨迹的局部切向进度系数为：

`(1 - κ(s) · u) ds`

对圆弧半径 `R=1/|κ|`，转弯内侧半宽 `H` 的理想路径切向比率是 `1-H/R`。**当 R≤H 时，严格刚体队形内侧的切向进度可能为0或反向。** 这不证明碰撞；而是说明若还要求所有士兵独立向前步行、以相近速度推进，运动学目标就可能相互冲突。因而“给全队统一一个急剧的路段朝向”不一定得到流畅、无挤压的成员路径。

用户实机描述：CA 会把接近180°的 Shift 折返转成约90°+90°。对于**两个都用半径 R 的普通圆角 fillet**，每个90度角需要占据相邻直线段长 `R tan(45°)=R`。共享中间直线段长 L 需有 `L≥2R`；而要给半宽 H 留正的切向进度与边际 M，需 `R>H+M`。两个条件同时成立，需要：

`L > 2(H+M)`  （针对这个简化的“两段90°圆角”，是必要的几何窗口，不是 CA 原生硬编码阈值）

**这提示新搜索目标：转角可用距离 / 队形横向半宽 / 目标角差与旧状态速度是否匹配。** 如果折返路线距离不足，单纯增大一个全局转向插值系数可能让动画更柔和，却不能让所有成员拥有物理上相容的局部路径。

### 纯合成反例（不是游戏测量）

设队形半宽6、两处90度角共享中间段8、余量0.5：最大非重叠圆角半径 `R≤4`，但内侧有正进度要求 `R>6.5`，**不能同时满足**。此时模型的 `1-H/R= -0.5`，表示该固定偏移圆弧的内侧成员相对于中心弧长有局部反向要求。这不是 CA 真实单位尺寸，也不是 Shift Bug 的已证根因。`formation_turn_feasibility.py` 给出可重复的严格合成测试。

## 4. 反推出可安全评估的 Native 改良策略，而不是盲目 NOP

推荐优先级：

1. **先定位几何条件**：同一 queued MOVE 后继路段，记录 `slot+0x9A`、`slot+0x98`、当前 Group 位置、解析后的世界目标、UnitRoot+0x270路线是否真正提交。比较 **signed circular heading delta** 而不是普通无环整数差； `65535→1` 应算2单位而不是-65534。
2. **关注转角间距和队形宽度**：若急转角短距离接连发生，检查原生路线成员分配是否有弧线空间预算。必要时研究通过原生几何输入调节**可行转弯半径与预瞄路径**，而不是全局压低模型最大角速度或强行等队伍停下。后者会牺牲 CA 的原生渐进转弯和避障能力。
3. **只有在证明目标一致而物理运动仍相互挤压时**，才去特定成员 steering/积分器中检查速度/角速度限制。不得仅凭本报告全局覆写 `member+0xE0` 或头向。
4. **修复应在原生 queued MOVE 的可证身份链上选最小补丁点**，保留普通 RMB、Shift ATTACK、CA navmesh/避障，并严格受新版 EXE SHA、原字节、线程和回滚约束。这个提交不含可部署补丁。

当前最高价值下一问：**原生路线构造器 `0x030F1B3C` 将16位方向与 Group/目标几何组合时，是否有“折返圆角半径/转弯预瞄/队形宽度”的输入或约束？** 若未找到这样的物理限制，再分析成员局部任务分段和 `0x03146FF0` 增量消费。
