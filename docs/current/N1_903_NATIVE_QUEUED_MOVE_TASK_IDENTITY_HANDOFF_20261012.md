# BSC N1 / 原生 MOVE 队列复用任务身份的精确逆向（2026-10-12）

> **当前关键结论：原生 MOVE 队列内存在经条件保护的“上一槽位任务对象转交下一槽位”路径。已经静态证明对象指针复用、状态重置至 1、48 字节目标几何替换；但尚未证明这条路径在用户 Shift 连续折返时实际命中，也没证明这种复用导致挤压。不能因此直接清空任何底层成员状态。**

## 1. 证据与可复现性

目标是 SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a` 的原始 `Warhammer3.exe`。使用完整 PE+x64 unwind 函数边界，以及 GNU objdump 核对全部 **35 个独立原生指令起点**；**6** 条 E8 源地址→被调函数边、**5** 个**带对象类型的 MOVE 槽位虚表入口**均成功静态校验。对应研究代码 `maintenance_tools/native_shift_re/audit_move_queue_task_handoff.py` 和 `tests/test_native_shift_re_move_queue_handoff.py`。区别原始 EXE 静态验证与尚未发生的运行时实例证明。

## 2. 真正的“新命令取代原队列 / 追加路点”开关

```asm
0x030323FC mov r14b,r9b         ; 通用原生命令入口第 4 个参数
...
0x030326B4 lea rcx,[rbx+0x278] ; 同一命令队列控制器
0x030326BB mov dl,r14b
0x030326BE call 0x02F50410
...
0x02F50425 test dl,dl
0x02F50427 jne 0x02F50449     ; 非零：不先清空旧队列
0x02F50444 call 0x02F39F94    ; 零：逐槽清除旧队列
```

`0x02F50410` 后续追加尺寸 0x120 的环形槽位，固定容量 0x28（40）；接着原始 `0x030326E4 call 0x030090BC` 初始化具体 MOVE 槽位。

**警告：**`DL=0` 的“replace/reset”和 `DL!=0` 的“append/queue”意义得到机器码证明；但你历史上的 Windows JSONL 没抓到真实用户键位及对应 R9B，所以不可把这项静态条件强行归为每一个具体 RMB/Shift 实例。

## 3. 关键：同类 MOVE 槽位真实 VTABLE

`0x030090D1` 取 `0x0390B4F0`，`0x030090D8` 将其写入新槽位对象；`0x030090E7` 使新槽位的 `+0xA0` 旧任务指针为 NULL。

| 槽位虚表偏移 | 真实实现 RVA | 功能证据 |
|---|---|---|
| `+0x08` | `0x03025D70` | 激活／提交 MOVE 槽位及相关动作任务 |
| `+0x38` | `0x008D3350` | 该具体类返回 true（`mov al,1; ret`） |
| `+0x40` | `0x03039FB0` | 若旧任务满足状态／群组要求，返回旧任务指针 |
| `+0x48` | `0x03040864` | **接受该旧任务指针，改写目标几何，并保存给新槽位** |

这个 MOVE 槽位类 **`0x0390B4F0` 与 B 缓存群组任务类 `0x03AE00E8`、构造后改包群组任务类 `0x03ADD608` 都不是同一种对象**。仅凭同样的 virtual 偏移不能跨类归因，已吸取以前误数 53 个发送者的教训。

## 4. 条件性的 MOVE→MOVE 复用任务交接

队列管理器 `0x0304433C` 的相关路径：

```text
旧 MOVE 槽位
  0x03044562 -> vtable+0x40 -> 0x03039FB0
    读 [oldSlot+0xA0] 的 oldTask
    要求 oldTask 非空
    要求 [oldTask+0x20] == 4
    要求 [oldTask+0x24] != 0
    要求 [oldTask+0x158] != NULL
    要求群组条件 0x02D63794 通过
    成功才返回原 oldTask 指针，否则不交接
                               |
  0x03044596 -> next MOVE vtable+0x38 必须返回 true
  0x0304459D -> ++oldTask.refCount(+0x18)
  0x030445A8 -> mov rdx,rsi (旧任务地址)
  0x030445AB -> next MOVE vtable+0x48 = 0x03040864
                               |
新 MOVE 槽位
  0x030408CF [same oldTask+0x20]=1
  0x030408EC [same oldTask+0x120]=新路线 16B
  0x030408F8 [same oldTask+0x130]=新路线 16B
  0x030408FF [same oldTask+0x140]=新路线 16B
  0x03040906 [newSlot+0xA0]=same oldTask
```

`0x030408AF` 调用的 `0x0301C1B4` 是已解码的短叶函数，读取群组方位浮点，不修改 RDX；因此 `0x030408CF` 之后的同一 RDX 仍是之前来自 `0x030445A8` 的旧任务对象。

**这个函数本身没有**清除 `oldTask+0x158`，也没有直接改写任何成员 `member+0x1E0` 目标。这里说的只是 setter 局部函数，没有排除后继 Tick、action、路径更新回调稍后主动刷新这些数据。

请勿把这条**条件性静态路径**夸大为“原生所有 Shift MOVE 都保留旧任务”。现有两次用户实机 JSONL：第一次只记录了少量成员，第二次虽然 group Tick 目标数据有效，但关键发送者/队列链接全部被 logger 丢弃；均未动态验证上述旧任务→下一槽位移交条件实际触发。

## 5. 与现有实机运动证据的关系

真实第二次采集：同组成员多次几乎同时反向，并在若干 group Tick 后逐个改变位移方向；Tick 659/660/661 观察到两名成员中心距离 **1.124→0.609→0.973**，仅证明位置靠近。后续静态几何复核还发现，在 Tick 548 的**三名**目标反转记录中，两条“当前位置到下一 motor lookahead 目标的直线段”在二维平面内相交（其余已保存的同 Tick 反转组未出现此交点）。

**交点是端点几何性质，不能证明真实曲线路径相交或碰撞；旧日志未记录精确 RMB/Shift 输入身份。** 因而后续必须区分：
- 前一原生任务 `+0x158` 等引用是否仍被后续动作读取且产生不一致；
- 合法 CA 渐进转向所需的短时速度惯性；
- CA 按成员分别分配的 lookahead 目标本身是否在转角时相互穿插。

## 6. 下一步允许做什么

先继续静态核对 **`0x03039FB0` 前置检查与 `+0x158` 具体类型／所有者、`0x03040864` 移交后谁再次读取它、后继 MOVE 槽位激活 `0x03025D70` 是否重建每名士兵目标**。任何原生修复应该保留队列对象和 CA 的成员路径几何／避障，不要将“普通 RMB 会清空队列”粗暴照搬到 Shift。
