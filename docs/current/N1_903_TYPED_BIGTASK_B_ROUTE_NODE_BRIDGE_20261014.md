# BSC N1 · WH3 9.0.3 · 大任务引用到 B 型路线节点的类型化桥接（2026-10-14）

## 研究结果与原始 EXE 证据等级

本轮在用户提供的固定 SHA256
`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`
的原始 x64 `Warhammer3.exe` 上，完成 **168/168 原码与真实 GNU objdump 指令起点、22/22 E8 直接调用、5/5 JCC 目标、3/3 RIP-relative 虚表安装及 3/3 类型化虚表槽位**。本地 **18/18 离线测试通过**，其中包括原始 EXE 全量审计；在公开 CI 中 EXE 项按预期跳过。

这次不仅把 `manager+0x1F0` 大任务链与 `manager+0x2D0` 路线节点链放到同一管理器，而且**找到了 B 家族原生辅助任务通过字段与调用栈，将大任务指针传给特化路线节点构造器的实际机器码路径**。它是带条件的静态分支，**未确认玩家具体 Shift 后继 MOVE 执行这条分支**，更未证明此行为就是兵模挤压根因。

## 一、重要纠错：相邻三张虚表不能合并

当前原始 EXE 中确有相邻的三张实际安装虚表，构造器的 RIP `LEA` 和写入点可以逐一证明：

| 虚表真实起点 | 实际安装点 | 本类型的 `+0x10` 方法 |
| --- | --- | --- |
| `0x03AE00E8` | `0x03263ED5` | `0x03281520` |
| `0x03AE0108` | `0x03263FE4` | `0x03281600` |
| **`0x03AE0128`** | **`0x03263ACF`** | **`0x03281408`** |

虽然 `0x03AE00E8+0x50 == 0x03AE0128+0x10` 在数字上恰好相同，**`0x03281408` 实际属于第三张表的 `+0x10`，不能称为第一张表的 `+0x50` 实现**。三种对象有不同构造器/字段所有权；不能跨表以相同虚函数偏移拼接实例。这修正了上一阶段误把 `0x03281408` 归入 `0x03AE00E8` 的推断。

## 二、短期 MOVE `shortTask+0x74` 影响辅助任务是否持有大任务引用

在 `0x02F561E8` 及两条构造器路径中：

1. **`shortTask+0x74 != 0` 分支**：`0x02F56358` 直接调用 `0x03263D68`。此处调用者栈第 5 个参数被置零；叶函数 `0x03263D6C` 从 `[rsp+0x28]` 读出零值，`0x03263D87` 写 `aux+0x20=NULL`。
2. **`shortTask+0x74 == 0` 分支**：`0x02F5641E` 调用 `0x02F4EFE0` 取得关联任务候选；`0x02F56431` 调 `0x03263E7C` 包装器。包装器 `0x03263EAC` 把该引用放入 Windows x64 第 5 个参数栈槽，再调用同一个 `0x03263D68`；叶函数写入 `aux+0x20`，非空时 `0x03263DDE` 给 `[task+0x18]` 增加引用。

二者最终可进入 `0x03279E40` 群组分派，但并不意味着都按相同方式生成路线节点。`+0x74` 是此处的实际分叉字节，不是 RMB/Shift 键位本身。

## 三、B 类型任务与线路节点的真实类型化构造链

当 `0x03279E40` 的模式门槛选择 B 族时，`0x03279ED8 → 0x03263AB0` 构造安装 **`vtable 0x03AE0128`** 的 B 类型对象。`0x03263AF2/AF6` 由栈描述符 `+0x08` 读取辅助任务，保存到 `Btask+0x58`。其真实 `vtable+0x10=0x03281408`，在对应状态下调用 `0x03281444`。

在 `0x03281444` 中：

- 如果 `aux+0x58` 已有路线节点，先走复用/有效性判定，不立即无条件创建。
- 否则若 `aux+0x20` 有大任务指针且其 `task+0x158` 为空，跳过本轮新节点生成（`0x032814A7/AF` 门槛）。
- 通过其他状态/描述符前置判断后，从 `aux+0x08 → +0x440 → +0x160` 得到共享管理器，并构造临时路线描述符。
- `aux+0x20` 有大任务时，`0x032814FB` 调用 **`0x03121ABC` 特化构造器**；否则 `0x0328150A` 调用 **`0x031219B0` 通用构造器**。函数把创建的节点指针放回 `aux+0x58`。

这不是“两个偏移都叫 +0x160 因而共享同一任务”的推测：它是 **`aux+0x20` 原生指针 → 具体控制流分支 → 特化节点构造器** 的机器码传递。

## 四、特化节点构造时从大任务和旧子任务生成 `node+0x70`

`0x03121ABC` 使用管理器的路线节点池，`0x03121B3B` 把临时描述符放在调用者第 5 参数槽，`0x03121B36` 把大任务指针放在第 6 参数槽，然后在 `0x03121B40` 调用 `0x030ECB10`。

真实 `0x030ECB10` 构造器**分别**读取两个参数：`[rsp+0x70]` 是描述符（通过 `0x030EC9EC` 复制到 `node+0x20`），`[rsp+0x78]` 是大任务对象。它从大任务中读取位置类字段 `+0x80/+0x84/+0x88`、指针 `+0x90/+0x98`，并在 `0x030ECB66` 取得 **`task+0x158` 旧子任务指针**。随后 `0x030ECB98` 调 `0x030FE1E4`，在 `0x030ECBA2` 把返回的路线对象指针写入 **`node+0x70`**。

`0x030FE1E4` 确有原生旧子任务链表处理：它由传入 `task+0x158` 开始，`0x030FE280` 将每个旧子任务的 `+0x18` 字段**地址**交给 `0x030C7858`，`0x030FE28C` 再沿旧子任务 `+0x08` 指针遍历。这是旧任务参考几何参与新路线构造的正证据。它没有证明 CA 的渐进转弯本身错误，不能清空这些合法引用。

## 五、生成节点的有效标志决定何时走通用重算

特化构造器在 `0x030ECB2E` 设置 **`node+0x08=1`**，并保存按大任务生成的路线输出。通用构造器 `0x031219B0` 则先于 `0x03121A25` 清除 `node+0x08`，再在门槛通过时用 `0x030FDA9C` 转换器填充 `node+0x70`，并可设置有效标志。

`0x03128E80` 的既有节点更新循环检查 `node+0x08`，在它非零时会**跳过当前通用 `0x030FDA9C` 重算路径**。因此特化路径携带的旧子任务几何不会在创建之后被同一个通用转换步骤立刻无条件覆盖；其它失效、对象池复用及后续重建路径仍存在。不能把这解读成“旧几何永久冻结”或“必然造成交叉”。

## 六、离线反例、限制及后续最小修复定位

新增的合成控制流模型 `symbolic_routes()` 分别覆盖无大任务引用、存在旧子任务、旧子任务为空、已有路线节点以及 B 模式不成立的情况。它**不是** WH3 帧模拟，只用来阻断“所有状态都选择同一构造器”的错误假设；18 个测试均通过，含错误 EXE 拒绝及原始 EXE 审计。

**已证明的静态关键边**：`shortTask flag` → 辅助任务是否持有大任务引用 → **真实安装的 B 族对象** → 两种路线节点构造器 → 旧子任务参考几何 → 初始 `node+0x70`，并受节点有效位/后续状态限制。

**未证明**：某次玩家 Shift 连续折返确实选择 B 族；这一 B 节点是当前 `record[i]` 的直接或唯一生成源；同一节点的几何代际如何对应每个成员 motor goal；原生目标分配导致的真实碰撞因果。因此仍不授权 gameplay patch。

**下一段直接检查**：`node+0x70` 的真实消费者和有效性失效条件 `0x030DEA20`，是否在同一大任务 `state=1` 转换后将旧节点/新节点映射至群组目标生成 `0x030D5490`，并确认成员目标身份。禁止默认清 `task+0x158`、跳过旧方向投影、任意交换成员索引或强制瞬时转向。不要再要求玩家证明已经实测成立的挤压。
