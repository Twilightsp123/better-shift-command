# N1 / WH3 9.0.3 — 首次用户日志中的真实目标反向交接（2026-10-12）

**证据等级：原始用户游戏 JSONL 中确实发生的 motor goal 修改和成员位置采样；命令来源 RMB/Shift 未记录。** 原始 EXE SHA256 固定为 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`。本报告匿名化成员，不公开用户运行时地址、原始日志或 EXE。

## 不应继续忽略的真实观察

上一轮 157 条真实游戏记录不只是 28 次延迟成员包，还包含同一群组**两名成员在同一个 group Tick 内几乎同步完成大角度 motor 目标反转**：

| 指标 | 真实观察 |
|---|---|
| 本机群组 Tick | `1584` |
| 目标反转成员 | 2 名（本次只采到两名，不能推广到全兵牌） |
| 两次不同成员实际 `GOAL_COMMIT_PRE` 间隔 | **1 毫秒** |
| 成员 S1 旧/新位移向量 cosine | **-0.982373** |
| 成员 S2 旧/新位移向量 cosine | **-0.998467** |
| S1 开始出现向旧目标反方向移动的采样 | group Tick `1592→1593` |
| S2 最后仍朝旧前进方向有净位移的采样 | group Tick `1595` |

这些是从 `GOAL_COMMIT_PRE` 的目标前 12 字节 float32 XYZ 与 `member+0x88/+0x90` 当前 X/Z 直接计算，非离线伪造例子。两名成员确实是相同组的采样，**但没有玩家命令的身份标记，所以不能声称这是 Shift 折返**。首次目标写入不是持续一段很长时间的不同步：这两个采样成员的目标切换分别于相同 Tick 1584、相距约 1ms 提交。随后运动位置在多个 Tick 内继续原先方向，是物理/动作渐进转向的可能表现（采样仅来自目标写入事件，不能声称每帧完整速度积分）。

## 比旧猜想更强的时间证据

成员 S1 的 26 次延迟目标包，group Tick 为 `1300,1311,1322,...,1575`，**25/25 个连续间隔均为 11 Tick**；S2 的两次为 `1584,1595`，相隔 11 Tick。S1 在同一段时间内收到的目标相对于成员实际位置，水平前视距离**中位约 9.0003 游戏坐标单位**。

已确认的另一群组原生重复发送任务 `0x03ADD608`，其 `0x03282E48` 原始机器码读取 `group+0x98`、全局速率 100、浮点 `0.001`，条件为 `groupTick*100*0.001 > previous_tick_scale+1.0`。这与观察的 11 Tick 周期高度吻合。**周期一致和五字段 packet 指纹仍不能替代 sender 真实 caller RVA／task 指针证据。** 不能宣称这就是历史现场执行的唯一发送任务。

## 对修复方向的影响

对这两名成员，**并非观察到一名长期保持旧目标、另一名早已换新目标**；反而是两者的新 motor 目标几乎同时反向，但至少 S1 的运动位移有多 Tick 转向过渡。这提醒后续不要只根据“旧 motor 数据在内存里”修改全局交接门槛，而应区分：

- 真正过期 motor 目标仍被原生动作读取；
- CA 合法渐进转向的成员惯性/局部转向阶段；
- 形成队列路段时不同成员目标几何引起的相向路线交叉。

与普通 RMB 对照的真实命令/群组身份**缺失**，不能做原生修复因果判断。特别是用户已证明 Shift 挤压，无需再重新证明缺陷存在。

## 一次实机采集的合格准备标准

新单次工具必须（a）原始 EXE SHA 和 13 条确切 x64 指令边界守卫，（b）明确区分 A/B/改包类三处 member 虚调用返回 RVA，不能复用 `+0x368` 的不同对象混淆，（c）记录同组逐名目标反转和之后多 Tick 的位置，（d）在老 Frida `session.detach()` 卡死时由独立 Python 监督者强制限制退出耗时，（e）自动给出保守分析，不把“匹配构造器指纹”当作已执行对应 Shift。

所有这些均需先在原始 EXE 离线 + JS mock + Python 合成/退出超时测试通过；即使通过，**Windows 游戏附加本身仍只能通过一次真实测试验证**。本报告和分析不授权 Native Patch。
