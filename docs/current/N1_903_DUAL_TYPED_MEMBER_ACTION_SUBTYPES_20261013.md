# N1 / 2026-10-13 / 型别确认的同成员两种动作子类及真正 motor 提交分叉

**此结果覆盖上一轮不严谨的“0x0306A8C0 自动接续 0x032599C8”的拼接。** 固定原始 EXE SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`；本地独立 PE/unwind/objdump 检查 **21 个 opcode、7 个 E8/E9 直接控制流目标、6 个 typed vtable 槽、2 个 RIP LEA vtable 安装** PASS，原始游戏 EXE 未修改。

## 相同一名成员，两个不同虚函数安装不同动作对象，但目标存储位置相同

此前已静态识别两张成员 vtable `0x038FD658`、`0x03910500` 的接收器 `+0x368=0x0306B9F0`。本轮进一步确认相同两张真实成员 vtable 同时提供两种安装方法：

| 同一成员的虚方法 | 原生实现 / 机器码 | 在同一 `member+0x330` 构造 | 子类 vtable / `+0x08` 方法 |
|---|---|---|---|
| `+0x580` | `0x0306A990` | `0x03249350` | `0x03913808` / `0x032599C8` |
| `+0x5B8` | `0x0306A8C0` | `0x03248EC8` | `0x03ADAA08` / `0x03259950` |

虚槽精确证据：
`0x038FDBD8 = 0x0306A990`,
`0x038FDC10 = 0x0306A8C0`,
`0x03910A80 = 0x0306A990`,
`0x03910AB8 = 0x0306A8C0`。
二者安装器分别在 `0x0306A99A`、`0x0306A8CA` 执行相同
`lea rbx,[rcx+0x328]`，后分别于 `0x0306A9AC`、
`0x0306A8DC` 执行 `lea rcx,[rbx+8]`，所以动作类对象均占用
**`member+0x330`**。这是同一成员对象上会因不同原生命令/任务条件
而安装不同子类的真实代码能力，不代表历史玩家操作已选中其中任何一类。

## 与最终 motor 提交的区别：只有已证明的 A 子类路径不能反过来算作 B 子类

**A 类型 `+0x580`** 有至少三个带原生结构的调用点：
`0x02F79C3D`、`0x02F79D6E`、
`0x02F7A116`，取成员 vtable+0x580，将不同命令记录转为对象。
安装器 `0x0306A990` 的直接 E8 指向 `0x03249350`，
创建带虚表 `0x03913808` 的动作类；
其 `+0x08=0x032599C8` 存在
`0x03259C55 CALL 0x0306EF1C`，
原生 `0x0306EF96 JMP 0x0311954C`，
而 `0x0311963A` 正是以前 Windows Frida 真实采集到的
`member+0x1E0` motor goal 更新站点。**该调用并非无条件，仍有内部谓词。**

**B 类型 `+0x5B8`** 在上一轮
`0x03117E8C` 的条件发包 `0x03117EF7` 等位置命中；
安装器 `0x0306A8C0` 的直接 E8 指向 `0x03248EC8`，
创建带虚表 `0x03ADAA08` 的动作类；
此类 `+0x08=0x03259950`，只是在本函数里
`add rcx,0xC0; jmp 0x0181CC98`，**不是 A 类型的 `0x032599C8`**。
不能把 `+0x5B8` 安装与 `+0x580` 动作处理函数拼成
一条静态已经打通的单一 MOVE→motor 写入链；
B 类型其它更新/派发消费者仍可间接触及 motor，不能排除。

这也提示：之前计划只修改 `nextSubtask` 四个 float
存在遗漏——真实成员在**同一个动作槽**可能选择不同原生子类，
相同几何值未必走同一个 tick/update/目标写入分支。

## 与用户 BSC 目标有关的严格证据界限

**已实证：** RMB／Shift 在原生命令层有队列 replace/append；
后继 MOVE 可条件复用大任务并条件用旧 subtask 投影；
同类成员有两种不同动作安装接口并共享同一动作槽，
它们的动作 vtable tick 及至少一条 motor 目标下发路径不同。

**仍未实证：** RMB 必选 +0x580 或 Shift 必选 +0x5B8，
在用户真实 Shift 后继路段确实发生的子类切换、
原始 `task+0x160` 的 nextSubtask 与
`0x03117D44` 的某个具体 RDX 是同一实例、
哪种子类/几何关系导致兵牌内相向路线交叉。
目前是结构类型/原生调用的真实证明，不是挤压因果。

下一阶段只需要继续静态追
`+0x580` 的三处真实原生调用者对象、
`+0x5B8` 的任务类型与队列槽位引用、构造新/旧
`member+0x330` 动作子类时的触发门槛。
如果它们可以通过单个 MOVE task/order 关联，才决定是否必须一次极短
实例身份取证；**现在不要求玩家实机测试，不制作 Native Patch。**

## 2026-10-13 下一轮深入：同一成员+0x348 定时任务的动作模式源与第三动作子类

**当前优先独立研究报告：**
`docs/current/N1_903_MEMBER_TIMER_MODE_ORIGIN_THIRD_ACTION_20261013.md`；
脚本 `maintenance_tools/native_shift_re/audit_member_timer_mode_lineage.py`；
测试 `tests/test_native_shift_re_member_timer_mode_lineage.py`。

已用 SHA256 精确匹配的原始 EXE + objdump 验证
**46/46 指令字节和起点、10/10 E8 调用边、18/18 typed vtable 槽**；
不连接游戏，不修改 EXE。该脚本的 CI 合约测试 PASS，但公有 CI 不含 EXE。

**真正的同对象关系：** 两张以前已经确认的成员虚表
`0x038FD658`、`0x03910500`，除 `+0x368=0x0306B9F0`
接收器，`+0x580=0x0306A990` 和
`+0x5B8=0x0306A8C0` 安装器外，
还同时有 `+0x348=0x0306B510`。
这一接口在成员 `+0x4A8` 创建
`vtable 0x03906C88` 延迟定时任务。
此 vtable 的 `+0x08=0x02F7301C` 和
`+0x10=0x02F83868` 均依据原生群组计数器/定时门槛，
有条件调用 `0x02F79BB8`。

**动作模式真实来源：** `0x032638C4` 群组描述符生成器
在 `0x032638D7` 将 `descriptor+0x02=0`；
`0x02F5F1E8` 构造器于 `0x02F5F207` 对
`task+0x40` 调用 `0x02D99E58`，该函数
`0x02D99E64/68` 把 `descriptor+0x02` 拷贝到
`task+0x42`。随后 `0x02F79BCD` 比较该字节：
**非零 → `member vtable+0x580`，
零 → `member vtable+0x4B0`**。
`0x032774B0/C0`、`0x03277B6E/80`、
`0x0327BD0B/29` 都出现生成描述符并调用
成员 `+0x348` 的本地路径；仅能确定生成时初始值，
不排除其他阶段会修改模式字节。
另一处理路径 `0x02F79CC4` 还可调用成员 `+0x5F0`。

**第三类原生动作：** `+0x4B0=0x03069844` 先检查
成员 `+0x324`、`+0x5C0`、
`+0x4A8` 的当前延迟任务及 `+0x330` 动作；
符合条件时 `0x03069910` 清理动作，再于
`0x03069924` 调用 `0x0304E5D4` 构造
**vtable `0x03ACD208` / `+8=0x0307C388`**。
与 `+0x580` 安装的 `0x03913808`、
`+0x5B8` 安装的 `0x03ADAA08` 是**三种不同子类**。
新的 `+0x4B0` 构造器，在目标对象非空时计算
`targetXZ - memberXZ` 并写 `action+0xE0/+0xE4`；
其 Tick 的某些分支写 `member+0x270`、
清 `member+0xB11` bit 0x20，不能把这些字段当可随意修改的补丁参数。

**重要研究纠错**：`+0x580` 不等于普通 RMB 专属，
`+0x5B8` 不等于 Shift 专属，
且默认模式字节为零的已识别分支反而可能选择 `+0x4B0`。
此前用“两类动作对应两种按键”的解释已失效。
当前没有玩家 RMB/Shift 的确切 order/task 对象链，也没有
动作子类选择造成逐名士兵挤压的因果证据。
下一步静态优先枚举描述符 `+0x02` 的所有写入和
`+0x348` 的调用者任务类型；**不要求玩家重复游戏测试，
不做 Native Patch，不修改 main。**
