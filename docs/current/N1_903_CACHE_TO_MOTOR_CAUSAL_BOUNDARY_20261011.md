# BSC 9.0.3 — RMB/Shift 旧空间关联到实际运动目标：原生机器码闭环

**调查日期：2026-10-11。结论等级：STATIC 真实 EXE PASS、OFFLINE 分支模型 PASS；V3 动态分支归因 UNKNOWN。**

原始用户 EXE SHA256：`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，PE ImageBase `0x140000000`，文中一律 RVA。保留 CA 原生渐进转向、命令队列及运动/物理；本包不 Hook、安装或改动 EXE。

## 问题一：`member+0x930` 到底影响运动目标吗？——是，静态原生数据流已闭环

**目标包接收后：** 原生 `0x0306B9F0` 对目标包 flag `0x26` 的普通成员处理，经 `0x03073224` 的目标处理，尾跳到 `0x03056ED4`。该函数将成员 `+0x910` 的空间数据重算，再按成员自己的环境、指针和几何条件决定 `member+0x930` 的旧空间关联是保留、刷新还是清空。`+0x930` 不等于玩家路点序号，不能简单置空。

**路径 A：成员个体动作。** 原生动作虚表 `0x03ACD468` 的 `+0x130` 是 `0x0308393C`。它在 `0x03083AD2` 读取同一成员 `+0x930`，`0x03083AFE` 经 `0x03102444` 检查新旧空间区域/几何兼容性；不兼容时 `0x03083B53 → 0x03071E04`，兼容时可走 `0x03083BB9 → 0x0306EF1C`。这说明“成员收到新高层目标”等于“每名成员立即以同一方式重建物理目标”是错误的。动作实例需通过原生 vtable 和状态守卫激活，不能断言它在 V3 每个成员都活动。

**路径 B：原生群组空间参考。** `0x0308279C → 0x030880E4 → 0x03088618` 已验证。`0x03088618` 在特定动作阶段（`action+0xE8=0`、`action+0x90=1`、成员状态、场景引用均符合条件）读取 `action+0x98` 指向对象的 `+0x32F8` 原生群组、再访问 `group+0xC10` 空间参考。它把该参考和成员 `+0x910/+0x930` 交给 `0x030522FC → 0x03102444` 判断，兼容则保留当前成员运动指令；不兼容则 `0x0308872E → 0x03071E04` 重建该成员目标，并更新 `action+0xE8`。另一路 `action+0xE8!=0` 的条件会检查当前 `member+0x710==4` 等，不等同于同一逻辑。**这些行为是有条件的，不是所有成员每帧都会跳转。**

**新目标真的进入运动处理吗？——是，独立消费端闭环。** `0x03071E04`：复制目标 payload 到 `member+0x7F8/+0x818`，设置 `member+0x710=1`，立即 `E8 0x03071E86→0x03071F20`。后者在 `0x030723E6–0x03072432` 变换 `member+0x7F8` 新目标、读取成员当前 X/Z (`+0x88/+0x90`)、计算位移长度 (`sqrtss`)，分支调用 `0x0311954C` 和相关运动处理。`0x0311954C` 在 `0x0311963A` 将原生目标写入 `member+0x1E0`，在 `0x03119687` 调用 `0x03102CA4` 更新其本机运动子系统。这**不是**先前已排除的只写 `+0xE0` 后验差分率。

**两个动作对象不是同一个。** `0x03069844→0x0304E5D4` 为其中一种动作安装虚表 `0x03ACD208`，`+0x10→0x0308279C`；`0x03069B10` 安装虚表 `0x03ACD468`，其 `+0x10→0x03083120`，再虚分发 `+0x130→0x0308393C`。两条路线可能覆盖不同成员情形，不能把任一类推广到全部60兵模。

## 问题二：已经证明 35–43 秒 V3 挤压由此导致吗？——没有，现有数据无法倒推出原生分支

以前真实 V3 游戏采样确认故障本身：该兵牌36名采样成员，Shift 渐进折返35–43 秒 29/40帧最近成员距离小于1；有近距离反向运动。**但先前 V3 采集器没有在每帧记录 `member+0x930/+0x710`、动作对象虚表，也没 Hook `0x0308393C` 或 `0x03088618` 的条件分支。** 因此即使机器码证明“旧关联影响新目标”，也不能根据旧 V3 位置轨迹唯一判定哪名士兵走了保留/重建分支。V3 旧 `0x030D5490` hook 零命中意味着其来源尚未被动态认证。把“可以解释冲突的可能性”升级成“V3 已确认根因”会造假。

**离线可确定的反例与可竞争机制**：在相同群组新参考下，成员A的旧空间关联被判兼容，允许保留当前局部目标；成员B的旧关联不兼容，原生代码重建新的 `+0x7F8/+0x818` 目标、将 `+0x710` 置1。这样可以造成阶段差异，但这是**原生控制分支的条件反例**，不是反向位移或实机碰撞的直接证据。还需区分正常 RMB 的替换初始化与 Shift 的共享续接有无令该分支在折返时更频繁发生。

**唯一动态归因阻断点**：V3 没有记录足以区分这条原生分支的事件/字段；从原始 EXE 静态文件，不能证明历史某次游戏中的分支被执行。此处不是缺少 Ghidra，也不是需要重做症状证明。按用户要求本轮 **不请求新实机测试**，也不交可能影响原生姿态/战斗的盲 Hook。

## 交付文件和运行

- `src/audit_cache_to_motor.py`：严格 SHA、56 条机器指令、18 条直接 E8 调用、3 个具体动作虚表槽；独立原始 PE 只读校验器。
- `src/audit_903_queued_member_activation.py`：复用的上一轮 pinned PE / 任务链审计源，保证解压后可以直接运行。
- `tests/test_cache_to_motor.py`：离线条件分支、错版本拒绝、字节不修改与原始 EXE 校验回归。
- `evidence/exact_binary.json`：原始 EXE 核验输出，明确 `branch_taken: UNKNOWN`。
- `asm/`：由 `objdump` 从原始 EXE 提取的有限原生函数反汇编，**不含游戏 EXE**。
- `SHA256SUMS.txt`：压缩包内部文件的 SHA256。

**修复决策**：明确确认了“每名成员的旧空间关联参与新运动目标是否重建”，但 V3 具体分支活动证据尚未提供。在证明其为挤压因果之前，不能强制清 `+0x930`，不能取消 CA 状态继承，也不能让所有成员强制进入 `+0x710=1`，不能发布 BSC 修复版。
