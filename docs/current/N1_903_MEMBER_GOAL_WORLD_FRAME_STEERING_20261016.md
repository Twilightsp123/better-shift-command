# BSC N1 · 第22轮 · 目标局部坐标 → 世界坐标参考框架 → 原生成员运动（2026-10-16）

## 本轮实际突破

**上轮把 `member+0x1E0` 称为「最终 motor goal」并未包括其使用时的坐标参考解析。**

固定用户原始 `Warhammer3.exe` SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，ImageBase `0x140000000`，所有地址为 RVA。独立只读原始二进制审计：**98/98 原码字节和 GNU objdump 真正指令起点、7/7 E8 直接调用、6/6 JCC 目标、15/15 本地单测 PASS**（含实际原始 EXE、错误 SHA 与 `python -O` 检验）。

新证明的是一个真正的**字段所有者／消费者／世界坐标转换闭环**：

`0x03071F20` 的两条受条件保护的出口 `0x030720D1/E3` 和 `0x030723CC/D9`，把同一个成员 `member+0x838` 的 24 字节路线目标记录送给 `0x0311954C`。该目标提交器在允许写入时保存：`member+0x1E0` 起始的局部三维目标及相关朝向、`member+0x1F0` 中的引用字段。之前的去重检查同样比较的是这个引用字段，**它不仅用于判别旧目标是否相同**。

成员主 Tick `0x03081EB4` 的有条件路径：

`0x030822F9 CALL 0x03054B84`
→ 运动函数特定分支 `0x0305501D LEA RCX,[member+0x1E0]`
→ `0x03055029 CALL 0x0311CED4`
→ 返回世界目标三维坐标
→ `0x03055032..0x03055060` 分别减去成员当前位置 `member+0x88/+0x8C/+0x90`
→ 归一化、配合 `member+0x1C0` 的速度/距离条件参与运动判定。

`0x0311CED4` 并非始终直接取 `member+0x1E0`：
- 如果 `[member+0x1F0]==NULL`：在 `0x0311CEEF..0x0311CEFF` 把原先保存的 xyz 直接复制到结果；
- 若非 NULL：`0x0311CEE4` 将引用偏移 `+0x18` 作为转换数据起点，`0x0311CEE8 CALL 0x02F38640`，由原本保存的 xyz 和该引用对象的**3×3 线性项 + 三维平移项**生成**世界 xyz**。

从 `0x02F38640` 真正的 SSE 机器码逐分量推出：

`worldX = T.x + M00*x + M01*y + M02*z`

`worldY = T.y + M10*x + M11*y + M12*z`

`worldZ = T.z + M20*x + M21*y + M22*z`

其中 `T` 存在传入矩阵对象 `+0x00/+0x04/+0x08`；`M` 在 `+0x20..+0x40`。这不是推测有 transform，而是三条结果写入点 `0x02F386B4/B8/C5/CE` 与各项 `mulss/addss` 的实际指令链。

## 本轮离线反例及因果限制

合成反例保留 **同一个** 局部目标 `(2,0,0)`：

| 引用几何 | 解析后的世界目标 |
|---|---|
| 平移 0、单位旋转 | `(2,0,0)` |
| 平移 0、水平180°翻转 | `(-2,0,0)` |

因此，对同一兵牌两个相邻士兵，**只比 `member+0x1E0` 存储的局部目标是否相同，不能断言实际 steering 的世界目标相同**。如果其 `member+0x1F0` 引用不同，或其引用对象上的矩阵被刷新，解析出的世界目标可以改变而局部 xyz 不变。这只是数学与静态代码的可能性证明；**没有证据证明用户的 Shift 折返真的发生了相反的 reference frame**，更没有证明这是 CA 运动混乱根因。

成员 Tick 在该运动计算之后还调用 `0x03082301 → 0x03088808`。后者只有在状态 `member+0x26C` 为 `0x78/0x79`、`member+0x30/+0x2E8` 有效、其它条件及随机阈值通过时，`0x03088A49` 才调用另一成员目标写入器 `0x03060D74`。它在 `0x03060E5A/66` 直接写 `member+0x1E0` 的16字节及 `+0x1F0` 的8字节。**这证明 `0x0311954C` 不是唯一写者**，但没有证据显示这个少见状态发生于普通 queued Shift MOVE，不把随机特殊路径直接当根因。

同样，`0x03054B84` 是**有条件的运动分支**，非所有士兵、所有动作必执行；目前追到世界目标参与移动方向/速度阈值，但尚未将它与最终的避障修正输出完全连接。

## 因果搜索决定：下一步只做这一个判断

若需进一步排除/定位原生 Shift 折返的**首次错误方向**，对同一 queued MOVE 槽位、同一 UnitRoot、同一 group 构造代际、两个相邻士兵，必须在同一个 Tick 的运动消费时依次比较：

1. `member+0x838` 上游路线目标记录；
2. `member+0x1E0` 当前局部 xyz 和 `member+0x1F0` 当前引用对象；
3. 引用对象（若非空）的 `+0x18` 参考几何**实际解析后的世界 xyz**；
4. 成员当前位置 `+0x88/+0x8C/+0x90`、当前运动 `+0xE0/+0xE8` 和速度输入 `+0x1C0`；
5. 如果**实际世界目标一致**、成员仍相向挤压，才应优先追逐帧 steering/avoidance 和碰撞修正。若世界目标**已经交叉**，应先追局部坐标/参考框架的所有者与生存期，而不是动共享的队列和目标提交函数。

这是搜索条件与必要观测字段，不是要求玩家现在再做实机测试。先用当前固定 EXE 和已有离线证据检查安全性/实例绑定，禁用过度收集和玩家指针上传。
