## A. 关键机制 1：前方预瞄点及失路回退（单士兵；不是 Shift 默认算法）

来自 Derpy `script/derpy_tp/move.lua`，直接逐行核对：

- `move.lua:4-14`：整体单位与单兵分别有预瞄逻辑；预瞄 15 m，整队距离目标 6 m 时刷新，方向差 12° 触发刷新，整体 `unitcontroller` 命令间隔不少于 0.5 s。
- `move.lua:64-110`：单兵将目标方向与当前朝向作最短圆周差，用 `turn_rate × real_dt` 限制单次改变。默认 `move_turn_rate = 360` 度/秒，见 `settings.lua:40`。沿限制后的实际朝向在前方 15 m 给出原生 walk 目标，而不是强行改人物坐标。
- `move.lua:93-109`：单兵当前 walk 已因目标不可达而结束时，下一次预瞄距离减半，最短 1.5 m；至少每 0.5 s 重试，并在 2 s 后恢复远预瞄。
- 作者代码注释记录了马匹 3 m 和 15 m 前方点对应的速度明显不同，例如约 1.25 m/s 和 7.35 m/s（当时记录了不同单位的测量）；该测量的原始游戏日志**未随 PFH5 发布**，应当只归类为作者自述测试，而非 BSC 新游戏证据。

**应用判断**：证明“原生步行动作对前方目标距离敏感”是强候选，不证明 CA Shift 的路点预瞄也是这些常量。BSC 可静态检查 queued MOVE 路线端点进入成员 action 时有没有接近脚下的过短目标或过近距离换段；不能在所有成员身上每 0.5 秒重新发原生 MOVE，否则是重新驱动 Shift 并可能造成新的停顿。

## B. 关键机制 2：原生单兵 walk_b 目标更新与缓存失效

来自 `platform.lua` 的实际原生代码洞（非它的文字说明）：

- 从 `member` Tick 入口 `0x03086F04` 接管**唯一指定的成员**，其它成员直接执行原入口。代码以 `CMP RCX,[mailbox+0]` 确认对象身份。
- 工作线程读取 mailbox 的 `walk` 请求；对 `member+0x330` 检测是否为 `walk_b` 的原生虚表 `0x03AE2400`。如果不是同一原生动作，则直接调用 CA `walk_start=0x0306F954` 构造新的 walk；没有伪造虚表。
- **如果已经是 walk_b**，它更新内嵌动作的 `member+0x368/+0x370` 目标、`+0x390/+0x394` 速度和步态、`+0x398` 目标朝向（条件性）。用差异标志判断是否确实发生改变；改变时原生 cave 才写 `member+0x3C0=0`。换算到 action 对象 `member+0x328`，此字段为 `action+0x98`。
- 这个后者的精确定义仍应由 CA 原始 `walk_b` 下游读取者确认，Derpy 注释称为 `cached destination`；本轮证实它**确有动作类型守卫和有条件零写指令**，但没有证明 B2 packet Action 的相同偏移语义。
- 实际 walk_b 虚表 `0x03AE2400 +0x10 = 0x03262850`，CA 普通 walk_a 虚表 `0x03919350 +0x10 = 0x03264B70`，B2 普通 packet action `0x03919B28 +0x10 = 0x03261688`，三种实现不同；上述映射在完整 SHA 游戏 EXE 的 `.rdata` 中重新核验。
- 注意两个“+0x368”是完全不同的用法：这里是 **member 字段 `member+0x368`**，BSC 以往的 **member 虚表偏移 `vtable+0x368`** 是另一个概念，不能混淆。

**最值得追查的新候选**：CA 原生 Shift 后继 MOVE 在换段时，若成员新路线/世界目标已经装入，但其**实际所处的 CA action 子类型**还保有不相容的缓存/路径状态，可能损害转弯连续性。必须逐类型核对 `walk_a`、B2 packet、以及实际 Shift member action 的缓存读写及换段失效条件。不得照搬 Derpy 对 walk_b 的 `member+0x3C0=0` 为全局补丁。

## C. 关键机制 3：同兵牌的被动运动和主动动作可以冲突

Derpy `platform.lua:537-558` 的注释是作者实机观察的直接记录：整队 MOVE／攻击任务可以使其中一个成员在没有独立移动输入时仍发生位移；即使表面站立，也可能被队伍运动“带着走”。作者还记录部分静止动作可出现远大于受控站立状态的位移。

原生 code cave `guard` 请求只针对 `walk_a / move_a / move_b / melee` 四种可识别的**整队原生命令类型**调用 CA 原生 `walk_stop=0x0306EDD4`，不会清理它自己创建的 `walk_b`，也不主动破坏 idle、击飞、摔倒和爬起等其它行动。这是有目的的**动作所有者分类**，不是简单设置速度零。

**对 BSC 意义**：不能仅看 `member+0x1E0` 目标或 `+0x13C` 积分，就推断全部成员位移来源；如果 Group 阵型调整和个体 action 的控制输入在折返交接时相互干涉，观察单兵的“目标方向正确”仍可能漏掉问题。但 Derpy 的 guard 是通过隔离一个士兵实现第三人称控制；直接对整支部队套用会破坏 CA 原生队形。

## D. 第三方实现的限制与不应复制的做法

- 单兵 `P.steer` 直接写 `member+0x1E0/+0x1E8` 和 `+0x194/+0x198`，这是 Derpy 在自有单兵任务中使用的特定操控手段；BSC 已证 `member+0x1F0` 是条件性参考框架，不能保证这些坐标对所有 Shift action 都属于世界坐标，不应照搬。
- 整队 `goto_location` 使用 Lua unitcontroller 替换指令，绝非 CA queued Shift 路线连续执行机制；其发令节流只是第三人称体验策略。不能改成“每半秒替换一次 Shift MOVE”。
- mailbox 请求位用 `xchg` 在工作线程读取，但 Lua 写入的目标、速度和朝向字段并非一次原子快照。它是可参考的具体工程实现，却不是多字段并发一致性的证明。
- 代码洞安装在普通 member Tick，可能与 BSC 原生观测冲突；不可与 vanilla 同开做严格对照。
- Derpy 的上述“被整队带走”是源码中的作者注释及实验结论，而非本轮重现或过去 V3 的完整原始轨迹。

## E. 下一步只有两条值得实际逆向的分支

1. **行动缓存代际**：针对新版 `0x03919350 walk_a → 0x03264B70`、`0x03919B28 B2 → 0x03261688` 的 CA 原生命令，识别各自读写的 *实际类型化路线缓存*、失效标志和换段条件；与 Derpy 仅在 `walk_b=0x03AE2400` 清理 `member+0x3C0` 的条件作排除式对照。没有缓存数据同实例错误证据，停止此方向。
2. **目标预瞄／整队运动干预**：检查 queued MOVE 后继路段触发时，是否有成员被迫接收极近目标并触发减速、同时 Group 仍在重排；核对 CA 原生路段激活与成员运动状态，而不是仿照 Derpy Lua 写目标或添加新任务队列。

## F. 本轮证据及验证

- 原始包 `.pack` 提取代码，使用防路径穿越 PFH5 解析器；仅保存**新编写的分析工具**，不发布完整 Derpy 源码或原 DLL。
- 通过实际 `Warhammer3.exe` 完整 SHA/PE 时间戳、普通成员 Tick 入口 7 字节、三组原生虚表各三个槽、walk_b +0x10 的实际状态/结束字段机器码守卫。
- Derpy code cave 410 字节，11 个关键机器码指纹已经从 `platform.lua` 的源数组静态核对；包括特定成员识别、XCHG 事件标志、动作类型选择、目标字段变化和 `member+0x3C0` 条件性零写。
- 独立离线 14 项 unittest 使用实际 Derpy ZIP + 当前游戏 EXE ZIP PASS；缺私有档案时 3 项不依赖文件的单测 PASS / 1 套私有档案测试 SKIP。包含恶意 PFH5 名称、错误 SHA、篡改目标缓存指令和预瞄常量漂移的负例。
- **没有本轮游戏内运行，没有证明 Shift root cause，gameplay_patch_authorized=false。**

## G. 补充：原生引擎自己确实按目标／路径状态读取这个缓存字段

二次专项只读审计已从 **真实新版 EXE** 验证：

- `walk_b` 动作 `virtual+0x10=0x03262850` 在 `0x032628D9` 通过直接 E8 进入 `0x0325AE78`，且 RCX 是传入的 **walk_b 动作对象**，不是其它组件。
- `0x0325B05A` 读取 `action+0x98`，`0x0325B060/+0x68` 测试 bit1/bit0。前置条件还包括动作 `+0x92` 标志及所属 member 的路径状态 `+0x710`。
- `0x0325B108/+0x114` 修改并保存动作 `+0x98` 状态，`0x0325B1EF` 置 bit0，`0x0325B1F6` 再测试 bit0，沿条件路径继续运动/路线处理。
- 这 7 个具体原生字节位置及 `0x032628D9→0x0325AE78` 直接调用已经在固定 SHA 上单独纳入审计器。它证明 `member+0x3C0 == action+0x98` 对 `walk_b` 来说是**真实的原生路径状态位字段**，比只依赖 Derpy 注释的“cached destination”更强。

**仍不能**把这项成功归因于修复 Shift 队列：原生 queued MOVE 成员 action 可能是另一类型，其虚方法和缓存布局还要重新核对。更新后的完整本地独立验证为 **14/14 PASS**；不存在新版玩家 Shift 实际命中或 gameplay 补丁。
