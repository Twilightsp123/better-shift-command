## 1. 真正新增：普通成员具有带标志的内嵌待处理目标记录

原生普通成员构造器 `0x03052BA8` 经过 `0x0305306F LEA RCX,[RBX+0x8D8] → 0x03053128 CALL 0x03051D98` 初始化内嵌记录。构造器把记录首个 WORD 清零，并初始化内部位置记录。

成员主 Tick `0x03086F04` 保存 `RDI=member` 后：

```text
03086FD2  CMP BYTE PTR [RDI+0x8D8],0
03086FD9  JE 0308706F                         ; 没有待处理记录，则跳过本通道
03086FE5  LEA R8,[RDI+0x8DC]                 ; 运动向量临时来源
03086FF1  LEA RDX,[RDI+0x8E8]                ; 带关联记录的目标来源
03087005  MOV RCX,RDI                         ; 当前同一个 member
0308700C  MOV BYTE PTR [RDI+0x8D8],0        ; 在发送之前清待处理标记
03087013  CALL 03065DB8
03087018  MOV WORD PTR [RDI+0x8D8],0        ; 再次确保标志已清理
03087034  MOVSD [RDI+0x8DC],zero             ; 后续清理源缓冲
0308705B  MOVUPS [RDI+0x8E8],zero            ; 后续清理目标缓冲
```

**关键限定：** “先清待处理标记、后调用消费者”是这一条已验证原生分支里的指令次序；并不证明跨线程原子性或其它更新入口不会读写同一成员。

## 2. 已闭合：待处理记录怎样变成成员当前目标与待应用位移

`0x03065DB8` 在入口保存 `RDI=RDX`（待处理目标地址）、`RBP=R8`（待处理运动向量地址）、`RBX=RCX`（当前 member）。随后：

```text
03065E8A  MOVUPS XMM0,[RDI]
03065E9E  MOVUPS [RBX+0x1E0],XMM0
03065EA5  MOVSD XMM1,[RDI+0x10]
03065EAA  MOVSD [RBX+0x1F0],XMM1
03065E98  MOV RDX,RBP
03065E9B  MOV RCX,RBX
03065EB2  CALL 03154974
```

`0x03154974` 的输入 `RDX` 被保存为 `R10`，`RCX=member` 被保存为 `RDI`。它先调用无 unwind 叶函数 `0x03169594` 清除成员在某些列表中的引用，再从刚才传入的向量读取三个分量：

- 把原向量写入 `member+0xE0/+0xE8`；
- 以原生常量 `100` 与约 `0.001` 对向量作比例换算，写入待应用增量 `member+0x13C/+0x140/+0x144`；
- 把 `member+0x14C/+0x150` 写成 PE 镜像初始化的 `0.0`；
- 设置 `member+0x108 bit0x02`，并有条件调用该成员的 `virtual+0x128`。

重要 Win64 ABI 校验：`RCX`、`R10`、`R11` 都属于 volatile。**不能仅看调用者**就断言它们在 `0x03169594` 之后仍有效。本轮完整检查该无 unwind 叶函数没有嵌套 CALL，也没有写这三个寄存器，才允许沿用它们的真实值。其内部会更新其它引用/计数，故不能把它当成完全无副作用。

### 对 R42 假说的修正

这条明确的待处理通道**不是仅覆盖目标并原样保留旧增量**。它会重新生成待应用位移并设置复杂积分分支所需的 bit0x02。若要从它解释折返挤压，必须先证明某个后继 queued MOVE 的具体成员确实触发该通道，并证明当次向量内容或消费时序不正确。

## 3. 第二种同布局路径：直接清理运动增量

另外审计了 `0x03071C84 → 0x0315FB24`：前者也会覆盖 `+0x1E0/+0x1F0` 目标；后者先把 `+0x13C/+0x140/+0x144` 清零，更新相对朝向，并把 `+0x14C/+0x150` 清零。它还依照成员 `+0x108 bit0x04` 条件触发 `virtual+0x128`。

两者对运动增量的处理**并不相同**：`0x03154974` 从输入向量计算新增量；`0x0315FB24` 清理增量。静态直接 E8 扫描确认两个 helper 的合法 E8 调用者分别只有 `0x03065EB2` 和 `0x03071CC9`。**未证明后者属于同一次 Shift MOVE，也没有证明两条入口实际互相竞争。**

## 4. 为什么暂不把 `+0x14C/+0x150` 作为主要目标来源

R42 的 `0x03146FF0` 会读取这两个浮点字段，条件性地用于修正 `+0x13C/+0x144`。本轮核对了以下**已类型化的局部写者**：

| 路径 | `+0x14C/+0x150` | 同次其它动作 |
|---|---|---|
| `0x03154974` | 均设置为镜像初始 `0.0` | 根据输入向量设置增量、bit0x02 |
| `0x0315FB24` | 均设置为 `0.0` | 清理运动增量、调整朝向 |
| `0x03146FF0` 的两个积分清理区域 | 均设置为 `0.0` | 应用/清理运动增量或运动状态 |
| R39 的特殊成员位置同步器 | 在已审计分支也清零 | 不是已证的普通步兵常规积分路径 |

**严格限制：** 这不是全 PE 所有可能的成员字段写者清单。间接别名、块复制、其它对象类型、运行时写入均未穷举。不能由此宣布这些字段在所有 Shift 更新中永远为零或复杂积分路径不可达。下一步优先追**明确可变的 `+0x13C/+0x140/+0x144` 与待处理记录生命周期**，而不是用未证明的 `+0x14C/+0x150` 速度做补丁。

## 5. 具体否定的历史假设与剩余因果断点

1. **否定本条待处理 Tick 通道会每帧无条件重发原目标。** 它有 `member+0x8D8` gate，且在调用消费者之前清标记。但其它通道/后续 Tick 仍需单独审计。
2. **否定本条通道只写世界目标、完全不触碰运动增量。** 它同时设置运动目标/增量和 bit0x02。
3. **限定“bit0x02=0 且 +0x155 bit0x04=0 会跳过直接应用”**：R42 的纯局部负证据仍然成立，但不能拿它推断每次后继 MOVE 都缺少恢复；本次新链恰恰能设置 bit0x02。
4. **目前不成立：** B2/Shift 正常后继 MOVE 必然走该待处理通道；没有真实同实例对象代际、+0x8D8 生产者与 vector/goal 内容的上游数据关联。
5. **尚无原生补丁位置：** 强制 bit2、强制清运动增量、全局跳过某个目标或取消原生状态恢复都可能伤害 RMB、Shift ATTACK、渐进转向及避障，不能实施。

## 6. 下一轮的唯一高价值问题

沿同一普通成员类型追查：**谁将 `member+0x8D8` 标记为待处理、谁填入 `member+0x8DC/+0x8E8`，它是否来自 queued MOVE 的实际 Group/route/packet 链？**

已核对的 `0x03051D98` 初始化器与 `0x03086F04` 消费器，不足以证明其生产者。由于字段可能通过 `&member+0x8D8` 的间接别名写入，不能仅靠搜索 `+0x8D8` 直接写指令就宣称没有生产者。若该记录不能与真实 Shift 后继 MOVE 连接，明确降低该猜想的优先级并转向原生成员的 steering 增量形成阶段。
