# BSC — RMB 与 Shift 底层路线差异：原始 EXE 数据流闭环

**完成日期：2026-10-11。** 用户提供的 WH3 9.0.3 标记 EXE（版本资源未再确认）SHA256：
`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`。
仅只读离线逆向，不包含也不修改游戏 EXE，不要求用户测试游戏。

## 结论：两者不是不同的士兵运动引擎，而是同一引擎接收不同的路线初始化上下文

### 普通 RMB / 非排队 MOVE：替换与首次初始化

1. `0x030323FC` 保存发令参数 `R9B`；`0x030326BE→0x02F50410` 通过此参数决定是否清旧队列。非排队请求走队列替换，排队请求保留现有项。**Shift 键输入如何形成此值没有在本轮重新证明。**
2. 同一个 MOVE 构造器 `0x030090BC` 在 `0x030090E7` 将 `MOVE+0xA0` 清零。
3. 新建的原生路线状态 `0x030EE850` 设 `state+0x20=0`、`state+0x160=0`；执行者 `0x0311DE74` 的 `state=0` 分支在 `0x0311E6F8` 进入初始路线建立。此分支调用 `0x03126B0C`，在特定原生条件下调用 `0x030DB8E8` 读取现有原生群组几何（若关联对象 `+0x3E08` 有缓存，取 `+0x3E10` 等；否则取输入对象 `+0x138` 等）。因此**存在以当前 native 几何为参考重新求解的入口**，但不应断言所有 RMB 的每个分支都必然走这一路。
4. 然后同样调用原生路线求解 `0x0311E80C`。该求解器内部又调用 `0x0310F560` 处理路线几何。

### Shift 后继 MOVE：条件续接与几何参数重基准

1. 原生队列处理 `0x0304433C` 检查前继 MOVE 的 `virtual+0x40` 与后继 MOVE 的 `virtual+0x38`。通过检查才在 `0x0304459D` 增加共享状态引用，并于 `0x030445AB` 调用后继 MOVE 的 `virtual+0x48 → 0x03040864`；否则仍用一般原生路径。
2. `0x03040864` 把同一个状态指针赋给后继 `MOVE+0xA0`，将 `state+0x20` 设为 **1**，把新的 MOVE 路线参数写到待处理块 `state+0x120/+0x130/+0x140`。这是**真实的几何参数续接**，不是简单复用空指针。
3. 后继 MOVE 进入 `0x03025D70` 时仍有一道**二次有效性检查**：校验 `state+0x25`，调用 `0x0311C634`，再比较当前原生路线标量与 `state+0xA0 - state+0xA4`；对于有限正常数值，在差异超过原生 **0.01** 时于 `0x03025E35/39` 减引用并清空 `MOVE+0xA0`。这个标量来自 MOVE 的显式 `+0x80` 或单位原生路线描述符 `root+0x270/+0x40`（`0x0301C1B4`）。**排队不等于一定继承成功**。
4. 对实际保留的共享状态，`0x0311DE74` 的 `state=1` 分支在 `0x0311E5C2–0x0311E618` 把 pending 复制到 active：
   - `+0x120/+0x130` → `+0x60/+0x70`，并再次复制到 `+0x80/+0x90`；
   - `+0x140/+0x144/+0x148` → `+0xA0/+0xA4/+0xA8`。
5. **首次/续接都会调用 `0x031086F8`** 重置路线子上下文，并进入同一个 `0x0311E80C` 求解器；`0x03108808` 会写 `state+0x160`。因此“Shift 永远带着完全不变的旧路线”也是错误解释。复用的是共享状态的对象身份和有条件的过渡上下文，原生引擎会重算内部路线。

### 最终进入成员目标和运动层

`0x03128E80` 遍历状态对象、调用 `0x0311DE74` 推进原生状态，并存在 `0x03129092→0x030FDA9C` 的路线子段构造。独立的群组成员分发 `0x030D554C` 也通过 `0x030D55F5→0x030FDA9C` 使用同一个路线子段构造函数，并在 `0x030D5603` 调用 `0x030D5490` 生成目标、按成员下发。**这证明两处复用了相同类型的原生路线段构造算法；尚未证明它们在用户 V3 那一次运行中引用同一个路线对象，也未证明每个条件分支都被执行。**

## 为什么普通 RMB 与 Shift 的运动可能不同？

两者共享 MOVE 类、路线求解函数和成员运动函数族；真正区别在：普通 MOVE 替换已有命令，以首次初始化参数进入路线求解；Shift 连续命令在满足资格和二次有效性检查时，使用前一原生状态对象，将**下一条 MOVE 参数**重基准进入同一求解器，同时原生队列可以快速预处理多个 MOVE。对多段紧凑折返，二者实际呈现的路线几何、成员目标组合不必相同。即使物理避障代码相同，也可能出现不同的成员靠近概率。

**这个结论解释了两种输入为什么可能得到不同的路线路径和运动结果，不等于已证明 V3 实际挤压由哪个具体原生 Bug 引发。** 用户 V3 记录了后续曲线路径中士兵挤压，但未采样 `MOVE+0xA0`、状态 `+0x120`、完整成员目标向量和具体 route solver 输出。不能编造“某个禁用旧状态补丁必然改善挤压”。

## 已排除的错误理解

- “普通 RMB 与 Shift 用完全不同的士兵避障器”：未发现此二选一实现，已确认核心成员运动函数族共享。
- “Shift 无条件继承并保留原来的全部几何路线”：错误，有 eligibility、0.01 对照、二次丢弃与重新求解。
- “原生队列工作入口每次意味着全体士兵到达路点”：错误，V3 已观察到多个快速 MOVE work 与随后数秒的渐进转弯。
- “所有 V3 成员 mode=0 意味着编队策略 Mode 0”：错误，`member+0x104` 是动作模式，编队策略另有选择器。
- “跳过旧状态继承就等于普通 RMB”：错误。已完成的默认关闭 DLL 是**另外一种高风险实验**，尚无游戏效果证明，不应启用作为修复。
