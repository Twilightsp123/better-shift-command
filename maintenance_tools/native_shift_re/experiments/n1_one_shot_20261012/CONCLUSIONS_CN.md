# N1 当前逆向结论与证据边界

- **已静态确认：** 原始 `0x03284B55 → 0x02F5F8DC` 构包后，`0x03284B65` 会清掉标志 `0x04`，`0x03284B75` 清除 `+0x44` 的低 32 位，`0x03284B7B` 真正调用成员 `virtual+0x368`。所以过去“包字节是 `0x02` 就绝不可能源自该构造器家族”错误。
- **已有用户真实运行证据：** 一名样本成员 26 次间隔恒为 **11 group Tick** 重新收到目标，短期目标约 **9 个坐标单位**前视；原生 `0x03ADD608` 任务的 Tick 频率计算与这一间隔高度一致，但来源仍没有返回地址证实。
- **首次实际折返的更强观察：** 同一群组两名已采样成员于 Tick `1584` 相隔约 **1 ms** 提交几乎 180° 新 motor 目标；其中一名在 Tick `1592→1593` 附近才在已有的目标写入时刻开始产生反向运动位移。另一名在 Tick `1595` 前仍有旧方向的净位移。这支持“新目标已经一致，物理/局部动作转向仍需多个 Tick”的可能机制；**原始日志未记录真实玩家指令归属，不代表已经确认是 Shift，也不能证明两名士兵当时物理挤压**。
- **因此当前不允许直接清空旧 `+0x1E0`、强制同步 `+0x568/+0x580`、修改 5 单位门槛或跳过 CA 原生状态继承。** 必须先通过本次来源身份采集区分“目标发包/旧动作读者”和“新目标已提交但逐兵物理转向滞后”。
- 本包 `original_validation.json` 是精确原始 EXE 的静态检查结果；`sanitized_existing_reversal.json` 是已上传用户 JSONL 的匿名化聚合。原始 EXE、用户运行时指针日志均**不随本包公开分发**。

- **离线测试工具状态：** 新版添加原生群组 Tick `0x02DD579C`，用其真正的 `group+0x98` 计数器连续取样，修复旧取证只能在成员目标再次写入时取样的问题。严格校验 **14** 处原始 EXE 代码 Hook 位点与另 2 条群组 Tick 对象和时钟字节守卫，Node Frida mock + Python **9/9** 离线测试通过，验证了后台 Frida 卸载挂起时保留已完成 SUMMARY 的退出路径。**Windows 真实 Frida 接入仍未实测**。
