# BSC N1：原生群组任务分叉与新增两类成员动作（2026-10-13）

## 结论：先按原生对象和条件划分任务，不按 RMB/Shift 键位猜测

在用户提供的原始战锤3 EXE
SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`
上，完整完成只读静态核验：本地独立审计 **31 个 x64 opcode／GNU objdump 指令边界、8 条真实 E8、15 个旧/新成员及任务指针表槽、2 个 RIP 相对虚表安装、2 条条件跳转全部 PASS**。另外 2 个新的子类构造器 LEA 和 2 个动作 vtable update 槽也独立核验 PASS；研究分支统一校验程序中固定了 **30 个 opcode、8 个 E8、17 个记录槽、4 个 RIP LEA**，配套回归测试 GitHub CI PASS。原始 EXE 不纳入 GitHub。

### 1. 一条被遗漏的原生群组处理函数

`0x03915930` 为一处**真实方法指针槽**，指向 `0x0327BD38`；虽然在连续函数指针区段内，**目前尚未确认该区段的确切虚表起点**，不应擅自称为 `0x03915900 +0x30`。

`0x0327BD38` 的关键两条分支：

```text
[groupTask+0x58] -> virtual+0x60
    |
    +-- 非 NULL：
    |     经过当前 member+0x5C0、已有 +0x4A8 延迟任务
    |     的其它原生条件，
    |     可能沿 0x0327BE3F -> 0x02F5F724
    |          -> 0x0327BE4B -> 0x0306B970
    |          在相同 member+0x4A8 装入另一任务类型
    |          task vtable 0x03AC8200
    |
    +-- NULL：
          再调用 group source virtual+0x70
          若结果也为 NULL -> 不安装
          若不为 NULL -> 0x0327BE86 -> 0x0306B54C
              在同一 member+0x4A8 装入
              task vtable 0x03AC7FF0
```

其中 `0x0306B970`／`0x0306B54C` 都先通过
`0x02DB0AB4` 清理成员原本的 `member+0x490`
控制状态，再将新任务子类安装在 `member+0x4A8`。
所以旧 `0x0306B510 -> 0x03906C88` 不是唯一的成员延迟任务工厂。

### 2. 两种新增任务各自进入不同的成员动作接口

| 成员任务 vtable | 原生回调 `+0x08` | 回调调用的成员接口 |
|---|---|---|
| `0x03AC7FF0` | `0x02F73074` | `virtual+0x4B8` |
| `0x03AC8200` | `0x02F73260` | `virtual+0x4C0` |
| **此前的** `0x03906C88` | `0x02F7301C` | 按 `task+0x42` 模式调用 `+0x4B0/+0x580` |

新增两种任务的 `+0x10` 都指向
`0x02F838E8`。这个短函数检测另一对象
`+0x154/+0x18` 的状态，不满足条件时设置
`task+0x20=1`；**并不是**已识别旧类
`0x03906C88` 的按 group clock 定时回调。

因此，上述三种任务绝不能按“普通 RMB vs Shift”二元分类。
真实差异首先来自所在群组对象、现有成员任务、回调状态及成员动作类。

### 3. 同一个成员动作槽已经发现至少五种原生子类

在此前已确认的同一成员 vtable
`0x038FD658`／`0x03910500` 上，
新增接口及行为：

| 接口 | 成员原生实现 | 创建的动作 vtable | 类的更新函数 `+0x08` |
|---|---|---|---|
| `+0x4B0` | `0x03069844` | `0x03ACD208` | `0x0307C388` |
| `+0x580` | `0x0306A990` | `0x03913808` | `0x032599C8` |
| `+0x5B8` | `0x0306A8C0` | `0x03ADAA08` | `0x03259950` |
| **`+0x4B8`** | `0x03069948` | **`0x03ACD5A0`** | **`0x0307C464`** |
| **`+0x4C0`** | `0x0306A7E8` 或另一群组级实现 `0x02DC39CC` | **`0x03ACD6D0`** | **`0x0307CAD0`** |

`0x03069948` 使用
`0x0306998B CALL 0x0304E77C` 安装 `0x03ACD5A0`，
`0x0306A7E8` 使用
`0x0306A813 CALL 0x0304ED1C` 安装 `0x03ACD6D0`。
这两种安装器同样先清理成员 `+0x328`，并使用共同的
`member+0x330` 动作位置，但**动作类的更新函数不同**。

`+0x4C0` 在两张成员 vtable 上**不是相同实现**：
`0x038FD658+0x4C0 -> 0x02DC39CC`，该函数还会遍历
`owner+0xB64/B68` 对象数组并条件传播；
`0x03910500+0x4C0 -> 0x0306A7E8` 则是单成员安装器。
两者是通过类型和调用链联系起来的，不得把所有 `+0x4C0`
都当单个士兵私有接口。

### 4. 对 Shift 挤压根因的意义和限制

已经证明，同一个成员的目标接收器 `+0x368` 与多套
延迟任务、不同动作安装器共存。沿用旧的“三种动作类”
或强制 `+0x580` 等于 RMB、`+0x5B8` 等于 Shift 的模型
会丢失真实路径。

**仍没有证明**哪个用户 Shift 后继 MOVE 实例选择了
哪种群组处理器/定时任务，哪些成员分别保留了旧方向，
或哪个类产生了实测相向挤压。

这次新查到的两个任务根本上由 `group virtual+0x60/+0x70`
返回结果分叉；它们**不是按某个已验证的 Shift 键位分叉**。
若修改这两个分支或成员动作 vtable，没有实例关联就很可能破坏
普通 RMB、Shift 以外的合法行为。

**下一个可判定任务**：查明 `0x0327BD38` 方法指针所属真实
群组对象的构造/虚表基址及 caller task/order 引用；
确定该组对象是否和先前的 MOVE 槽位 `0x0390B4F0` 有身份联系。
然后针对可达的成员动作，继续比较新/旧端点与实际 motor 目标。
不要再重复证明 Shift 挤压；不授权 Native Patch。


## 2026-10-14 第13轮 · B 家族大任务引用→旧子任务几何→路线节点的类型化静态链（最新）

**重要纠错：** `0x03AE00E8`、`0x03AE0108`、`0x03AE0128` 是由三个不同构造器实际安装的相邻虚表；`0x03281408` 真实属于**第三张** `0x03AE0128+0x10`，尽管该槽地址数值上也等于第一张表+0x50。绝不能跨对象类型拼接。短期 MOVE task `+0x74` 影响辅助对象是否沿 `0x03263E7C→0x03263D68` 将关联大任务指针写入 `aux+0x20`（并对非空任务引用增加 `+0x18` refcount）。B 型任务构造器 `0x03263AB0` 把该辅助对象放到自身 `+0x58`；类型化 `+0x10→0x03281408→0x03281444` 依当前节点、`aux+0x20` 及 `task+0x158` 条件，分叉到普通 `0x031219B0` 或大任务特化 `0x03121ABC` 路线节点构造。特化构造器 `0x030ECB10` 以**独立第六个 ABI 参数**读取大任务 `+0x80/+0x84/+0x88/+0x90/+0x98/+0x158`，`0x030FE1E4` 沿旧子任务 `+0x08` 链将各自 `+0x18` 几何输入关联为原生路线，结果存 `node+0x70`，同时将 `node+0x08` 初始标记有效，因而随后一般重算并非无条件立刻覆盖它。原始 SHA `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a` EXE 实际完成 **168/168 opcode/objdump，22/22 E8，5/5 JCC，3/3 RIP vtable install，3/3 typed slots**；本地 **18/18 回归 PASS**。详见 `docs/current/N1_903_TYPED_BIGTASK_B_ROUTE_NODE_BRIDGE_20261014.md`、新只读审计与测试。**未证明某个玩家 Shift MOVE 实例命中 B 类型，也未证明 node+0x70→record[i]→motor goal 的错误因果；禁止 Native gameplay patch，禁止清空旧 subtask 以破坏原生渐进转弯。**
