# Better Shift Command — 普通 RMB / Shift：兵牌命令与成员局部目标交接，原始 EXE 静态闭环

**2026-10-11。状态：EXE 静态核验 PASS / 离线条件反例 PASS / Windows Native 补丁未构建 / WH3 运行未测试。**

目标 EXE SHA256：`518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`；原始基址 `0x140000000`，本文所有地址均为 RVA。游戏版本号 9.0.3 为用户标记，未独立认证 VERSIONINFO。不重新要求用户实测挤压是否存在；原有 V3 已记录渐进折返中的成员靠近及反向运动。本轮没有完整 V3 原始 JSONL，无法从静态码推出当时精确分支是否命中。

## 结论：相同新 MOVE 可以有不同的局部运动衔接，但并未证明成员自己完成玩家路点

1. **普通 RMB REPLACE**：原生发令入口使用替换策略，原生 MOVE 构造器 `0x030090BC` 在 `0x030090E7` 清空 `MOVE+0xA0` 初始共享状态。它**不是另一套步兵物理/寻路引擎**。
2. **Shift 后继 MOVE**：`0x0304433C` 的特殊交接分支在前一 MOVE 共享状态就绪、队列有下一条并满足其它条件时，调用后继 MOVE `virtual+0x38`（其实现 `0x008D3350` 恒真），通过 `0x030445AB` 转交共享状态，在 `0x030445B1` 弹出前一条 MOVE。这个**局部分支本身**未直接遍历士兵各自的任务完成字节，也未读取单位辅助计数 `+0x240`。这不能宣称整个引擎其它路径绝不检查成员状态。
3. **下一命令向士兵下发**：原生群组 `0x030D5490` 生成 48-byte 对齐的成员目标，`0x02F5F868` 构造 `packet+0x50=0x26`，随后逐个传入 `virtual+0x368`。36/38 张构造可追溯的成员虚表的共用接收函数 `0x0306B9F0` 看到包内 bit 0x20，会跳过“延迟建立成员任务 `0x02F5F7C8`”的分支，而进入直接处理。它并**不是**“旧任务没结束所以新目标不能发”的证据。此前 V3 对 `0x030D5490` 的 Hook 为零命中；本项为有条件静态可达，不冒充当次游戏动态路径。
4. **首次补齐到真正的局部消费者**：这 36 张虚表的 `virtual+0xE8` 最终全部到达 `0x03073224`（28 张直接，3/4/1 张经过不同包装函数）。该函数调用原生目标／姿态处理 `0x0315EC98`，然后**尾跳转 `0x03056ED4`**。所以“成员收到新目标”之后，确实还有逐成员独立的路线/空间关联处理，并非所有士兵共享一个完成字节。
5. **逐成员处理的分叉点**：`0x03056ED4` 每次从成员类型相关对象重新生成并写入 `member+0x910` 头 32 字节；但是否保留 `member+0x930/+0x938` 的上次空间关联，要依据该成员的旧指针、归属上下文、`member+0x104` 动作模式与 `0x018325EC` 空间几何检查。必要时通过 `0x0312D088` 再查询新关联，或者清空缓存。这个机制允许一次共同目标下发后，**不同成员的缓存选择不同**；它尚不能被直接命名为“独立推进下一个玩家 Shift 路点”。
6. **成员类型差异**：四张成员虚表的包装函数 `0x02F4F910` 还使用 `member+0x910/+0xB80` 构造局部曲线，并再次调用共同接收；另一张的 `0x0311C92C` 通过 `member+0xB60` 进行不同的局部运动处理。不同成员类型的内存字段不可一概而论。
7. **纠正前轮“第二成员分发路径”的误判**：原生 `0x030135E0` 确实调用 Mode 0 生成器 `0x030C9A64`，但其 `0x0301389E/0x03013B9C → 0x02E0AFDC` 构建的是 **28 字节记录**，`0x030138AD/0x03013BAB → 0x02DED114` 则按 `0x1C` 步长**追加到数组**并增加数量；检查到的函数内部不是对士兵的 virtual+0x368 分发，不能冒充模型目标交接，也不能用此解释旧采集器零命中。

### 原生局部缓存核心分支（从机器码而非变量名反推）

```text
0x03073224 -> 原生 0x0315EC98 -> jmp 0x03056ED4
                                      |
                            0x03056F01 -> 0x03057D24
                                      | (总是重算/复制 +0x910 头32字节)
                                      +-- 返回标志==1 ---> 清空 +0x930/+0x938
                                      |
                                      +-- 旧 +0x930 == nullptr ---> 查找新缓存
                                      |
                                      +-- 旧指针 == 当前环境关联，actor mode 不为1/2 ---> 查找新缓存
                                      |
                                      +-- 其它情况：0x018325EC 空间检查
                                                  +-- 返回1 ---> 保留旧 +0x930
                                                  +-- 返回0 ---> 0x0312D088 查找新 +0x930
```

在已记录的 V3 `member+0x104==0` 情况下，如果旧关联与当前上下文相同，该路径会刷新空间缓存；如果两者不相同，仍可能经几何检查保留旧缓存。这是**实际原生分支的离线反例**，但我们没有 V3 当时的 `+0x930` 与环境指针，所以不是该回合实际发生的证据。

`0x0312D088 → 0x0312D0D0 → 0x02F8AB54` 是与空间区域/候选定位有关的链。特别注意：`member+0x930` 不能直接称为玩家路点、运动指令或最终速度。当前不能凭此修改。

## 明确否决的旧修复方式

- 不要强制所有士兵的局部任务 `task+0x20` 同时完成，它是另一类成员任务的完成字节，且目标包 `0x26` 本来就跳过该延迟分支。
- 不要把快速单位 MOVE-work 调用次数理解成每名士兵已走完全部路径；V3 中快速发令的两轮产生不同的后续挤压程度。
- 不要把 `member+0x930` 擅自改成 nullptr、清空全部路径缓存或强制成员相同：它可能保存空间区域位置；可能导致直行、避障、死亡/载具回归。
- 不要启用旧版 `0x0304459D` 跳过共享状态继承的 Win64 试验 DLL。它虽已通过独立构建，但没有证明保持 CA 渐进转弯，也没有解决上述成员独立缓存问题。
- 不要恢复 Lua 重发命令、直接改 OrderHead、强改模式 `member+0x104`。
