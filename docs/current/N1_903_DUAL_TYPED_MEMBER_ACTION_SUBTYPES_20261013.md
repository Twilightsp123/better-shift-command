# N1 / 2026-10-13 / 型别确认的同成员两种动作子类及真正 motor 提交分叉

**此结果覆盖上一轮不严谨的“0x0306A8C0 自动接续 0x032599C8”的拼接。** 固定原始 EXE SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`；本地独立 PE/unwind/objdump 检查 **19 个 opcode、5 个 E8/E9 直接控制流目标、6 个 typed vtable 槽、2 个 RIP LEA vtable 安装** PASS，原始游戏 EXE 未修改。

## 相同一名成员，两个不同虚函数安装不同动作对象，但目标存储位置相同

此前已静态识别两张成员 vtable `0x038FD658`、`0x03910500` 的接收器 `+0x368=0x0306B9F0`。本轮进一步确认相同两张真实成员 vtable 同时提供两种安装方法：

| 同一成员的虚方法 | 原生实现 / 机器码 | 在同一 `member+0x330` 构造 | 子类 vtable / `+0x08` 方法 |
|---|---|---|---|
| `+0x580` | `0x0306A990` | `0x03249350` | `0x03913808` / `0x032599C8` |
| `+0x5B8` | `0x0306A8C0` | `0x03248EC8` | `0x03ADAA08` / `0x03259950` |

虚槽精确证据：
`0x038FDBD8 = 0x0306A990`,
`0x038FDC10 = 0x0306A8C0`,
`0x03910A80 = 0x0306A990`,
`0x03910AB8 = 0x0306A8C0`。
二者安装器分别在 `0x0306A99A`、`0x0306A8CA` 执行相同
`lea rbx,[rcx+0x328]`，后分别于 `0x0306A9AC`、
`0x0306A8DC` 执行 `lea rcx,[rbx+8]`，所以动作类对象均占用
**`member+0x330`**。这是同一成员对象上会因不同原生命令/任务条件
而安装不同子类的真实代码能力，不代表历史玩家操作已选中其中任何一类。

## 与最终 motor 提交的区别：只有已证明的 A 子类路径不能反过来算作 B 子类

**A 类型 `+0x580`** 有至少三个带原生结构的调用点：
`0x02F79C3D`、`0x02F79D6E`、
`0x02F7A116`，取成员 vtable+0x580，将不同命令记录转为对象。
安装器 `0x0306A990` 的直接 E8 指向 `0x03249350`，
创建带虚表 `0x03913808` 的动作类；
其 `+0x08=0x032599C8` 存在
`0x03259C55 CALL 0x0306EF1C`，
原生 `0x0306EF96 JMP 0x0311954C`，
而 `0x0311963A` 正是以前 Windows Frida 真实采集到的
`member+0x1E0` motor goal 更新站点。**该调用并非无条件，仍有内部谓词。**

**B 类型 `+0x5B8`** 在上一轮
`0x03117E8C` 的条件发包 `0x03117EF7` 等位置命中；
安装器 `0x0306A8C0` 的直接 E8 指向 `0x03248EC8`，
创建带虚表 `0x03ADAA08` 的动作类；
此类 `+0x08=0x03259950`，只是在本函数里
`add rcx,0xC0; jmp 0x0181CC98`，**不是 A 类型的 `0x032599C8`**。
不能把 `+0x5B8` 安装与 `+0x580` 动作处理函数拼成
一条静态已经打通的单一 MOVE→motor 写入链；
B 类型其它更新/派发消费者仍可间接触及 motor，不能排除。

这也提示：之前计划只修改 `nextSubtask` 四个 float
存在遗漏——真实成员在**同一个动作槽**可能选择不同原生子类，
相同几何值未必走同一个 tick/update/目标写入分支。

## 与用户 BSC 目标有关的严格证据界限

**已实证：** RMB／Shift 在原生命令层有队列 replace/append；
后继 MOVE 可条件复用大任务并条件用旧 subtask 投影；
同类成员有两种不同动作安装接口并共享同一动作槽，
它们的动作 vtable tick 及至少一条 motor 目标下发路径不同。

**仍未实证：** RMB 必选 +0x580 或 Shift 必选 +0x5B8，
在用户真实 Shift 后继路段确实发生的子类切换、
原始 `task+0x160` 的 nextSubtask 与
`0x03117D44` 的某个具体 RDX 是同一实例、
哪种子类/几何关系导致兵牌内相向路线交叉。
目前是结构类型/原生调用的真实证明，不是挤压因果。

下一阶段只需要继续静态追
`+0x580` 的三处真实原生调用者对象、
`+0x5B8` 的任务类型与队列槽位引用、构造新/旧
`member+0x330` 动作子类时的触发门槛。
如果它们可以通过单个 MOVE task/order 关联，才决定是否必须一次极短
实例身份取证；**现在不要求玩家实机测试，不制作 Native Patch。**
