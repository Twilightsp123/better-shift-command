# 2026-10-13：普通 RMB vs Shift 的相同底层、不同前序几何（原始 EXE 静态审计）

**独立原始 EXE 校验完成**：SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`，43/43 opcode 守卫、7 个 unwind 所属函数中 43/43 GNU objdump 真实指令起点、4/4 E8 调用目标、常量 `+0.5f`（`0x0391CBC8`）与 `-0.5f`（`0x0391CF80`）。**静态验证，不是 Windows 游戏操作，不能证明 Shift 挤压根因。**

## 相同点

两者不是不同的底层士兵移动引擎。`0x030323C8` 是统一 MOVE 命令处理入口，**游戏内部队列管理器也可能调用它，不能仅凭入口命中就认定 RMB**。命令最终走同类 MOVE 槽位（vtable `0x0390B4F0`）和 CA 原生任务/成员运动系统。尤其：

```asm
0x0311E636 call 0x0311E80C  ; 旧任务复用 state=1
0x0311E772 call 0x0311E80C  ; 新建任务 state=0
```

**两个路径使用同一个原生任务生成器 `0x0311E80C`。** 不应靠两套运动算法解释差异，也不应让 Lua 替换原生 Shift。

## 不同点一：队列生命周期

`0x030323FC` 接收 R9B，`0x030326BB` 把 R14B 交给 DL，`0x02F50425/27` 判断：`DL=0` 清既有队列（`0x02F50444`），`DL!=0` 保留并追加槽位。通常对应普通右键替换移动和 Shift 追加移动，但**没有历史游戏日志能把特定用户键位/命令实例与这个 R9B 的值一一绑定**。

## 不同点二：在后继槽位有条件复用已有大任务

`0x03044562` 通过 typed MOVE slot `vtable+0x40` 调 `0x03039FB0`，成功满足旧任务 status4、`+0x24`、`+0x158` 及 group 检查才返回原 task；`0x030445AB` 再经下一 MOVE 的 `vtable+0x48` 调 `0x03040864`，令 **同一 task 指针** state=1 并更新新路段 `+0x120/+0x130/+0x140`。不是所有 Shift 后继 MOVE 必定成功交接，也不应认定任何一次 RMB 必定只走 state=0。

## **最关键差异：相同子任务的横向几何端点，有两种数据来源**

**两套处理最终写同一个 `nextSubtask=[task+0x160]` 的 `+0x48,+0x4C,+0x50,+0x54` 字段；这是本轮新确认的精确比较点。**

1. **共同生成器中的新段投影**：`0x0311E829` 取 nextSubtask；在 `0x0311EB14` 成功检查且 `0x0311EB3C` 子任务 flag=1 等条件下，`0x0311EB42..0x0311EBB2` 使用新路段位置、朝向查表（`nextSubtask+0x68` heading index）、新长度，分别乘原生常量 `-0.5f` 与 `+0.5f`，构造一对局部端点并写至 `nextSubtask+0x48/+0x4C/+0x50/+0x54`。
2. **state=1 继承投影**：同一个共同生成器返回后，`0x0311E63B` **必须重新检查** `task+0x24==1`，否则跳过。通过时才从 `task+0x158` 读旧 subtask，并将其引用存入 `nextSubtask+0x20`，接着按 `oldPosXZ ± 0.5*oldExtent*oldDirectionXZ` 于 `0x0311E6A4/E6A9/E6E2/E6E7` **覆盖刚才共同生成器写过的同一组 nextSubtask 局部端点**。最后才清主 task `+0x158`，不等于断开 nextSubtask 保存的旧引用。

这提供了明确的比较对象：**不是“RMB 有新寻路算法，而 Shift 有旧寻路算法”，而是“同一个原生生成器之后，有条件的后继 MOVE 会用旧子任务位置／方向／长度覆盖新段局部目标端点”。** 这种方向连续性可能是 CA 合法渐进转弯机制，**不能仅因有覆盖就判定错误**。

## 对 180° 折返挤压的可检验机制假说

对于相反的新旧路段方向，`oldDir≈-newDir`。共同生成器生成的新段端点与 state=1 覆盖的旧方向端点可能横向位置、两端序发生变化；若成员的对应侧顺序/局部目标分配没有与新路段一致地转换，就可能出现单位内部相向穿插。**尚未证明这种变化确实发生在用户 Shift 命令的实例，亦没有证明它导致碰撞；这是假说，不是修复结论。**

后续逆向必须沿两个输出（`0x0311EB8C/EB92/EBAC/EBB2` vs `0x0311E6A4/E6A9/E6E2/E6E7`）追逐名成员目标消费者和朝向／阵型索引，而不是继续笼统搜函数名。若尝试补丁，应保持队列、任务引用、平滑转弯和避障，不直接 `task+0x158=NULL` 或拦截全部过渡投影。

**没有进行新的实机测试；没有修改 gameplay。** 相关完全脱敏只读本地复核程序输出 43 opcode + 4 E8 + 2 个 float 常量校验全部 PASS。
