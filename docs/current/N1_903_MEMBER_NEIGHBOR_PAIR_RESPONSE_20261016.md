用**原始 EXE** 只读验证 **122/122 机器码、GNU objdump 真正指令起点、18/18 E8、8/8 JCC**，确认涉及 **5 个原生 unwind 函数**；本地独立 12/12 回归 PASS，包括真实 EXE 和 Python -O/错误 SHA 负例。公开 GitHub 的 14 项合同测试另需 CI 确认，私有 EXE 一项必须跳过。全部是 **EXACT_ORIGINAL_EXE_STATIC + SYNTHETIC_BRANCH_CONTRACT**，绝不等于某个玩家 Shift 折返已命中或已经找到物理挤压根因。

## 一、发现真实的“当前成员 → 空间候选 → 选中邻近对象”链

`0x03081EB4` 成员 Tick 在 `0x030822F9` 调 `0x03054B84`，后者是真正综合成员状态、邻近对象与运动方向的条件函数，不是单纯「读取世界目标」。它并非所有动作或成员状态必执行：入口就受 `member+0x2E0/+0xB10/+0x324/+0x30` 等门槛约束。

按已明确的同一函数寄存器和对象字段：

1. `0x03054D7B` 准备结果向量 `0x04338CD8`，`0x03054DB3 CALL 0x03062988` 带当前成员和附近查询点收集候选。
2. `0x03062988` 通过 `0x03062A90` 或 `0x03062AFF` 调 `0x03062688` 进行空间候选迭代，候选中实际读取 `+0x88/+0x90` 的位置；在 `0x03062835` 通过虚方法取回与当前成员同类布局的对象，`0x03062850` 检查 `0x03068B98`，`0x03062933` 有条件写入候选向量。
3. **重要类别门槛**：`0x0306288D..0x030628AD` 的某条件分支比较候选和当前对象的 `+0x80` 归属引用是否相同。相同引用要求共享的 `flags(+0x6C) & 0x01` 位；不同引用要求共享的 `0x02` 位。只有启用该筛选标志时才应用这个具体类别规则，不能将它说成总是屏蔽某一侧。
4. `0x03054DDE/DE8/DEC/DF7` 遍历候选、经 `0x030765B0` 获取实际对象并调用 `0x03068B98` 检验，然后用双方 `+0x80` 归属、`+0x74` 优先级、`+0x88/+0x90` 位置、`+0xE0/+0xE8` 当前速度和相对方向求分值。`0x03054F26 MOV RSI,RBX` 仅在选中时保存一个候选；这不是所有候选平等发包。
5. 同一 `0x03054B84` 在一条进一步受状态/距离保护的路径调用 `0x03055029→0x0311CED4`，才获取当前参考框架下的**世界目标**，再和当前位置、方向/速度比较。它可以另外考虑一个选择好的邻近对象 `RSI`。因此世界目标是否正确和接触响应是否同样触发是**两个不同问题**。

此处 `member+0x80` 是两种候选都按相同对象类型布局读取的「归属引用/分组引用」字段；尚未证明它在所有对象实例上严格等于 `UnitRoot` 或单调不变的 Group generation ID。绝不能因为地址相等就忽略对象池 ABA 风险。

## 二、进一步收敛至接触响应分发，但尚未确认最终速度写者

在 `0x03054B84` 的条件分支中：

- `0x03055647` → `0x0324EB24`
- `0x0305566A` → `0x0324E9DC`
- `0x03055688` → `0x0324E814`
- `0x030556A1` → `0x0324EE00`

这些是**四个条件性处理方法**，不等于一个 Tick 会把它们全部调用一遍；不同状态、邻近选择和动作类别会改变进入哪条分支。

随后另一受条件保护的路径 `0x03055780` 将一个按双方运动属性导出的标量加入输入，`0x030557BC CALL 0x030800C4`，传当前对象 `RCX`、环境/响应上下文 `RDX`、选中候选 `R8=RSI`，以及一组相对位置、速度和标志的栈参数。

`0x030800C4` 的 `0x030800E3/EA` 对双方 `+0x74` 优先级差做判断，`0x030801E0..0x03080247` 装配具有双方对象身份、位置、优先级标志的响应记录；`0x0308024D` 取上下文 `+0x1D8` 的对象并在 `0x03080257` **调用它的 virtual+0x10**。

**这里是新的下游未闭合边界**：原始机器码已证有接触/邻近响应记录被分发，但**尚未证明目标虚方法是谁、是否改写 member+0xE0/+0xE8、member+0x1C0，或直接修改位置。** 所以不能宣布根因是避障器，也不得未经身份确认去 Hook 这个虚表偏移。

## 三、比前22轮更明确的首次差异判定

如果两个士兵在同一 queued MOVE 中：
- `member+0x1E0` 目标和 `member+0x1F0` 的参考框架解析成相近、合理的世界目标；但
- 对应 Tick 的候选集合、`+0x80` 归属位、`+0x74` 优先级、`+0x6C` 类别位、最近候选 `RSI` 或四条响应方法出现不同，

那么**首次分叉可能位于邻近响应选择，而非上游路线目标安装**。只有验证其分发后的运动量变化及两名相邻士兵的实际实例，才能升级为挤压因果。反过来，若 world goal 已交叉，就优先回去查 `member+0x1F0` 的引用框架和路线生成代际，不应把邻近响应当替罪羊。

为了避免无限地址搜索，下一步只追 **`0x030800C4` 中 `[context+0x1D8] virtual+0x10` 的真实安装者/实现和输出到速度或 steering 的最近数据边**；若它只是通用事件通知而不改变运动量，应立刻排除并改查其他实际速度写入者。不要让用户再做一长串试验。
