# N1 · 2026-10-13 · 两种 MOVE 局部端点的成员动作下游（真实类型校验）

## 新静态结论

对原始 EXE 固定 SHA256 `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a` 继续沿之前明确的两套写端点函数：

- 共享 task 生成器的“新路段”端点：`0x0311EB8C/EB92/EBAC/EBB2`；
- 条件性 state=1 “旧方向”端点覆盖：`0x0311E6A4/E6A9/E6E2/E6E7`。

两者在匹配的 subtask 布局都涉及四个 float32：`+0x48/+0x4C/+0x50/+0x54`。本轮发现符合这份布局的原生动作几何分发路径，且首次通过同一套实际**成员虚表**把“接收包”与“动作下发”连接，而不是按相同虚函数偏移猜测对象类型。

```text
几何输入（符合 nextSubtask +0x48..0x54 布局）
0x03117D44
  ├─ 方法开始时调用另一个 +0x260 虚方法，非零可跳过打包
  └─ 读取四个端点和其它参数
     → 0x03117DEB CALL 0x0324983C（生成临时动作记录）
     → 0x03117E00 CALL 0x03117E8C
          ├─ [groupOwner+0xB64] 对象数组计数
          ├─ [groupOwner+0xB68] 对象指针数组
          └─ 经多个原生条件筛选
             → 对象 vtable+0x5B8
                  = 0x0306A8C0
                       → 0x03248EC8 → 0x03249510
                              → 0x02F5E8A4（动作参数复制）
                                 到对象+0x330 的嵌入动作状态
```

原生对象 vtable 的两套**同类型正对照**：

| 接收包虚表 `+0x368` → `0x0306B9F0` | 动作虚表 `+0x5B8` → `0x0306A8C0` |
|---|---|
| 槽位 `0x038FD9C0` | 槽位 `0x038FDC10` |
| 槽位 `0x03910868` | 槽位 `0x03910AB8` |

两项槽位的距离均为 `0x5B8-0x368`，并分别静态解析出上面两个目标函数。这避免了历史“所有 +0x368 都是士兵发包者”的类型混淆。**但是对象数组所含成员的具体生命周期和子类种类尚未穷举，不能断言每个成员都会通过 +0x5B8 分支。**

## 输入四个 float 的真实打包映射

经 `0x03117D44` 装配参数和 `0x0324983C` 的真实写入校验：

| 几何输入 | 临时记录目标 |
|---|---|
| `+0x48` | `+0x48` |
| `+0x4C` | `+0x4C` |
| `+0x50` | `+0x50` |
| `+0x54` | **`+0x60`** |

临时记录 `+0x54` 是 `uint16` 字段，**不是第四个 float**。后续 `0x02F5E8A4` 又根据类型复制和保留标志位。所以绝不能用简单 `memcpy(four floats)` 猜测成员动作格式，更不能直接互换两个端点的四个连续 DWORD 来“修正转向”。

## 验证和一个必须保留的反证

本地对精确原始游戏 EXE 运行只读 `audit_endpoint_dispatch.py`：

- **49/49** 原指令字节及真实 PE unwind/叶函数边界、GNU objdump 指令起点校验 PASS；
- **6/6** E8 直接调用关系 PASS；
- **5/5** 真实虚表槽位 PASS；
- **5/5** 本地测试 PASS（含错误 EXE 拒绝）。
- GitHub 研究分支另纳入轻量只读 `audit_typed_member_geometry_fanout.py` / `test_native_shift_re_typed_member_geometry_fanout.py`（29 个关键 opcode），确保这一层可在公开 CI 上被后续维护。

**此前新的猜想“公共生成器先写新端点，便已经下发／缓存，再被 state1 用旧端点覆盖太迟”仍不成立为证据。** `0x0311EBC8` 先调用的 `0x03105B4C` 在自己的 unwind 函数里直接维护队列/列表 `nextSubtask+0x58` 等字段，但**没有直接从 R13+0x48/+0x4C/+0x50/+0x54 读取四个端点**。不排除间接接口读了，现有静态证据**既不能确认也不能排除**旧新几何被不同组件并存消费。

**极其重要：当前并未建立** `task+0x160=nextSubtask` 的那个**具体实例**就是 `0x03117D44` 的 RDX 参数，也没有通过用户 RMB/Shift 的真实 order id、任务对象和成员目标实例串起运行时执行。静态“结构匹配 + 类型相符”不是运行时同一实例证明。

因此尚不可认定旧方向覆盖就是拥挤根因、也不允许 Native Patch。

## 2026-10-13 新增：同一原生成员可在 +0x580 / +0x5B8 安装不同动作子类（最新优先结论）

见 `docs/current/N1_903_DUAL_TYPED_MEMBER_ACTION_SUBTYPES_20261013.md`；
研究源码 `audit_dual_member_action_subtypes.py`、同名前缀单元测试。
在精确 SHA EXE 上通过 19/19 opcode、5/5 原生 E8/E9、
6/6 同一成员 typed vtable、2/2 RIP LEA 安装验证；CI PASS。

**必须覆盖本文件旧错误推断**：上一次找到
`0x03117E8C -> virtual+0x5B8=0x0306A8C0
-> ctor 0x03248EC8` 的成员几何安装，
并不直接沿 `0x032599C8` 更新 motor。
实际上 `+0x5B8` 的子类 vtable 是 `0x03ADAA08`，
其 `+0x08=0x03259950`；而
`0x032599C8` 属于**另一子类** vtable `0x03913808`，
由**相同成员对象**虚函数 `+0x580=0x0306A990`
通过构造器 `0x03249350` 安装。
两者都以 `lea rbx,[member+0x328]; lea rcx,[rbx+8]`
在**同一 `member+0x330` 动作位置**构造不同子类。
`+0x580` 调用可在
`0x02F79C3D/0x02F79D6E/0x02F7A116` 看到；
`+0x5B8` 在 `0x03117EF7/0x03118040`。
前一类动作的 `0x032599C8` 条件路径
`0x03259C55 -> 0x0306EF1C -> 0x0306EF96 ->
0x0311954C` 能到达此前实机命中过的
`0x0311963A` motor goal 写入。
**切勿推断**这也必然是另一类型 `+0x5B8` 的真实 tick 路径。

**新的可修复层搜索方向是动作类选择/转换及成员的目标对应**，
不只是假定改写 oldSubtask 的四个 float。
但尚未有 CMD/Shift 输入实例、`task+0x160` 与具体子类的指针配对，
因此不说 RMB 使用 A、Shift 使用 B；
目前对“哪条造成 Shift 挤压”没有因果结论，不授权任何 gameplay 修改。
