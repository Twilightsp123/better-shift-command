# BSC / WH3 9.0.3 — RMB、Shift 与成员实际运动目标的差分审计

**日期：2026-10-11。原始 EXE SHA256：** `518c4f292f275142df13b96b9db704a3db7b4870b2c519df83d850596ecc822a`。所有地址均为 RVA。

## 本次真正检查的两个条件

1. 从普通 RMB 新建 MOVE 和 Shift 符合条件时的共享状态续接，接到成员空间状态筛选。普通 RMB 初始 `MOVE+0xA0=null`；Shift 特殊续接使用共享状态并切入 `state=1`，这两种状态最终共享原生成员运动系统。
2. **同一个成员收到下一批目标时，什么条件会让它继续现有运动目标、做局部重置，或者完整重建目标？** 沿机器码追到两个原生动作类型，区分处理方式，不再把所有兼容分支统称为「保留旧命令」。

## 机器码闭环与修正

- 原生空间兼容判断 `0x03102444`：`0x03102461` 执行 `cmp rdx,r9`（旧关联与候选关联）；若指针相等，`0x03102464` 直接跳到 `0x0310255E` 返回 `true`，**不再检查后面的几何条件**。这只是原生「空间关联兼容」判断，不是两个运动方向已经相同。
- **群组动作 A** `0x03088618`：在特定动作 `+0xE8=0`、`+0x90=1`、成员状态与群组参考符合条件时，调用 `0x030522FC → 0x03102444`。兼容时在 `0x030886E2` 跳过目标重建；不兼容时在 `0x0308872E` 调用 `0x03071E04` 安装新的成员目标记录。这一动作类型允许同兵牌成员因各自空间引用不同而**出现不同的目标切换时机**。
- **成员动作 B** `0x0308393C`：它同样调用 `0x03102444`，但**兼容时并非直接不动**：`0x03083BB9 → 0x0306EF1C → 0x03071EA4 → 0x0311954C`，先清理 `member+0x828` 及 `+0x710` 的部分旧状态，再进入原生运动目标写入器。非兼容则 `0x03083B53 → 0x03071E04 → 0x03071F20 → 0x0311954C`，执行较完整的目标重建。两条分支都可能更新新目标，只是重建的上下文不同。**上轮「兼容必保留旧目标」的笼统结论在动作 B 上不成立。**
- 目标写入器 `0x0311954C` 本身还有早退条件（如 `member+0x228==1`），`0x03102CA4` 通知运动子系统也有位标志条件。因此，「调用写入器」仍不等于该帧一定改变了目标。

## 对 RMB 与 Shift 的因果含义

这套局部筛选函数是原生公共代码，并没有在函数内部显示用 RMB/Shift 直接二选一。但是两种 MOVE 的高层路线状态来源不同，所以进入它们的**新候选空间关联**和**动作状态**可以不同。

在一个严格按原生条件构造的离线反例里，同一兵牌的 A 士兵新旧空间引用相同，群组动作保留已有 motor goal；B 士兵引用不同且空间检查失败，群组动作完整重建目标。**这是机器码允许的分叉，而非历史 V3 已发生的分叉。** 对另外一种原生成员动作 B，兼容时仍会局部重置和写新目标，不能把所有士兵视作同一种「继续旧命令」机制。

这与用户观察的「前后成员朝反方向走」在机制层面相容，**还不能证明历史 35–43 秒场景确实走了哪个动作类型和判断分支**。历史 V3 没有记录 `+0x930/+0x710`、动作对象 VTable 及这些分支命中次数，原始 EXE 静态字节无法反推历史事件。

## 已排除和唯一需取得的动态判据

排除：全局清空 `member+0x930`、修改统一动作 `+0x104`、强行统一局部轨迹编号、取消 Shift 全部状态继承、或直接把群组兼容的返回值统统强制 `false`。这些都会波及普通 RMB、特殊成员/战斗动作或 CA 的渐进弯道。

目前剩下的一个**可证伪判据**是：同一次原生 Shift 的路段续接期间，是否确实存在同兵牌成员采用群组动作 A，且有的命中 `0x030886E2` 的兼容跳过、有的命中 `0x0308872E` 的完整目标重建；同时相同条件下普通 RMB 是否表现不同。原始静态文件不能证明历史 V3 分支活动。本轮不要求用户进行游戏测试；应先在独立 Windows 上构建/验证精确范围的只读观测器及安装/卸载安全性，再由一轮完整综合测试对照，不能让用户反复试错。
